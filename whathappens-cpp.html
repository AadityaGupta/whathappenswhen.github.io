Track 01 — How C++ runs

Foundations

Why C++ is chosen when failure isn't an option: it compiles all the way to native machine code with no interpreter, no JIT and no garbage collector between your code and the CPU. Start here and the rest follows.

01Foundations

You compile and run a C++ program

Analogy: C++ is translated all the way down to the machine's own language before it runs — nothing stands between your code and the CPU at run time.

C++ is compiled and executes natively. The build has distinct stages: the preprocessor expands #includes and macros into one big text (a translation unit); the compiler turns each translation unit into assembly and then an object file of machine code; the linker stitches all the object files and libraries together, resolving every symbol into a single executable; and a loader finally maps it into memory to run. There is no virtual machine, no just-in-time step, and no garbage collector at run time — which is exactly why C++ dominates where every microsecond and byte counts.

Two consequences to internalize early. Compilation is per translation unit — each .cpp is compiled on its own, which is why headers exist (to share declarations), and the One Definition Rule says each entity may be defined once across the whole program or you get linker errors. And because nothing babysits you at run time, the optimizer is your performance engine: it inlines, unrolls, vectorizes and elides, turning high-level abstractions into tight machine code (the "zero-overhead principle" later in this guide).

Contrast the alternatives: Python interprets bytecode as it runs; Java compiles to bytecode that a JVM JIT-compiles and a garbage collector manages. C++ front-loads all of that into the build, trading longer compile times and manual resource management for predictable, no-surprises run-time behavior — the exact deal a drone, a car, or a satellite needs.

Why it mattersNo GC pauses, no JIT warm-up, no VM: deterministic execution straight on the metal is why real-time and safety-critical systems pick C++ (and C).

02Foundations · key idea

Where an object lives: the stack vs the heap

Analogy: the stack is a stack of plates you add and remove only from the top (fast, automatic); the heap is a big warehouse where you rent space and must remember to return it.

Local variables live on the stack: a region that grows and shrinks automatically as functions are called and return. Calling a function pushes a stack frame (its locals, parameters, return address); returning pops it, instantly reclaiming everything. It's extremely fast (just moving a pointer), cache-friendly, and can't leak. The trade-offs: stack space is small and fixed (often a few KB to a couple of MB), and an object's lifetime is tied to its scope.

The heap (the "free store") is for objects whose size or lifetime you decide at run time: you request memory with new and it stays until released. It's flexible and large, but slower (the allocator must hunt for a free block), it can fragment over time, and each allocation is a lifetime you now own and must not lose. On a microcontroller the heap is tiny and fragmentation can be fatal, which is why hard-real-time and safety code often forbids heap allocation after startup.

The instinct to build: prefer the stack and value semantics — they're faster, automatic, and leak-proof. Reach for the heap only when you must (runtime-sized data, polymorphism, shared ownership), and when you do, wrap it so something owns it automatically (RAII and smart pointers, coming next). Knowing where an object lives — and therefore how long it lives — is half of understanding C++.

On the vehicleReal-time and flight code commonly pre-allocates every buffer and object at startup, then never touches the heap again — so the running system's timing is fully deterministic.

03Foundations · the big one

An object goes out of scope (RAII)

Analogy: a self-closing, self-locking door — the moment you leave the room it shuts behind you, whether you walk out calmly or bolt in a panic.

RAII — Resource Acquisition Is Initialization — is the single most important idea in C++. The rule: tie a resource (heap memory, a file, a mutex lock, a socket, a GPIO line) to the lifetime of an object. Acquire it in the constructor; release it in the destructor. Because C++ guarantees that when an object goes out of scope its destructor runs — automatically and deterministically — the resource is always released.

The power is in the phrase "on every exit path." Whether the function returns normally, hits an early return, or an exception is thrown and the stack unwinds, the destructor still runs. So you never write manual cleanup and you cannot leak by forgetting — the compiler inserts the release for you at the closing brace. Objects are destroyed in reverse order of construction (LIFO), which is exactly right for nested resources.

This is why modern C++ barely uses raw new/delete: std::lock_guard takes a mutex and releases it at scope end; std::unique_ptr frees memory when it dies; std::fstream closes the file. Compose them and cleanup becomes automatic and exception-safe. For embedded work, RAII is how you guarantee a motor is disabled or a bus lock released even when something upstream goes wrong. If you learn one C++ thing, learn this one.

{
    std::lock_guard<std::mutex> lk(m);       // acquire: mutex locked
    auto buf = std::make_unique<Frame>();   // acquire: heap owned
    process(*buf);
}   // ← lock released AND buffer freed here, automatically,
    //   even if process() throws. No cleanup code needed.

04Foundations · key idea

You copy an object — or move it

Analogy: copying is photocopying a document (slow, and now there are two); moving is handing over the original and keeping nothing (instant).

Objects in C++ have value semantics by default: assign or pass one and you get an independent copy. For a type that owns a heap buffer (like std::string or std::vector), that copy is deep — it allocates a new buffer and duplicates every byte, so the two objects are fully independent. Correct, but potentially expensive: copying a megabyte vector copies a megabyte and hits the allocator.

C++11 added move semantics for the very common case where the source is about to disappear (a temporary, or something you explicitly std::move). A move steals the guts: it copies the internal pointer and nulls out the source, turning an O(n) copy-plus-allocation into an O(1) pointer swap. The compiler picks move automatically for temporaries and return values; you opt in for a named object with std::move, which really just says "you may treat this as expiring."

For systems work this matters twice. It's a big performance win — return large objects by value cheaply, hand buffers between pipeline stages without copying. And it enables move-only types like unique_ptr and std::thread that represent unique ownership and must never be silently copied. Writing types that move cheaply, and knowing when a copy is secretly happening, is core to fast, correct C++.

05Foundations

Your code invokes undefined behavior

Analogy: UB is a contract you broke with the compiler — once broken, it's allowed to do literally anything, from "seems to work" to a silent security hole.

C++ trades safety for speed through a contract. Do certain forbidden things — read past the end of an array, use a dangling pointer, overflow a signed integer, race on shared data, dereference null — and the behavior is undefined: the standard imposes no requirement whatsoever. It might crash, might appear to work, might corrupt unrelated memory, might behave differently the moment you enable optimization. That unpredictability is what makes UB the scariest class of bug — the program can be wrong without ever telling you.

Why is it allowed? Because assuming you didn't invoke UB is precisely what lets the optimizer be aggressive: it can assume pointers aren't null, loops terminate, and indices stay in range, and generate the tight code that makes C++ fast. The price is that the responsibility for honoring the contract falls on you, the programmer.

The professional response isn't "be careful" — it's to build guardrails. Turn on all compiler warnings and treat them as errors; run the sanitizers (AddressSanitizer, UBSanitizer, ThreadSanitizer) in testing to catch UB at run time; use static analysis; and prefer safe constructs (vector::at, std::array, references over raw pointers, RAII over manual new/delete). In safety-critical work, coding standards like MISRA exist largely to forbid the constructs that lead to UB. Respecting UB — knowing it exists and engineering against it — is a hallmark of a serious C++ engineer.

Safety noteIn a flight or weapon system, UB isn't a crash you restart — it can be silent corruption with real-world consequences, which is why these domains stack standards, static analysis and sanitizers on top of the language itself.

Track 02 — Who owns what

Memory & ownership

C++ has no garbage collector, so ownership — who is responsible for freeing a resource — is something you design. Modern C++ makes it automatic and safe with smart pointers built on RAII.

06Memory

You call new and delete (and why you shouldn't)

Analogy: raw new/delete is a library book with no due-date reminder — easy to forget to return, and easy to "return" twice.

new allocates an object on the heap and hands back a raw pointer; delete frees it. The problem is that a raw pointer says nothing about ownership — it doesn't record who is responsible for the delete, or when. So real programs leak (nobody deleted it, or an exception skipped the delete), double-free (two places deleted the same object), or use-after-free (deleted, then used). These are among the most common and dangerous C++ bugs and a huge share of real-world security vulnerabilities.

Manual new/delete also isn't exception-safe: if anything between the new and the delete throws, the delete is skipped and you leak. Once you have more than one resource and more than one exit path, doing this by hand correctly becomes genuinely hard.

The modern answer is: almost never call them directly. Wrap ownership in RAII smart pointers (unique_ptr, shared_ptr) created with make_unique/make_shared, which delete automatically and exactly once, on every path. Prefer stack objects and owning containers (a vector owns its storage) over naked heap allocation. A raw pointer is still fine as a non-owning observer — it may look but not free — and that's the one clean rule to carry: a raw pointer never owns.

On the vehicleA slow leak in a long-running autonomous system eventually exhausts memory and kills it mid-mission — so ownership discipline is a safety property, not just tidiness.

07Memory · key idea

You own something with unique_ptr

Analogy: a single house key that only one person may hold — to give it to someone else you physically hand it over; you can't photocopy it.

std::unique_ptr models exclusive ownership: exactly one unique_ptr owns the heap object, and when it's destroyed (at scope exit) it deletes that object — automatically and exactly once. It's RAII for heap memory, and it's a zero-overhead abstraction: under the hood it's just a pointer, so it costs nothing at run time versus a raw new/delete, yet the compiler enforces the ownership rules for you.

The defining property is that it's move-only: you cannot copy it (that would create two owners of one object), so to transfer ownership you std::move it — after which the source becomes nullptr. You create one with std::make_unique<T>(args...), which is exception-safe and keeps naked new out of your code entirely.

This is the default smart pointer — reach for it first, and only upgrade to shared_ptr when you genuinely have shared ownership. It can also own arrays and take a custom deleter, which makes it the RAII wrapper for any resource — e.g. a unique_ptr whose "deleter" closes a C library handle or a file descriptor, so cleanup happens automatically at scope exit.

08Memory · advanced

You share ownership with shared_ptr (and hit a cycle)

Analogy: a shared cabin with a sign-in sheet — it stays open while anyone's name is on it, and the last person out locks up.

std::shared_ptr models shared ownership through a reference count kept in a heap "control block." Copying a shared_ptr bumps the count; destroying one drops it; when the count reaches zero the object is deleted. Use it when an object genuinely has several owners with independent lifetimes and you can't say which will outlive the others.

It isn't free. The control block is an extra allocation (make_shared fuses it with the object's), and the count updates are atomic so the pointer is thread-safe to copy — safe, but heavier than unique_ptr. So don't reach for shared_ptr by default "just in case"; overusing it adds overhead and, worse, muddies who really owns what.

The famous trap is the cycle leak: if A holds a shared_ptr to B and B holds one back to A, neither count ever reaches zero and both leak forever, GC-less. The fix is std::weak_ptr — a non-owning observer of a shared object that does not raise the count; you call lock() on it to get a temporary shared_ptr if the object is still alive (and a null one if it's gone). The pattern: an owner points to what it owns with shared_ptr, and anything pointing "back up" or merely watching uses weak_ptr.

Sim · reference count; object dies at zero; weak_ptr doesn't count

Add and remove owners and watch the count. A weak_ptr observes the object but never keeps it alive — the tool that breaks reference cycles.

On the vehicleWhen several subsystems observe the same live object — a tracked target, a shared map — shared_ptr plus weak_ptr cleanly expresses "shared use" and "watch without owning."

09Memory

You pass an argument to a function

Analogy: hand over a photocopy (by value), lend the original to be changed (by reference), lend it read-only (const-ref), or give an address that might point to nothing (pointer).

How you pass a parameter quietly decides three things: copying, mutation, and lifetime. By value (T) copies the argument — safe and independent, but pays for the copy: fine for small trivial types like int or a handle, wasteful for a big object. By reference (T&) gives the function the caller's actual object — no copy, and it may modify it.

By const reference (const T&) is the workhorse: "read a big object without copying it." No copy, cannot modify, and it's the default way to pass strings, vectors and structs you only read. A pointer (T*) is like a reference but can be nullptr and can be re-pointed — use it to say "this argument is optional (may be absent)," or where you genuinely need pointer arithmetic; otherwise prefer references, which can't be null.

The guideline to internalize: pass cheap-to-copy types by value; pass everything else by const& to read and by & (or via a returned value) to modify; use T* only when "no object" is a real option. For a "sink" parameter you intend to store, take it by value and std::move it into place. Getting this right is the difference between a function that's zero-copy and one that silently deep-copies a megabyte on every call.

On the vehiclePassing large messages and images by const& instead of by value is one of the simplest ways to keep per-frame CPU cost — and latency — down.

10Memory · advanced

A pointer dangles (use-after-free & iterator invalidation)

Analogy: a forwarding address for a house that's been demolished — the address still "works," but it points at rubble.

A pointer or reference is just an address. If the thing it points at is destroyed, the pointer is now dangling, and using it is undefined behavior — a crash, or silent corruption. The classic causes: returning a reference or pointer to a local variable (destroyed the instant the function returns); keeping a pointer to a heap object after it's been deleted (use-after-free); and the one that surprises everyone, iterator invalidation.

Iterator invalidation is holding an iterator, pointer, or reference into a container and then modifying the container. The killer example: push_back into a vector can trigger a reallocation (from the growth scenario) — the vector moves all its elements to a new, larger buffer and frees the old one, so every existing iterator, pointer, and reference into it now points into freed memory. Erasing elements shifts things similarly. The value you carefully saved a moment ago is now a landmine.

Defenses: never return a reference to a local; prefer values and owning containers; learn each container's rules (a vector invalidates on reallocation, while std::list and node-based maps are far more stable); re-fetch iterators after any mutation; and run AddressSanitizer, which catches use-after-free and out-of-bounds access the instant they happen. This entire class of bug is exactly what smart pointers, RAII and value semantics exist to prevent.

Safety noteUse-after-free is both a crash source and the number-one memory-safety vulnerability class — a big reason it gets so much scrutiny in defense and automotive code, and a big part of why Rust is rising alongside C++.

11Memory · advanced

The compiler copies, moves & destroys your class (Rule of Zero/Five)

Analogy: if your class owns something, C++ needs to know how to copy it, move it, and clean it up — get one wrong and two copies quietly share, or double-free, the same resource.

Every class has special member functions the compiler can auto-generate: the destructor, copy constructor, copy assignment, move constructor, and move assignment. They govern what happens when your object is destroyed, copied, or moved. If your class manages a raw resource (a bare pointer to heap, a file handle), the compiler's default is a member-wise copy — it just copies the pointer — so two objects believe they own the same resource, and you get double-free or shared-mutation bugs.

The Rule of Five says: if you have to hand-write any one of {destructor, copy, move}, you almost certainly must write all five, consistently. But the better modern guidance is the Rule of Zero: don't manage raw resources yourself at all — hold them in members that already do it correctly (unique_ptr, shared_ptr, vector, string). Then every compiler-generated special is automatically right and your class needs none of them.

So in practice you write either a class that owns nothing raw (Rule of Zero — the goal) or, rarely, one careful RAII wrapper that implements all five. You can also be explicit with = default ("generate this") and = delete ("forbid this") — for instance deleting the copy operations to make a type move-only, exactly how a unique device handle should behave.

class LidarDriver {
    std::unique_ptr<Connection> conn_;   // owns the connection
    std::vector<Point>          scratch_; // owns its buffer
    // No destructor, no copy/move written — the members handle everything.
    // Copy is auto-deleted (unique_ptr is move-only); move just works.
};   // Rule of Zero: correct by construction.
Why it mattersThe Rule of Zero is why disciplined modern C++ has so few destructors: ownership lives in the members, and copy/move/destroy correctness comes for free.

Track 03 — Abstractions that cost nothing

Zero-cost abstractions

C++'s promise: you can write high-level, generic, reusable code that compiles down to machine code as tight as if you'd hand-written it. Here's how templates, virtual dispatch, constexpr and the STL deliver that.

12Abstractions · key idea

You write a template

Analogy: a cookie cutter — you write one recipe with a "T"-shaped hole, and the compiler stamps out a real, specialized function or class for each type you use it with.

Templates are C++'s compile-time generics. You write code parameterized by a type (or a value) — template<class T> T max(T a, T b) — and the compiler generates a separate concrete version for each type you actually use: a max<int>, a max<double>. This is monomorphization: no runtime dispatch, no boxing, no type tags — each instantiation is exactly as fast as if you'd written it by hand for that type. Templates are the zero-cost way to write generic code, and the entire STL (vector<T>, sort, …) is built from them.

The cost moves to compile time: more work for the compiler, longer builds, and famously cryptic error messages when a type doesn't meet the template's unwritten requirements (C++20 Concepts fix that by letting you state the requirements up front). Templates also unlock compile-time techniques — type traits, tag dispatch, if constexpr, and full template metaprogramming, where the compiler computes results during compilation.

For systems work the payoff is concrete: one algorithm — a PID controller, a Kalman filter — written once and instantiated for float on a powerful CPU or fixed-point on a tiny MCU, with zero abstraction penalty either way. The thing to weigh is code bloat: every instantiation is separate machine code, which matters on tight flash budgets, so you don't template everything mindlessly.

On the vehicleOne generic filter templated on the numeric type compiles to optimal code for float on the main computer and fixed-point on a sensor's microcontroller — same source, no penalty.

13Abstractions · key idea

You call a virtual function

Analogy: a directory lookup — you say "the shape's area()", and at run time the object's own hidden directory says which real function to dial.

This is runtime polymorphism. When you call a virtual function through a base pointer or reference (Shape* s; s->area();), C++ decides which override to run based on the actual object type, at run time. The mechanism: each polymorphic object carries a hidden pointer, the vptr, to its class's vtable — an array of function pointers, one slot per virtual function. The call becomes "follow the vptr to the vtable, read the slot for area(), call that function pointer." A Circle's vtable points at Circle::area, a Square's at Square::area, so one call site dispatches correctly to each.

The cost is one extra indirection per call (a pointer chase, and the compiler usually can't inline it), plus one vptr of memory per object. Negligible in ordinary code; occasionally too much in the very hottest inner loop, where a non-inlinable call blocks other optimizations.

The systems judgment call: virtual dispatch is excellent for plugin-style designs — a common Sensor interface with many implementations the rest of the stack treats uniformly. But hard-real-time hot paths and MISRA-style rules often avoid it, preferring static polymorphism (templates, resolved at compile time, fully inlinable) or plain functions when the type is known. Knowing when the indirection earns its keep — and that dynamic_cast/RTTI add still more cost — is the skill.

14Abstractions · advanced

The compiler runs your code at compile time (constexpr)

Analogy: doing your homework the night before rather than during the exam — the answer is ready before the program ever runs.

constexpr tells the compiler "this can be computed at compile time." A constexpr variable is a true compile-time constant; a constexpr function will run during compilation when given constant inputs, baking the result into the binary as a literal — zero run-time cost. So a lookup table, a CRC table, a unit conversion, or a config value can be computed once by the compiler, and the running program simply reads the constant. C++17 hugely expanded what constexpr functions may do (loops, branches, locals — most of the language) and added if constexpr for compile-time branching inside templates.

For embedded and real-time this is a genuine lever: work done at compile time is work the device never does, and constants placed in flash cost no RAM and no cycles. It also enables compile-time correctness checks via static_assert — you catch a bad configuration at build time instead of discovering it in flight.

The habit to build is to keep asking "how much of this can I move to compile time?" Precomputed tables, buffer sizes, and math resolved before deployment give you a smaller, faster, more predictable program. (Later standards push further, with consteval for "must run at compile time" and constexpr containers.)

15Abstractions

You reach for the STL

Analogy: a professionally-stocked toolbox — battle-tested containers, algorithms, and the iterators that clip them together, so you never re-implement (or mis-implement) the basics.

The Standard Template Library gives you three cooperating pieces. Containers store data: vector (a dynamic array — your default), array (fixed size), string, plus map/unordered_map (key-value), set, deque and more, each with documented complexity guarantees. Algorithms operate on data: sort, find, transform, accumulate, count_if and dozens more — general, tested, and often faster than a hand-rolled loop. Iterators are the glue: a uniform "position in a sequence" so any algorithm works on any compatible container (sort works on a vector or an array because both expose iterators).

The working wisdom is "prefer std:: over hand-written." STL code is correct, optimized, and communicates intent — std::find_if says what you mean, where a raw loop makes the reader decode it. It's also the STL that proves the zero-cost principle: templates plus inlining make these abstractions compile to code as tight as the manual version.

Two things to get right. Pick the container by its complexity and access pattern (vector for contiguous iteration, unordered_map for O(1) lookup, and so on), and remember iterator invalidation. And for embedded, note the STL's allocation habits — vector and map allocate — so real-time code uses reserve(), fixed-capacity containers, or custom allocators to keep behavior deterministic.

On the vehicleRobotics code leans on vector for point clouds and buffers, unordered_map for lookups, and STL algorithms for transforms — with reserve() or custom allocators wherever the real-time budget forbids surprise allocations.

16Abstractions · advanced

You write a lambda (and reach for std::function)

Analogy: a sticky note with a small task on it that you can hand to someone — and, if you like, it can remember a few things from where you wrote it.

A lambda is an anonymous function you define inline: [capture](args){ body }. The capture list is the interesting part — it lets the lambda remember variables from the surrounding scope, by value ([=] or [x]) or by reference ([&] or [&x]). Under the hood the compiler turns a lambda into a small unnamed struct (a "closure") holding the captured data as members with operator() as the body — so it's a real object, usually stack-allocated, and calls into it inline beautifully at zero overhead. Lambdas are everywhere in modern C++: comparators for sort, callbacks, short local helpers.

std::function<Sig> is a different tool: a type-erased wrapper that can hold any callable matching a signature — a lambda, a function pointer, a functor. That flexibility is how you store heterogeneous callbacks in a container or a class member. The catch is that it may heap-allocate (to store a larger captured state) and always adds an indirect call, so it is not zero-cost. It's great for setup and event wiring, but you keep it off the hot path, where you prefer a template parameter or a plain function pointer.

Two hazards worth flagging. A capture-by-reference lambda that outlives the variables it captured is a dangling-reference bug — a callback firing after the referenced object has died. And std::function's possible allocation is exactly the kind of thing real-time code audits out of its control loop. Love lambdas; use std::function deliberately.

Track 04 — C++ and the machine

Performance

Fast C++ isn't about clever tricks — it's about understanding the machine underneath: caches, memory layout, and how the compiler turns your abstractions into tight code. This is where robotics and games win their speed.

17Performance · key idea

Why vector beats list (cache locality)

Analogy: groceries on one shelf you grab in a single reach (vector) versus items scattered across a warehouse you walk to one at a time (list).

Modern CPUs are far faster than RAM, so they hide the gap with caches — small, ultra-fast memories holding recently-used data. The key detail: memory is fetched in cache lines (typically 64 bytes) at a time, so touching one byte pulls its neighbors in for free. That makes data layout, not just algorithmic complexity, decide real-world speed.

std::vector stores its elements contiguously, so iterating it streams whole cache lines and the hardware prefetcher correctly predicts the next one — very few misses, very fast. std::list stores each element in a separately-allocated node scattered around the heap, so every "next" is a pointer chase to who-knows-where: a likely cache miss on every hop, and a single miss can cost hundreds of cycles.

This is why "vector is almost always faster than list," even for operations where list has the better big-O on paper — for realistic sizes the constant factor from cache misses dwarfs the theoretical advantage. The lesson generalizes: prefer contiguous, cache-friendly layouts, and don't assume a "cleverer" pointer-chasing structure wins. It's also the gateway to data-oriented design (a few cards on), where organizing data for the cache can be a 10× win on the very same algorithm.

18Performance

A vector grows past its capacity

Analogy: you keep adding books to a shelf; when it's full you buy one twice as big, move every book across, and throw out the old shelf.

std::vector tracks two numbers: size (how many elements it holds) and capacity (how many it can hold before needing more room). push_back appends in O(1) — until size hits capacity. Then it must grow: allocate a new, larger block (typically doubling capacity), move or copy every existing element into it, and free the old block. That reallocation is O(n) and hits the allocator.

Because capacity doubles, these events get rarer as the vector grows, so the average (amortized) cost of push_back stays O(1) — but any single push can be an expensive spike, and every reallocation invalidates all iterators and pointers into the vector (the invalidation trap from track 02).

When you know the count, the fix is reserve(n): it allocates capacity once, up front, so subsequent push_backs never reallocate. This is a standard performance move and — crucially — a real-time one: reserve at startup and the hot loop's appends become allocation-free and predictable. The doubling strategy is also the price the vector pays to stay contiguous and cache-friendly. So: know the size, reserve; growing unpredictably in a tight loop without it is a classic latency bug.

You return a big object by value

Analogy: instead of building a chair in the workshop and carrying it to the room, the compiler just builds it in the room to begin with — no move at all.

A common newcomer worry: "if I return a big object by value, won't it be copied?" Usually no. The compiler applies copy elision — it constructs the returned object directly in the caller's storage, skipping the copy or move entirely. The specific form for returning a local is (Named) Return Value Optimization (RVO/NRVO). And in C++17, elision for returning a temporary (a prvalue) is guaranteed by the standard — conceptually there isn't even a copy to optimize away.

Even when elision can't apply, the object is moved out of the function, not deep-copied, which for a well-written type is cheap. So the modern guidance flips old C++ folklore: return by value. It's clean, it's usually free thanks to elision, and it composes far better than "output parameters," which hide intent and invite uninitialized-use bugs.

This is a big part of why value semantics are practical for performance in modern C++: you can build and return large objects — a computed trajectory, a filled message — from factory functions without fear of copies, and the compiler makes it efficient. Understanding elision is what lets you drop the awkward out-params and simply trust return-by-value.

20Performance · advanced

Zero-overhead abstractions & data-oriented design

Analogy: a filing cabinet organized "all names together, all phone numbers together" (SoA) rather than one folder per person (AoS) — because you usually process one field across everyone.

The zero-overhead principle is C++'s core promise: you don't pay for what you don't use, and what you do use you couldn't hand-code any better. Templates, RAII and iterators compile away to nothing — the abstraction is genuinely free. But the cache scenario adds a companion truth: performance is dominated by memory layout, and that's where data-oriented design comes in.

The classic choice is Array of Structs (AoS) versus Struct of Arrays (SoA). AoS stores a vector<Particle> where each Particle keeps {x, y, z, mass, …} together — natural and object-oriented, but if a hot loop only touches x and y, every cache line you load is mostly wasted on the fields you don't need. SoA stores separate arrays — one vector<float> of all the xs, another of the ys — so a loop over positions streams tightly-packed, relevant data with no waste, and it vectorizes (SIMD) far better.

This is the mindset behind fast robotics, simulation and game engines: organize data by how it's accessed in the hot loop, not by the tidy object model, because the same algorithm can run several times faster from layout alone. In real code you keep clean object-oriented interfaces where clarity matters and switch to data-oriented layouts (SoA, contiguous pools, entity-component systems) in the performance-critical core. Zero-overhead abstractions plus cache-aware layout is how C++ gets both expressiveness and speed.

Track 05 — Many things at once, on a deadline

Concurrency & real-time

Robots and vehicles do many things simultaneously, and some of them must never be late. This track is threads and the safe sharing of data — then the real-time discipline that keeps a control loop deterministic.

21Concurrency

You spawn a std::thread

Analogy: hiring a second worker who runs off and does a job in parallel while you carry on — but now two people share one workshop, and they can collide.

std::thread launches a function to run concurrently on another OS thread, executing in parallel with the rest of your program — truly in parallel on a multicore CPU. You start it with std::thread t(func, args…). The RAII catch: before the std::thread object is destroyed you must either join() it (wait for it to finish) or detach() it, or the program calls std::terminate(). So threads are wrapped in RAII (C++20's jthread joins automatically), never left dangling.

The real difficulty isn't starting threads — it's sharing data between them. Threads share one address space, so any data touched by more than one thread is a hazard, which is what mutexes, atomics and the next several cards are all about. Hold this distinction: threads give you parallelism (do many things at once, use every core), as opposed to async concurrency (overlap waiting). C++ offers std::thread for parallelism, plus higher-level tools (std::async, thread pools).

On embedded, "threads" are your RTOS tasks with priorities; on a Linux-class robotics computer you use std::thread and often pin threads to specific cores and set real-time priority so the control thread is never preempted by background work. Spawning is easy; the engineering is all in how the threads communicate.

22Concurrency · key idea

Two threads touch the same data (races & mutexes)

Analogy: two people editing one document at once with no rule about taking turns — their edits overwrite each other and text goes missing.

When two threads access the same memory and at least one writes, without synchronization, you have a data race — and in C++ a data race is undefined behavior, not merely "sometimes wrong." Even counter++ breaks, because it's a read-modify-write (load, add, store): two threads interleave and an update is lost — the same lost-update hazard from the interrupt world, now across cores.

A std::mutex (mutual exclusion) fixes it: a thread locks the mutex before touching the shared data and unlocks after, so only one thread is in the critical section at a time. You always take the lock via RAII — std::lock_guard or std::unique_lock — so it's released on every path including exceptions; never manual lock()/unlock(). But mutexes have costs: they serialize (threads wait, so a coarse lock kills your parallelism — keep critical sections short), and multiple locks invite deadlock (A holds lock 1 waiting for 2 while B holds 2 waiting for 1). Defenses: always acquire multiple locks in a consistent order, or use std::scoped_lock (C++17) to take several at once safely.

For real-time there's a further trap: priority inversion — a high-priority thread blocked on a lock held by a low-priority one. RTOSes offer priority-inheritance mutexes, and because a mutex can make a thread wait an unbounded time, hard-real-time loops often avoid locks entirely in favor of the lock-free structures coming next. The mantra: shared mutable state is the enemy — minimize it, and protect what's left.

23Concurrency · advanced

You use std::atomic (and meet memory ordering)

Analogy: a turnstile that lets exactly one person through per push — two people can never half-enter and jam it.

For a single shared value — a flag, a counter, a pointer — a full mutex is overkill. std::atomic<T> makes operations on that value indivisible: an atomic increment or compare-and-swap happens as one uninterruptible step the hardware guarantees, so no lost updates and no torn reads, with no lock. These map to special CPU instructions. Atomics are the building block of lock-free programming — structures where threads make progress without ever blocking on a lock, so no deadlock, no priority inversion, and bounded latency, which is exactly why they're prized in real-time and low-latency code.

The deep part is memory ordering. CPUs and compilers reorder memory operations for speed, so "thread A wrote X then Y" can be seen by thread B as "Y then X." Atomics let you specify an ordering: relaxed (atomicity only), acquire/release (establish happens-before between two threads), or seq_cst — the default — a single global order that's easiest to reason about. Getting orderings right is genuinely hard, so the safe advice is: use the default seq_cst unless you've measured a need and truly understand the weaker models.

Practical guidance: reach for std::atomic for simple shared flags and counters, and to build a few carefully-reviewed lock-free structures (like the ring buffer next); use a mutex for anything involving several related variables or a complex invariant. Lock-free is powerful but easy to get subtly, catastrophically wrong, so most teams confine it to a small set of audited primitives rather than hand-rolling it everywhere.

24Concurrency · advanced

Sensor → processing over a lock-free ring buffer

Analogy: a conveyor loop between one loader and one unloader — the loader drops boxes at the head, the unloader takes from the tail, and they never need to talk.

A ring buffer (circular buffer) is a fixed-size array with two indices — head (where the producer writes) and tail (where the consumer reads) — both wrapping around modulo the size. It's the standard way to pass a stream of data between two threads: a sensor thread producing samples, a processing thread consuming them. The single-producer/single-consumer (SPSC) case is special: with exactly one writer advancing head and one reader advancing tail, and the indices published atomically, it can be lock-free — neither thread ever locks or blocks the other, so there's no mutex, no deadlock, no priority inversion, and bounded, predictable latency. Exactly what a hard-real-time system wants.

The mechanics: it's full when advancing head would collide with tail (the producer must wait or drop the sample), empty when head equals tail (the consumer waits). Because the buffer is a pre-allocated fixed array, there's no runtime allocation on the hot path — the real-time rule. And it decouples the two sides: a fast sensor and a slower consumer coexist, with the buffer absorbing bursts up to its capacity.

Getting a lock-free queue correct needs careful atomics and memory ordering (acquire/release on the indices), which is why teams reuse a small number of well-tested implementations rather than rolling their own each time; multi-producer/multi-consumer versions are much subtler. The SPSC ring buffer is the canonical "sensor → processing" hand-off across embedded and robotics.

25Real-time · the golden rule

The control loop must never miss its deadline

Analogy: a heartbeat that must never skip — being fast on average isn't enough; a single late beat is a failure, so you remove anything that could ever cause a pause.

A hard-real-time system must finish each iteration of its control loop before a deadline, every single time — a flight controller at 1 kHz has 1 ms per cycle, and missing it can flip the aircraft. What matters is worst-case latency, not average. So the rule is to purge from the hot path anything with unbounded or unpredictable timing: heap allocation (the allocator can take a variable, long time and can fragment), locks (a thread can wait an unbounded time, worsened by priority inversion), exceptions (stack unwinding isn't bounded — many RT/safety systems disable them entirely), blocking system calls, and anything that can trigger a page fault.

The positive discipline: pre-allocate all memory at startup (object pools, reserved vectors, fixed-size arrays), communicate via lock-free structures like the ring buffer, keep the loop's work bounded and its data cache-resident, and on the OS side pin the thread to a core with real-time scheduling priority so it isn't preempted. The result is a loop whose execution time is tight and deterministic.

This is precisely where C++ (and C) beat garbage-collected languages: a GC pause is exactly the unpredictable, unbounded stall that's unacceptable here, and C++ gives you the control to eliminate every such source. "Allocation-free, lock-free, exception-free hot path" is the phrase that captures real-time C++ — and it's why the sim's occasional spike, caused by allocating inside the loop, is a genuine failure, not a cosmetic one.

Track 06 — When it absolutely must not fail

Error handling & safety-critical C++

How C++ reports errors — and why the domains that put C++ in cars, aircraft and weapons deliberately use a stripped-down, analyzed, certified version of the language.

26Errors · key idea

You throw an exception

Analogy: pulling the fire alarm — everyone evacuates in an orderly way, each locking their own door on the way out (RAII), up to whoever is trained to handle the emergency.

An exception reports an error the current code can't handle to a caller up the stack that can. When you throw, normal execution stops and the runtime performs stack unwinding: it walks back up the call chain, and for every local object in every abandoned frame it runs the destructor, until it finds a matching catch. This is why RAII and exceptions are made for each other — as the stack unwinds, all your locks release, files close, and memory frees automatically, so the error path is as clean as the success path.

The model is "throw where the error is detected, catch where it can be handled" — often far apart — which keeps the happy path free of error-checking clutter. But it has costs: throwing is relatively expensive and, more importantly, non-deterministic in timing (unwinding time isn't bounded), plus a small always-on overhead for the tables that drive unwinding.

The discipline is exception safety — code that stays in a valid state if an exception passes through it. The guarantees, strongest first: no-throw (can't throw — mark it noexcept; move operations and destructors must not throw), strong (either fully succeeds or has no effect, like a transaction), and basic (no leaks, valid but possibly-changed state). RAII gives you the basic guarantee almost for free. All of which sets up the next card: because of the timing cost and the tables, many embedded and safety systems turn exceptions off entirely.

27Safety · key idea

You handle errors without exceptions (optional / expected)

Analogy: in a cockpit you don't want surprises with unpredictable timing — you want every possible outcome visible in the return value and checked on the spot.

Given the previous card, many embedded, real-time and safety-critical projects disable exceptions and RTTI (compiler flags) and forbid them in their coding standard. The reasons: unwinding time isn't bounded (bad for hard-real-time), the unwinding tables cost code space (precious on MCUs), and certification regimes distrust the non-local, hard-to-analyze control flow. Instead, errors are handled as explicit values in the return type.

The classic is a C-style error code or a status enum you must check. Modern C++ has cleaner tools: std::optional<T> expresses "a value or nothing" (a lookup that may miss, a parse that may fail — no sentinel values, no out-params), and from C++23 std::expected<T, E> expresses "the value or an error," which is the exception-free model many teams now standardize on (before C++23 they use tl::expected or Boost.Outcome). The trade-off is explicitness versus ergonomics — every failure is visible and checkable in the type, with deterministic cost, at the price of checking at each step. [[nodiscard]] helps by making the compiler warn if you ignore a returned status. RTTI (dynamic_cast, typeid) is similarly avoided because it adds runtime type metadata; designs use static polymorphism or an explicit variant/type tag instead.

The takeaway for a newcomer: "how do we report errors?" is an architectural decision in C++ that varies by domain — exceptions on the autonomy/desktop side, value-returned errors (expected/optional) in the real-time and safety-critical core. Knowing both models, and why each domain picks one, is the mark of a systems engineer.

Track 07 — What C++17 gives you

C++17 features that matter

C++17 is the version the automotive-safety world standardized on (MISRA C++:2023 targets it). These are the features that make modern C++ safer, faster and far more readable — the ones to adopt on day one.

31C++17 · key idea

You model "a value or nothing", and "one of several" (optional / variant)

Analogy: a labeled box that either holds exactly one known thing or is honestly marked "empty" — no guessing, no invalid sentinel values.

C++17 added vocabulary types for common situations. std::optional<T> holds either a value or nothing — the clean way to say "this might not have a result": a lookup that can miss, a parse that can fail, an optional config field. It replaces error-prone conventions like returning -1, a null pointer, or an out-parameter-plus-bool. You test it (if (opt)) and access with *opt.

std::variant<A, B, C> is a type-safe union — it holds exactly one of a fixed set of types and always knows which, unlike a raw C union (a classic UB footgun). It's the modern way to model "one of several alternatives," which makes it excellent for state machines (a State is a variant of Idle, Driving, Fault…) and message types; you dispatch with std::visit, and the compiler makes sure you handle each case. (std::any holds a value of any type with a runtime check — occasionally handy, rarely reached for.)

Why this matters for systems: variant-based state machines are a robust, allocation-free way to model a robot's or a protocol's states with compiler-enforced completeness; optional makes "no value" explicit and impossible to forget; and both retire the null-pointer and invalid-union bugs that plague C-style code. The newcomer takeaway: prefer these over sentinels, nulls and raw unions — they make intent explicit and let the compiler catch mistakes.

32C++17 · key idea

You read data without copying it (string_view / span)

Analogy: a bookmark pointing at a passage in a book you already own — you can read the passage without photocopying it.

A recurring performance leak is a function taking a std::string parameter and forcing a copy — pass a literal or a substring and you allocate and duplicate. C++17's std::string_view is a non-owning view: a pointer plus a length referring to an existing character sequence, owning and copying nothing. A function taking string_view accepts a std::string, a C string, or a substring with zero copies and zero allocation — ideal for parsing and read-only text, which embedded systems do constantly (protocol messages, config).

The same idea generalizes to std::span (C++20) — a non-owning view over any contiguous range (an array, a vector, a raw C buffer) — so you write one function over "a view of N contiguous Ts" that works no matter where the data lives.

The crucial caveat: a view does not own its data, so it's a dangling hazard. If the underlying string or buffer is destroyed or reallocated while a view still refers to it, that's undefined behavior. Views are for parameters and short-lived reads, never for storing. The rule to carry: views for reading, owners for keeping. This zero-copy discipline is exactly how high-performance parsers and sensor pipelines avoid needless allocation.

On the vehicleA driver parsing a binary sensor frame passes a std::span over the received buffer through its parse functions — zero copies — reading fields in place instead of duplicating the packet at every layer.

33C++17

You use if constexpr and structured bindings

Analogy: an assembly line that reconfigures itself for each product before it even starts — the wrong branches are physically removed, not just skipped.

if constexpr is a compile-time if inside templates: the branch not taken is discarded at compile time and isn't even required to compile for the current type. It replaced heaps of awkward metaprogramming (SFINAE, tag dispatch) with readable code — "if this type is integral, do X, else do Y" — resolved by the compiler, with only the chosen branch generated: zero runtime cost, no dead branches in the binary. It's a cornerstone of writing one template that adapts to many types.

Structured bindings let you unpack a pair, tuple or struct into named variables in one line: auto [x, y] = point; or for (auto& [key, value] : myMap) — instead of the clunky .first/.second and get<>. It makes iterating maps and returning multiple values readable and pleasant.

These are "quality-of-life plus performance" features. if constexpr gives cleaner, faster-compiling, zero-overhead generic code — very relevant when you template a numeric algorithm for different platforms — and structured bindings remove boilerplate wherever you handle grouped data (a function returning a result-and-status, a loop over key-value pairs). For a newcomer these are daily-use features: they don't change what's possible, but they make modern C++ dramatically more readable — which, in a large safety-critical codebase, is itself a correctness benefit, since clear code has fewer bugs and passes review faster.

34C++17

The rest of the C++17 toolbox

Analogy: a set of small, sharp upgrades to the standard toolkit — none flashy alone, but together they modernize how you write everyday C++.

C++17 shipped a broad toolbox. Parallel algorithms: most STL algorithms gained execution policies — std::sort(std::execution::par, …) tells the implementation to parallelize across cores automatically, a low-effort speedup for big data transforms (great for batch processing on a multicore robot computer, though kept off the hard-real-time path). [[nodiscard]]: an attribute that makes the compiler warn if the caller ignores the return value — invaluable for error-returning functions (a status you must not drop) and factory functions, and heavily used in safety code. std::filesystem: a portable, standard way to work with paths, files and directories — finally cross-platform file handling in the standard library, used for tooling, logging and loading maps/config.

Plus many smaller wins: inline variables (simpler header-only libraries), fold expressions (clean variadic templates), guaranteed copy elision (the RVO card), and nested namespace syntax (namespace a::b::c {}). Individually minor, collectively these mark the shift to "modern C++": safer defaults ([[nodiscard]]), more expressive generics (fold expressions, if constexpr), zero-copy (string_view), type-safe alternatives to old hazards (optional/variant over null/unions), and easy parallelism. That MISRA C++:2023 targets C++17 means this is exactly the language version the automotive-safety world has settled on.

The newcomer's practical path: you don't need every feature on day one, but adopting optional/variant/string_view/structured bindings/if constexpr/[[nodiscard]] early makes your C++ immediately more modern, safer and more readable. That's the "quickly get going" payoff — a handful of features carry most of the benefit.

Track 08 — The bigger picture

Architectures of C++ systems

Great systems aren't just fast code — they're well-organized. These are the structural patterns real robotics, aerospace and automotive teams use to keep large C++ systems modular, portable, testable and safe.

35Architecture · key idea

The layered stack (HAL → drivers → middleware → app)

Analogy: a building with floors — the penthouse (app logic) never touches the plumbing directly; it asks the floor below, which asks the floor below, down to the hardware.

Real embedded and robotics systems are built in layers, each depending only on the one beneath it. From the bottom: Hardware (CPU, sensors, motors); a HAL (Hardware Abstraction Layer) plus drivers that wrap chip-specific registers behind clean interfaces (a GpioPin, an ImuSensor); an OS/RTOS providing threads, scheduling and timers; a middleware layer for messaging and services (ROS 2/DDS or a custom bus); and at the top your application (perception, planning, control). The rule — each layer talks only to the layer below, through an interface — is what buys portability and testability.

The payoff is that you can swap the bottom without touching the top. Because the app talks to an ImuSensor interface, not to STM32 registers, you port the same autonomy code from a dev board to the real vehicle by rewriting only the HAL/driver layer — or run it in simulation by substituting a fake HAL. In C++ these interfaces are abstract base classes (virtual, for runtime substitution) or templates/concepts (for zero-cost compile-time substitution), with dependency injection wiring the concrete implementation in at startup.

It's also what makes unit testing possible: mock the layer below and test a layer in isolation. For a newcomer, "design against interfaces, not implementations; layer the system; keep dependencies pointing downward" is the habit that keeps a growing codebase maintainable — and it's why a well-built robot stack can move between hardware, run in a simulator, and be tested piece by piece.

Sim · commands travel down, sensor data travels up, one layer at a time

Follow a command down or a sensor reading up. Each layer only knows the one below it — so you can replace the hardware layer (real / bench / sim) without changing the app.

36Architecture · key idea

The pub/sub node graph (ROS 2 / DDS)

Analogy: a newsroom where reporters post stories to topics and anyone interested subscribes — nobody phones anyone directly, so you can add or remove staff without rewiring.

The dominant architecture for robots is a graph of independent nodes (processes or components) that communicate by publish/subscribe over named topics rather than calling each other directly. A camera node publishes images on an /image topic; a perception node subscribes and publishes detections on /objects; a planner subscribes to those. This is the ROS 2 model, and under the hood ROS 2 uses DDS (Data Distribution Service), an industry pub/sub middleware also used in defense and aerospace.

Why it dominates: decoupling. Nodes know only about topics and message types, not about each other — so you can add a new consumer (a logger, a second planner) without touching producers, swap a node's implementation freely, run nodes as separate processes so one crashing doesn't take down the rest (fault isolation), and distribute nodes across multiple computers transparently (the middleware handles the networking). DDS adds Quality-of-Service controls — reliability, deadlines, history depth — and can deliver deterministically, which is why it's trusted in safety and defense systems.

The C++ angle: nodes are C++ classes, messages are strongly-typed structs (defined in IDL and code-generated), and the middleware handles serialization and transport. The trade-off to know: pub/sub indirection and serialization add latency versus a direct function call, so the hard-real-time inner control loop is usually not a distributed pub/sub graph but tightly-coupled in-process code — pub/sub connects the larger subsystems while the time-critical core stays direct. This is the "bigger picture" of how robot software is organized.

Sim · nodes exchange messages on topics, not by direct calls

Messages flow along topic connections between decoupled nodes. Any node can be added, swapped, or moved to another computer without the others knowing.

37Architecture · key idea

The two-tier split: real-time control vs autonomy

Analogy: a fast, reflexive spinal cord (real-time control) beneath a slower, deliberate brain (autonomy) — the reflexes must never wait for the brain to finish thinking.

A robot has two very different kinds of work with two very different timing needs, and mature architectures split them into tiers. The autonomy tier (perception, mapping, planning, decision-making) is compute-heavy, best-effort, and runs at "think" rates (a few to tens of Hz) — it's fine for it to occasionally take longer, use lots of memory, run on a powerful multicore/GPU computer, and be written in expressive C++ (sometimes mixed with Python for research). The real-time control tier (stabilization and the actuator loop) must hit a hard deadline every cycle (hundreds of Hz to kHz), runs on a dedicated real-time computer or microcontroller under an RTOS, and is written in the conservative, allocation-free, lock-free subset from track 05.

They're deliberately decoupled: the autonomy tier sends setpoints/goals down ("drive this trajectory"), and the control tier runs its tight loop independently and publishes state back up. So if the autonomy computer stalls or crashes, the control tier keeps the platform stable and safe. This is often literally separate hardware — a "flight computer" plus a "companion computer" communicating over a link — precisely so the non-deterministic side can never block the deterministic side.

For a newcomer this is the single most important architectural idea for real vehicles: separate the deterministic real-time core from the best-effort autonomy, give each the environment it needs, and design the interface (setpoints down, state up) so a failure in the smart part degrades gracefully instead of causing a crash. It's the structural reason the whole system can be both intelligent and safe.

38Architecture · advanced

Components, state machines & the HAL

Analogy: a well-run factory — each station (component) has one job, a clear inbox/outbox, and a posted status board (state machine); you can retool one station without stopping the line.

Zooming into how the software itself is structured, a few patterns recur. The component/actor model: build the system from self-contained components, each owning its own state and data and communicating only by messages — no shared mutable state between them. This maps perfectly onto pub/sub nodes and onto concurrency: because each actor owns its data and processes messages one at a time, you sidestep the data races and lock complexity of shared-state threading. Explicit state machines: robot and protocol behavior is naturally a set of states with defined transitions (Idle → Arming → Active → Fault), and modeling that explicitly (often a std::variant of state types, or a state-machine library) makes behavior predictable, testable, and auditable — you can prove which transitions are allowed and that every state is handled, exactly what safety review wants. HAL abstraction (from the layered card): every hardware touchpoint sits behind an interface so the logic above is hardware-independent and testable.

Together these give a system that is modular (components developed and tested independently), concurrency-safe (message-passing over shared state), predictable (explicit state machines), and portable (HAL). In C++ you implement components as classes, messages as typed structs, state machines with variant/visit or a library, and interfaces as abstract classes or concepts.

The synthesis for a newcomer: good systems C++ isn't just fast code, it's this architecture — message-passing components with explicit state, layered behind hardware abstractions, split into real-time and non-real-time tiers, connected by pub/sub. Learn the language (tracks 1–7) and these patterns (track 8), and you can reason about, and build, a real robot's software — which is exactly what the UGV case study assembles next.

Case study: an unmanned ground vehicle's C++ stack

39UGV · the whole stack

The full C++ stack of a UGV

Analogy: a relay race — sensors hand data to perception, which hands a world-model to planning, which hands a path to control, which drives the wheels — with a referee (the safety monitor) who can stop the race at any instant.

Assembled bottom-to-top, and split across the two tiers from track 08: Compute & OS — typically two computers: an autonomy computer (multicore x86/ARM, often with a GPU, running Linux, frequently with the PREEMPT_RT patch) and a real-time control computer or MCU (an RTOS such as FreeRTOS/Zephyr/QNX, or bare metal). HAL & drivers (C++) talk to sensors and actuators over the buses from the embedded volume — CAN/CAN-FD to motor controllers, SPI/I²C to IMUs, Ethernet to lidar/cameras, serial to GPS — each behind a clean interface. Middleware — ROS 2 on DDS carries typed messages between subsystems and across both computers, with QoS for reliability and timing.

On top: Perception (often PCL for point clouds, OpenCV / deep-learning for vision) turns lidar/camera/radar into obstacles and detections. Localization — a SLAM / state-estimation stack (an Extended Kalman Filter or factor-graph optimizer fusing IMU + wheel odometry + GPS + lidar) answers "where am I?". Planning — a global planner finds a route on the map; a local planner produces a smooth, obstacle-avoiding trajectory in real time. Control (real-time tier) — a PID or MPC controller turns that trajectory into steering/throttle/brake commands at high rate on the RT computer, closing the loop over CAN. And an independent safety monitor / E-stop can cut motor power regardless of what the rest of the software does.

Notice how the whole guide shows up at once: RAII and smart pointers manage every resource; value semantics and move pass big messages cheaply; vectors and SoA keep perception fast; threads with lock-free ring buffers move sensor data; the control loop is allocation-/lock-/exception-free; optional/variant model states and results; the layered + pub/sub + two-tier architecture organizes it all; and the safety-critical parts follow MISRA / ISO 26262. This is C++ doing what it's uniquely good at — high-level expressiveness where you can afford it, bare-metal determinism where you can't, in one system.

40UGV · advanced

Sensor ingestion & time synchronization

Analogy: many witnesses describing a fast-moving scene — their accounts are only useful if you know exactly when each happened, so you can line them up.

Everything above perception rests on getting sensor data in, correctly timestamped, and combined. A UGV has many sensors at different rates: lidar (~10–20 Hz), cameras (~30 Hz), IMU (hundreds–thousands of Hz), GPS (~10 Hz), wheel encoders. Each has a C++ driver that reads its bus (Ethernet/CAN/SPI/serial, often with DMA so the CPU isn't copying every byte — the embedded-volume technique), parses the raw frame (using string_view/span for zero-copy), and publishes a typed message.

The critical, easy-to-underestimate problem is time synchronization. To fuse a lidar scan with a camera image and an IMU reading, you must know precisely when each was captured, on a common clock — otherwise a fast-moving vehicle fuses data from different moments and builds a wrong world model. Solutions: hardware timestamping at capture, a shared time protocol (PTP / IEEE-1588 over Ethernet, or GPS time) aligning all clocks to sub-microsecond, and buffering so consumers can pick the readings nearest a target time. This is where the lock-free ring buffers, careful threading, and pre-allocation from the concurrency track earn their keep — the pipeline must be fast, lossless under bursts, and non-blocking.

The pipeline shape is: driver (DMA read → timestamp → parse) → ring buffer → filter/sync → typed message → consumers. The lesson for a newcomer: autonomy is only as good as its data plumbing — correct timestamps, a fast non-blocking pipeline, and clean typed messages are what let perception and localization work at all. Sensor fusion is a time-alignment problem before it's an algorithm problem.

41UGV · safety

The safety architecture (E-stop, watchdog, redundancy, degraded modes)

Analogy: a car doesn't rely only on the driver being careful — it has independent brakes, seatbelts and airbags that work even if everything else fails.

A UGV can hurt people and property, so its architecture is designed around what happens when things go wrong. The key elements: an E-stop independent of the main software — often a hardware circuit and a physical/remote button that cuts motor power directly, so it works even if every computer crashes. A watchdog: a timer the control software must "pet" regularly; if the software hangs and stops petting it, the watchdog fires and forces a safe state (stop). Heartbeats between subsystems and computers, so if the autonomy computer goes silent, the control tier notices and stops rather than driving blind. Redundancy for the highest-risk functions (dual sensors, dual controllers, sometimes diverse implementations) with a voter/monitor deciding. And degraded modes: defined fallbacks — lose GPS → slow down and rely on local sensing; lose a camera → widen safety margins; lose autonomy → controlled stop — rather than a binary works/crashes.

Architecturally, the safety-critical control-and-monitor path is kept simple, deterministic and separate (its own computer/process, written to the MISRA/ISO 26262 subset, allocation-free, no exceptions) so it can be analyzed and certified, while the complex, less-trusted autonomy runs beside it and can only request, never command past, the safety limits. That's the "safety monitor" in the pipeline sim — an independent authority that constrains the smart-but-fallible part.

The key insight for a newcomer: in these systems, C++ architecture is safety architecture. The two-tier split, the independent monitor, the watchdog, redundancy and degraded modes are how a system that must be intelligent (and therefore complex and imperfect) is nonetheless made safe — by ensuring the simple, verifiable safety layer always has the final say.

Build, tooling & deployment

Analogy: the workshop around the workbench — the jigs, gauges and quality checks that turn hand-built parts into a repeatable, shippable product.

How a C++ UGV codebase is actually built, tested and shipped — the engineering around the code. Build system: CMake is the de-facto standard — it describes targets and dependencies portably and generates the real build; for robotics, ROS 2's colcon builds many packages together. Dependencies: package managers like Conan or vcpkg fetch and build third-party libraries (Eigen for linear algebra, PCL, OpenCV, a DDS) reproducibly. Cross-compilation: you develop on a powerful desktop but the target is an ARM vehicle computer or an MCU, so you cross-compile with a toolchain file (and arm-none-eabi-gcc for MCUs, from the embedded world).

Testing: unit tests (GoogleTest/Catch2) on components — made possible by the interface/HAL design — plus integration tests and simulation: you run the whole autonomy stack against a physics simulator (Gazebo or a game-engine sim) to test behavior safely before touching hardware, and hardware-in-the-loop (HIL) wires the real control computer to a simulated vehicle. CI/CD: every change runs the build, the tests, the sanitizers, and static analysis (MISRA / clang-tidy) automatically — and for safety builds this produces the traceable evidence certification needs. Deployment: the cross-compiled binaries are packaged and installed onto the vehicle computers, increasingly with secure over-the-air (OTA) updates.

The meta-point that closes the guide: production systems C++ is as much about the toolchain as the language — reproducible builds, cross-compilation, a strong test-and-simulation loop, and CI that runs analysis and sanitizers on every commit are what make a safety-critical robot codebase trustworthy and maintainable. A practical starter path: learn CMake, use a package manager, write GoogleTest unit tests, run clang-tidy and the sanitizers, and try ROS 2 with a simulator. That toolchain, plus the language (tracks 1–7) and the architecture (track 8), is the complete, real picture of how modern C++ systems are built.
