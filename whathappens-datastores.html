Store 01 — The default relational choice

PostgreSQL

The "boring, correct" default. Its whole personality — concurrency, vacuum, planning, indexing, scaling — falls out of one design decision: multi-version concurrency control. And with pgvector it doubles as a RAG store.

01Postgres · core

A row is updated (MVCC)

Why it mattersMVCC is the foundation of Postgres concurrency — and the root of vacuum, bloat, and isolation behavior.

Postgres never updates a row in place. An UPDATE writes a new version of the row — a new tuple — and marks the old one expired. This is MVCC, multi-version concurrency control. Each tuple carries xmin (the transaction that created it) and xmax (the one that superseded it), and every transaction has a snapshot deciding which versions it can see. So a reader sees a consistent snapshot without locking — readers don't block writers and writers don't block readers. A DELETE just sets xmax; the old, now-invisible versions are dead tuples that must be cleaned up later.

MVCC is why Postgres gives high read/write concurrency without read locks, and it explains a chain of behavior: isolation levels are implemented via snapshots (read-committed takes a fresh snapshot per statement, repeatable-read one per transaction); an update that changes an indexed column may touch every index; and dead tuples accumulate, so storage grows and needs vacuuming. The "update in place is free" intuition from other systems is wrong here — an update is effectively an insert-plus-tombstone, which is why high-churn tables bloat and why HOT updates (heap-only tuples, when no indexed column changes) are an important optimization.

02Postgres · core

A transaction commits (WAL & checkpoints)

Why it mattersThe WAL is how Postgres is durable and fast at once — and it powers replication and point-in-time recovery.

On COMMIT, durability comes from the WAL — the write-ahead log. Before any change touches the data files, a WAL record is written and flushed to disk (fsync) — commit returns only once the WAL is durable. The modified pages live in shared buffers and are written to the data files lazily, by the background writer and at checkpoints. A checkpoint flushes all dirty buffers and records a safe recovery point, so crash recovery only replays WAL from the last checkpoint (redo committed, roll back uncommitted) — no committed transaction lost, none half-applied.

The WAL is the elegant core: sequential log writes are cheap, so you get durability without random-write cost on commit, and the same stream is shipped to replicas (streaming replication) and archived for PITR. The knobs I care about: synchronous_commit (off trades a small loss window for throughput on non-critical writes), checkpoint tuning (too frequent = write storms; too rare = long recovery and huge WAL), and fsync — never disabled in production, that's how you lose data on a crash. It's the same principle across databases: the log is the database.

03Postgres · advanced

VACUUM runs (dead tuples, bloat, wraparound)

Why it mattersNot understanding vacuum is how Postgres silently bloats and, worst case, shuts down on transaction-ID wraparound.

Because MVCC leaves dead tuples behind, Postgres needs VACUUM. Regular (auto)vacuum marks dead-tuple space reusable within the table (it doesn't shrink the file — that's VACUUM FULL, which rewrites and locks), refreshes the visibility map and statistics, and freezes old tuples. The advanced danger is transaction-ID wraparound: XIDs are 32-bit and wrap; VACUUM must freeze old tuples before the counter laps them, or Postgres refuses writes to protect data — an emergency that has taken down major sites.

I treat vacuum as a first-class operational concern, not background magic. High-churn tables produce dead tuples faster than default autovacuum cleans them, so they bloat — heap and index bloat that slows scans and wastes storage — so I tune autovacuum per table, monitor dead-tuple counts, and watch the age of the oldest unfrozen transaction so wraparound never surprises me. The silent killer is a long-running transaction: it holds back the vacuum horizon — nothing newer than the oldest running snapshot can be cleaned — so one forgotten open transaction causes cluster-wide bloat. This is the Postgres-specific tax of MVCC.

04Postgres · core

A query is planned (the optimizer)

Why it mattersReading and shaping the plan is the core skill of database performance.

SQL is declarative — you say what, not how — so the planner decides how. It parses and rewrites, then enumerates strategies: access method per table (seq scan vs index scan vs index-only), join algorithm (nested loop / hash / merge), and join order. It estimates each plan's cost from table statistics (row counts, most-common-values, histograms gathered by ANALYZE) and picks the cheapest. EXPLAIN shows the chosen plan; EXPLAIN ANALYZE runs it and shows estimated vs actual rows — how you catch bad estimates.

Performance work is mostly reading plans and fixing why the planner chose badly: stale or missing statistics (wrong estimates → wrong plan), a missing index, a query written so an index can't be used (a function on the column, a leading wildcard), or skew. So I lean on EXPLAIN ANALYZE — a big gap between estimated and actual rows means bad stats — keep ANALYZE current, and design indexes to the query. The model I teach: the planner is a cost-based bet using statistics — keep its information accurate and it usually bets right; starve it and it guesses.

05Postgres · advanced

An index is used — including pgvector

Why it mattersIndexing is the highest-leverage performance lever — and pgvector makes Postgres a RAG store.

The default index is a B-tree — O(log n) for equality and range, and it can serve an index-only scan when all needed columns are in the index. But there's a family: GIN for multi-valued/contained data (JSONB, arrays, full-text), GiST for geometric/nearest-neighbor, BRIN for huge naturally-ordered tables, plus partial indexes (only rows matching a predicate) and expression indexes. An index isn't used if the column is hidden in a function, if the planner thinks a scan is cheaper, or if stats are stale. For AI workloads, the pgvector extension adds a vector type and ANN indexes (HNSW, IVFFlat) so Postgres does embedding similarity search — turning your existing Postgres into a vector store.

Indexes trade write cost and storage for read speed, so I index to actual query patterns, not everything — every index slows writes and must be vacuumed. The senior moves: composite indexes with the right column order (equality first, then range), covering/index-only scans for hot queries, partial indexes for skew, GIN for JSONB. And the AI point I'd make unprompted: pgvector means many RAG systems don't need a separate vector database — keeping embeddings next to relational data, with metadata filtering as a plain WHERE clause, is simpler and often enough until scale justifies a dedicated store. "Postgres until it hurts" is a defensible default.

06Postgres · advanced

Postgres scales — replication, pooling, partitioning

Why it mattersKnowing how — and how far — Postgres scales, and its ceilings, is core architecture.

The scaling tools: streaming replication ships the WAL to replicas that stay near-current, giving read replicas (offload reads; async by default, or synchronous for zero loss at a latency cost) and HA (promote a replica on failover). Logical replication replicates selected tables. For write scaling — which replicas don't help — you reach for partitioning (declarative range/list/hash) and, beyond a node, sharding (Citus or app-level). And connection scaling is its own problem: each connection is a process with real memory, so thousands crush Postgres — you put PgBouncer in front.

The framing I bring is "reads scale out easily, writes scale up and eventually shard." Read replicas are the first lever, but they're eventually consistent — replication lag means a replica can serve slightly stale data, a real read-after-write consideration. Writes bottleneck on the single primary, so I partition big tables early, use PgBouncer to keep connection counts sane (the classic incident is a serverless fleet opening thousands of connections and exhausting Postgres), and shard only when a single primary genuinely can't keep up — because sharding gives up cross-shard transactions and joins. Postgres scales remarkably far vertically before you need any of the exotic stuff.

Store 02 — Postgres, operated by AWS

RDS PostgreSQL

The same engine, with the toil handed to AWS — and a shared-responsibility line worth stating precisely. HA via Multi-AZ, recovery via PITR, and a decision tree that ends at Aurora when the single writer or coupled storage is the ceiling.

07RDS · core

You run Postgres on RDS (managed)

Why it mattersKnowing the managed/self line separates "I used a DB" from "I chose a data platform."

RDS is managed Postgres: AWS runs the same engine but takes over the undifferentiated ops — provisioning, OS and minor-version patching, automated backups, monitoring, and (with Multi-AZ) failover. You still own what needs domain knowledge: schema and index design, query tuning, instance sizing, and configuration via parameter groups — you get no shell or superuser, so settings come through parameter/option groups rather than postgresql.conf and OS access. You connect to an endpoint (a DNS name), not a host, so the underlying instance can be replaced beneath you.

The value is shifting operational toil to AWS so the team focuses on data modeling and queries — but the shared-responsibility line matters: RDS does not save you from a bad schema, an N+1 query, or a missing index, and it constrains you (no superuser, supported extensions only, config via parameter groups). So I pick RDS when I want managed Postgres with control over version and instance, and I'm explicit that "managed" means managed infrastructure, not managed performance — that's still mine. The endpoint-not-host model is also why apps must reconnect gracefully, since the instance can move.

08RDS · core

RDS Multi-AZ fails over

Why it mattersIt's the HA story you must be able to narrate — and its limits.

With Multi-AZ, RDS keeps a synchronous standby in a different Availability Zone — every commit is written to both before it's acknowledged, so the standby is an exact, current copy, but it is not readable (it's for failover, not read scaling). When the primary fails — hardware, an AZ outage, or during patching — RDS automatically fails over: promotes the standby and flips the endpoint's DNS to it, typically in about 60–120 seconds. The app sees a brief blip and reconnects to the same endpoint. The newer Multi-AZ cluster deployment adds two readable standbys and faster failover.

Multi-AZ gives durability and automatic failover with RPO near zero (synchronous), and the number to state is the RTO — roughly a minute or two of DNS-flip plus reconnect, not instant — so apps need retry logic and I design for a short blip, not zero downtime. The distinction I draw: Multi-AZ standby (synchronous, not readable, for HA) versus read replicas (asynchronous, readable, for scaling, can be cross-region) — different tools, often confused. Multi-AZ protects against instance/AZ failure within a region; cross-region DR needs read replicas or cross-region snapshots. It maps straight to the RPO/RTO framing.

09RDS · core

A backup and point-in-time restore happens

Why it mattersBackups you can't restore aren't backups — PITR is the recovery story, usually for human error.

RDS takes automated daily snapshots and continuously archives the transaction logs, retaining them for a configurable window. Together they enable point-in-time recovery: restore to any second within retention, because RDS takes the nearest snapshot and replays WAL to your chosen timestamp. Crucially, a restore creates a brand-new instance with a new endpoint — it does not overwrite the running one — so recovering from a bad migration or a bad delete means restoring to just before it, then repointing or comparing. Manual snapshots persist until deleted (unlike automated ones that age out) and can be copied cross-region for DR.

The discipline I stress is that a backup strategy is a restore strategy — I test restores, because "we have snapshots" is worthless if nobody's proven a recovery. PITR is the tool for the most common disaster — human error, a bad UPDATE without a WHERE — and restore-creates-a-new-instance shapes the runbook: you restore in parallel and cut over, never in place. For DR I copy snapshots (or run read replicas) cross-region and set retention and RTO/RPO deliberately. And backups are not a substitute for Multi-AZ — one is recovery, the other is availability.

10RDS · advanced

RDS hits its ceiling (scaling & Aurora)

Why it mattersKnowing when to scale up, add replicas, add a proxy, or move to Aurora is a real architecture decision.

RDS scaling levers: vertically, change the instance class (a brief failover on Multi-AZ); storage can autoscale and you provision IOPS (or use gp3) for throughput. Horizontally for reads, add read replicas (async, readable, cross-region possible). For connections, RDS Proxy pools and multiplexes — vital for Lambda/serverless fleets that would exhaust Postgres. But single-primary write throughput and the coupling of compute and storage are the ceilings — which is where Aurora Postgres comes in: it re-architects storage as a distributed, auto-scaling layer shared across instances, giving faster failover, up to 15 low-lag read replicas, and auto-growing storage, at higher cost and with some behavioral differences.

My decision tree: start on RDS Postgres (simplest, standard Postgres); scale the instance up and add read replicas as load grows; put RDS Proxy in front if connection count is the problem (the serverless classic); move to Aurora when you need its decoupled-storage benefits — very fast failover, many low-lag replicas, or effortless storage scaling — and can accept the cost and lock-in. When even a single writer isn't enough, that's genuine sharding or a different data model, not a bigger box. What I won't do is reach for Aurora reflexively; RDS Postgres carries most workloads, and "boring Postgres" is usually the right answer.

Store 03 — In-memory, atomic, fast

Redis

An in-memory data-structure server whose whole character comes from two facts: everything is in RAM, and commands run single-threaded and atomic. That makes it a superb cache, lock, counter, queue — and an LLM semantic cache — with durability and scale as deliberate choices.

11Redis · core

A GET/SET hits Redis

Why it mattersUnderstanding why Redis is fast — and single-threaded — explains everything else about it.

Redis is an in-memory data-structure store: all data lives in RAM, so operations are microsecond-fast and mostly O(1). It's (mostly) single-threaded for command execution — one command at a time on one core via an event loop — which sounds limiting but is a feature: no locks, no races between commands, each command atomic. Clients speak a simple protocol (RESP), and values aren't just strings — they're rich structures (strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog) with server-side operations.

"In memory and single-threaded" drives every consequence. Fast because RAM plus no lock contention; atomic per command, so it's a great coordination primitive; but one slow command blocks everyone — a KEYS * or a big sort on a huge collection stalls the whole server, so you never run O(n) commands on large keys in production. Capacity is your RAM, and data is volatile unless you configure persistence. The model I give: Redis is a networked, atomic data-structure server, not "a faster cache" — its value is doing real work (counters, leaderboards, rate limits, queues) server-side at memory speed.

12Redis · core

Redis persists — or loses — data

Why it mattersTreating Redis as durable when it isn't is how you lose data; knowing the modes is the architect's call.

Redis is memory-first but can persist two ways. RDB takes point-in-time snapshots (a fork dumps every N minutes / M changes) — fast to load, compact, but you lose everything since the last snapshot on a crash. AOF (append-only file) logs every write command and replays it on restart; with fsync-every-second (common) you lose at most ~1 second, or fsync-every-write for max durability at a throughput cost. You can run both. On restart Redis rebuilds from RDB and/or AOF — for a large dataset a noticeable cold start.

The decision is durability vs performance vs restart time, and it starts with a blunt question: is Redis a cache or a store of record? If it's a cache, I can even run with no persistence — losing it means a cold cache and thundering-herd risk (the stampede scenario), not a data-loss incident. If it holds data I can't lose, I use AOF (everysec at least) plus replicas, and I'm honest that Redis is not Postgres-grade durable — RDB can lose minutes, everysec-AOF a second, and a crash mid-fsync is still a window. So for money/billing I don't make Redis the source of truth; I make it the fast layer in front of one.

memory-firstRDB snapshots (lose since last)AOF (per-command, fsync everysec/always)restart rebuild (cold start)durability vs performancecache vs store-of-recordnot Postgres-grade durable
13Redis · advanced

Redis fills up — eviction & expiry

Why it mattersMemory limits and eviction policy are where Redis surprises people in production.

Redis is bounded by RAM, and you set maxmemory. When it's reached, behavior depends on the eviction policy: noeviction (reject writes with an error — safe for a store, but can wedge an app assuming writes succeed), or an LRU/LFU/random/TTL-based policy that evicts keys to make room (allkeys-lru evicts any key; volatile-lru only keys with a TTL). Expiry is separate: TTL'd keys are removed lazily (on access) and by a background sampler (active expiry), so an expired key can briefly still occupy memory. Redis can also free memory asynchronously (lazy-free) so deleting a huge key doesn't block the single thread.

The policy encodes intent. For a pure cache, allkeys-lru/lfu is right — Redis self-manages, evicting cold data. For a store where every key matters, noeviction plus capacity planning is right — but then running out of memory is an outage, so I alert well before maxmemory. The traps I flag: mixing cache and durable data in one instance (eviction can silently drop the durable keys), the big-key problem (one enormous key dominating memory and blocking on delete), and forgetting TTL'd keys aren't instantly gone. Memory management isn't automatic peace of mind — it's a policy I choose to match whether this instance is a cache or a store.

14Redis · advanced

You use Redis as more than a cache

Why it mattersRedis's real power — and its footguns — show when it's a lock, a queue, a rate limiter, or an LLM cache.

Beyond GET/SET caching, Redis's structures and atomicity make it a coordination layer. Counters and rate limiters via atomic INCR with expiry. Leaderboards and time-ordered feeds via sorted sets. Queues and Streams with consumer groups (a lightweight Kafka-like). Distributed locks via SET-if-not-exists with a TTL — though correct distributed locking is famously subtle (the Redlock debate: a single-node lock can be lost on failover, and even Redlock has contested edges, so correctness-critical locks add fencing tokens or use a consensus store). Pub/sub for fan-out. And for AI platforms: an LLM semantic cache (cache by embedding similarity to cut cost and latency) and Redis's vector-search as a lightweight vector store.

I reach for Redis when I need shared, atomic, low-latency state across instances — its atomic commands let many app servers coordinate without their own locking. But I'm precise about guarantees: a Redis lock is a performance optimization or best-effort mutex, not a correctness guarantee across failover, so for "must never double-charge" I don't rely on it alone. And I keep responsibilities separate — a cache instance shouldn't also be my only copy of a queue. The AI angle I'd raise unprompted: an LLM semantic cache in Redis is one of the highest-ROI cost levers on a GenAI platform, tying straight back to the gateway's caching story.

15Redis · advanced

Redis scales — replication, Sentinel, Cluster

Why it mattersSingle-node Redis has hard limits; HA and sharding — and the hot-key problem — are the scaling story.

A single node is limited by one machine's RAM and one core's throughput. Replication gives replicas that copy the primary asynchronously — for read scaling and as failover candidates (async means a failover can lose the last writes). For automatic HA, Sentinel monitors the primary and promotes a replica on failure. For horizontal scale, Redis Cluster shards data across nodes using 16384 hash slots (each key hashes to a slot, slots distributed across primaries with replicas); the client is redirected to the node owning a key's slot, and resharding moves slots. The catch: multi-key ops and transactions must stay within one slot (hash tags co-locate related keys).

I scale in that order — single node (astonishingly capable, so don't shard prematurely), then replicas + Sentinel for HA, then Cluster only when one node's RAM or throughput is genuinely the wall. The costs I name: async replication means Redis HA can lose recent writes on failover (again, not for can't-lose data without care); Cluster constrains you to single-slot multi-key ops (so model data to co-locate related keys via hash tags); and single-threaded execution means a hot key on one shard can bottleneck the whole cluster — you can't spread a single hot key by adding capacity, only by design. So capacity planning is about RAM, hot-key distribution, and command cost, not just total ops.

Store 04 — Object storage & the data lake

Amazon S3

Not a filesystem — a flat, immutable, eleven-nines object store that is the gravity well of every analytics and ML platform. Throughput scales per prefix, cost is a tiering decision, and misconfigured access is a headline breach.

16S3 · core

An object is PUT and GET

Why it mattersObject storage is a different model from a filesystem — getting that right underlies everything.

S3 is object storage, not a filesystem. You PUT an object (bytes plus metadata) into a bucket under a key, and GET it by that key over an HTTP API. There are no real directories — the namespace is flat, and "folders" are just key prefixes. Objects are immutable: you overwrite the whole object, you don't edit in place, and rename is copy-then-delete. S3's headline guarantees: eleven nines of durability (99.999999999%), achieved by redundantly storing each object across multiple devices in multiple AZs; and, since 2020, strong read-after-write consistency — after a successful PUT, a GET immediately returns the new data. Objects can be up to 5 TB, and you can range-GET part of one.

The model shift I emphasize is "objects, not files" — no in-place edits, no cheap rename, a flat keyspace, access over HTTP with rich metadata — which is why S3 is for whole-blob workloads (media, backups, logs, data-lake files, ML datasets and model artifacts) rather than a mutable database or a POSIX filesystem. Eleven-nines durability means I treat the object as effectively unloseable (though I still use versioning and replication against accidental deletes and regional loss), and strong consistency removed a whole class of "I wrote it but can't read it yet" workarounds. It's the cheapest, most durable place to put bytes at any scale.

17S3 · advanced

S3 scales for throughput (prefixes & multipart)

Why it mattersS3 scales massively but not magically — request-rate and large-object mechanics matter at scale.

S3 scales request throughput per prefix: it supports very high rates (thousands of requests/second per prefix) and auto-partitions the keyspace, so spreading keys across many prefixes gives near-unlimited aggregate throughput, while hammering one prefix can throttle. For large objects, multipart upload splits a big file into parts uploaded in parallel and retried independently (and it's required past 5 GB); parts are assembled server-side. Downloads parallelize with byte-range GETs. Transfer Acceleration or CloudFront front S3 for global/edge delivery.

The counterintuitive bit is that S3's scaling is per-prefix, so key design is a performance decision — for write-heavy workloads I spread keys across prefixes (S3 auto-partitions now, so the old random-hash-prefix trick is unnecessary, but a single hot prefix can still throttle briefly). For big files — data-lake objects, ML datasets, model checkpoints — multipart upload and range reads are how you get throughput and resilience (a failed part retries, not the whole upload). For read-heavy public content I put CloudFront in front so S3 isn't serving every request. "S3 is infinitely scalable" is true in aggregate, but you design keys and use multipart to actually get there.

18S3 · advanced

Storage classes & lifecycle (cost)

Why it mattersStorage-class and lifecycle strategy is one of the biggest cloud-cost levers — and a real architecture design.

S3 has tiers trading retrieval speed/cost for storage price: Standard (hot, instant, priciest storage), Standard-IA / One-Zone-IA (infrequent access — cheaper storage, retrieval fee, still instant), Glacier Instant Retrieval (archive, instant), and Glacier Flexible / Deep Archive (cheapest storage, retrieval in minutes to hours). Intelligent-Tiering auto-moves objects between access tiers by usage for a small monitoring fee. Lifecycle policies automate transitions ("IA after 30 days, Glacier after 90, delete after 365") and expiration by age or tag.

Cost optimization here is a design decision up front, not a cleanup afterthought — match the storage class to the access pattern and let lifecycle policies enforce it automatically. Hot data on Standard; aging data on IA; cold compliance/backup on Glacier; unknown/variable patterns on Intelligent-Tiering. The retrieval-cost trap is what to watch: IA and Glacier are cheap to store but you pay (and wait) to read, so they're wrong for frequently-accessed data. This is exactly the storage-tiering TCO design I've done — tiering observability/log data across classes to cut spend — where the levers are class + lifecycle + retrieval-pattern awareness, and at petabyte scale the savings are enormous.

19S3 · advanced

S3 as a data lake and event source

Why it mattersS3 is the backbone of analytics and ML data platforms — and it reacts to changes.

S3 is the de-facto data lake: you land raw and processed data as objects (often Parquet/ORC), partition by prefix (date, tenant), and query it in place with Athena, Redshift Spectrum, or Spark — storage decoupled from compute. It emits event notifications on object create/delete that fire Lambda, SQS, SNS, or EventBridge — so an upload can trigger a pipeline (the classic "file lands → Lambda transforms it"). Versioning keeps every version (protecting against overwrite/delete, enabling rollback), and cross-region replication copies objects for DR or locality. For ML/AI, S3 is where training datasets, feature files, embedding dumps, and model artifacts live.

The pattern I lean on is S3 as the durable, cheap, decoupled storage layer under analytics and ML — compute (Athena, Spark, SageMaker) reads from and writes to S3 without owning the data, so you scale or swap compute freely and many systems share one source of truth. Event notifications make it reactive — the trigger for event-driven ETL, and it ties to the RAG ingestion pipeline: docs land in S3, an event kicks off chunk-embed-index. I design with partitioning for query cost (Athena charges by data scanned, so partition + columnar formats matter), versioning for safety, replication for DR. S3 is less "a service" than the gravity well the rest of the data platform orbits.

20S3 · advanced

S3 security & access

Why it mattersS3 misconfiguration is a top cause of public data breaches — access design is non-negotiable.

Access is deny-by-default and layered: IAM policies (what a principal can do), bucket policies (resource-side rules, cross-account, conditions), and — as a strong backstop — Block Public Access, which overrides permissive policies to prevent accidental exposure. Data is encrypted at rest (SSE-S3, or SSE-KMS for customer-managed keys and audit) and in transit (TLS). For controlled, time-limited access without credentials, you issue presigned URLs — a signed link granting GET or PUT to one object for a set window. VPC endpoints keep S3 traffic off the public internet.

The failure I design against is the infamous "public S3 bucket leaked millions of records," so Block Public Access is on by default and any public bucket is an explicit, reviewed exception. The principles: least-privilege IAM, bucket policies for cross-account/condition-based access, SSE-KMS when I need key control and an audit trail (and to enforce encryption via policy), and presigned URLs so clients hit S3 directly without me proxying bytes or sharing keys — great for upload/download at scale, and it dovetails with the gateway/virtual-key mindset. Encryption in transit and at rest is table stakes. For a regulated domain, this access model — plus versioning and access logging — is a compliance requirement, not a nice-to-have.

Store 05 — Serverless NoSQL at any scale

DynamoDB

A distributed hash table with ranges, dressed as a database. Single-digit-millisecond at any scale — if you model backwards from access patterns and design the partition key for even distribution. Fight it with relational habits and it punishes you.

21DynamoDB · core

An item is written and read

Why it mattersThe partition-key model is the whole basis of DynamoDB's scale and its constraints.

DynamoDB is a managed, serverless NoSQL key-value/document store built for predictable single-digit-millisecond latency at any scale. Every item lives in a table and is located by its primary key: either just a partition key, or a composite of partition key + sort key. DynamoDB hashes the partition key to decide which physical partition stores the item, so a read/write by key goes straight to one partition — no scan. The sort key lets many items share a partition key and be range-queried (all orders for a customer, by date). You provision throughput as on-demand (pay per request, auto-scales) or provisioned capacity (set read/write units, optionally auto-scaled).

The model I insist on is "a distributed hash table with ranges, not a relational database." Because everything hangs off the partition key's hash, DynamoDB scales horizontally almost without limit and stays fast — but only if you access by key. No joins, no ad-hoc queries; querying by a non-key attribute means a Scan (read everything, expensive) unless you built an index. So the power and the constraint are the same fact: design around keys and access patterns and you get effortless scale; fight it with relational habits and you get slow, costly Scans. That's why DynamoDB modeling is access-pattern-first, not entity-first.

22DynamoDB · advanced

You model for access patterns (single-table design)

Why it mattersDynamoDB rewards modeling backwards from queries — the opposite of relational normalization.

In relational you model entities and normalize, then query however you like. In DynamoDB you invert it: enumerate your access patterns first, then design keys so each pattern is a direct key lookup or a sort-key range query. This leads to single-table design — multiple entity types (customers, orders, items) in one table with generic composite keys (like PK=CUSTOMER#123, SK=ORDER#2026-…) and overloaded indexes, so one query returns a customer and their orders together (emulating a join by co-location). You denormalize deliberately — duplicating data so each read is single-shot — because storage is cheap and extra reads are not.

This is the hardest shift for relational people and the thing that separates someone who's run DynamoDB from someone who's read about it. The rule: know all your access patterns before you create the table, because the key schema encodes them and changing it later is painful. Single-table design trades modeling simplicity for query performance and cost (one request, not many); denormalization trades write complexity (keeping duplicates in sync, often via Streams) for read speed. I'm honest about the flip side too: if access patterns are unknown, ad-hoc, or analytics-heavy, DynamoDB is the wrong tool — that's where Postgres wins. DynamoDB is for known, high-scale access patterns.

23DynamoDB · advanced

A hot partition throttles

Why it mattersHot partitions are the classic DynamoDB production incident — and the model explains exactly why.

Throughput is distributed across partitions, so it's effectively per-partition. If access concentrates on one partition key — a celebrity user, today's date as a key, one popular product — that partition takes disproportionate traffic and can exceed its share and throttle, even while the table's total capacity looks fine. DynamoDB's adaptive capacity mitigates by shifting capacity toward hot partitions and can isolate a very hot key, but it's not a cure for a fundamentally skewed key. The fix is in the data model: write sharding (append a suffix to spread a hot key across N partitions), a higher-cardinality partition key, or distributing the load (don't key by raw date).

The lesson I state is "your partition key is your scalability, so a low-cardinality or skewed key is a scaling bug baked into the schema." I design keys for even distribution from the start — high cardinality, no single value attracting a large fraction of traffic — because you can't fully fix a hot partition at runtime, only in the model (and write-sharding after the fact is painful). It's the DynamoDB face of the same hot-key problem as Redis: a single hot key can't be spread by adding capacity, only by design. So partition-key design is a capacity-planning decision, not an afterthought.

24DynamoDB · advanced

Query vs Scan, GSI vs LSI

Why it mattersChoosing the right access construct is the difference between fast and cripplingly expensive.

A Query fetches items by partition key (and optional sort-key condition) — efficient, reads only matches. A Scan reads the entire table and filters after — expensive and slow, a red flag in production. To query by non-key attributes you add secondary indexes. A GSI (Global Secondary Index) has its own partition/sort key and its own throughput and is maintained asynchronously (so it's eventually consistent with the base table) — effectively another access pattern, another "table" DynamoDB keeps in sync. An LSI (Local Secondary Index) shares the base partition key with an alternate sort key, must be defined at table creation, and can be strongly consistent. Indexes can project a subset of attributes to save space/cost.

The rule I enforce is "Query, never Scan, in the hot path" — a Scan in production is almost always a modeling miss, and the fix is a GSI that turns the needed pattern into a Query. I reach for GSIs to add access patterns after the fact (flexible — own keys, own capacity, added anytime), accepting their eventual consistency and extra write cost (every base write updates the index). LSIs I use rarely (creation-time only, share the partition key). And I project only needed attributes to keep index cost down. The senior signal is treating Scan as an alarm, knowing a GSI is usually the answer, and knowing indexes aren't free — they're duplicated writes and storage.

25DynamoDB · advanced

Consistency, transactions & TTL

Why it mattersThe consistency and transaction model determines what's safe to build on DynamoDB.

Reads default to eventually consistent (a read might not see a just-completed write for a fraction of a second, since it may hit a replica) — cheaper, lower-latency; you can request strongly consistent reads on the base table (latest write) at double the read cost. Single-item writes are atomic. For multi-item atomicity, DynamoDB Transactions (TransactWriteItems) give all-or-nothing across a bounded set of items, with conditions — for "debit A and credit B together." Conditional writes (write only if a condition holds) give optimistic concurrency without a transaction. TTL sets a per-item expiry timestamp and DynamoDB deletes expired items automatically, for free and asynchronously — great for session/chat/cache-like data.

I match the consistency choice to the operation — eventually consistent for the vast majority (cheaper, faster), strongly consistent only where a stale read is actually harmful. For correctness across items I use transactions or conditional writes deliberately (they cost more and have limits, so reserve them for genuine invariants — not double-applying a payment, my billing world). TTL I use as a feature: the clean way to expire agent/chat session state at scale without a cleanup job — which is exactly why DynamoDB is a common backing store for LLM conversation history and agent memory (keyed by session, TTL'd, single-digit-ms). Knowing these primitives is what lets you build safely on an eventually-consistent store.

26DynamoDB · advanced

Streams & global tables

Why it mattersChange-data-capture and multi-region are the advanced patterns that make DynamoDB a platform.

DynamoDB Streams is a change log: every item-level change (insert/modify/remove) is captured in order per partition key, available ~24 hours, and typically consumed by Lambda. That's the CDC primitive — powering derived views, syncing to another store (a search index, analytics, a cache), maintaining denormalized copies, or triggering event-driven workflows on data change. Global Tables build on Streams to give multi-region active-active replication: write in any region and DynamoDB asynchronously replicates to the others, with last-writer-wins conflict resolution — so users worldwide get local low-latency reads and writes, and you get regional DR.

Streams turns DynamoDB from a store into an event source — the same pattern as S3 notifications or Kafka, at the row level — so I use it for CDC: propagate changes to a search index, keep denormalized single-table copies consistent, fan out downstream, all without app-level dual-writes (which risk inconsistency). Global Tables give genuine multi-region active-active with the honest caveat of eventual consistency and last-writer-wins (which can silently drop a concurrent update). This ties to the active-active multi-region strategy I've worked on — Global Tables are one of the cleanest ways to get it, precisely because the conflict model is simple and replication is built in — but I keep strongly-consistent, conflict-sensitive operations region-pinned.

Store 06 — Memory-first document DB

Couchbase

Cache, key-value store, and document database in one, sharded across 1024 vBuckets and scaled per-service. Fast because memory-first — which makes durability a knob you must set deliberately — with XDCR for active-active across regions.

27Couchbase · core

A document is stored and fetched (KV)

Why it mattersCouchbase's memory-first, KV-at-the-core architecture explains its speed and its trade-offs.

Couchbase is a distributed document database (JSON) with a built-in, memory-first architecture: a managed cache (a Memcached-derived layer) sits in front of storage, so hot data is served from RAM at sub-millisecond latency and writes land in memory first. Data is organized into buckets, and within them scopes and collections (roughly databases/schemas/tables). Every document has a key; Couchbase maps that key to one of 1024 vBuckets (its sharding unit), and vBuckets are distributed across nodes — so a KV GET/SET goes directly to the node owning that vBucket. Sub-document operations read/modify parts of a document without fetching the whole thing.

The framing I use is "Couchbase is a KV store and a managed cache and a document DB in one" — the integrated cache is why it's fast and why teams pick it over bolting Redis in front of a separate database (fewer moving parts, no cache-invalidation dance). The vBucket model is the key to its distribution: 1024 fixed vBuckets hashed from the key and remapped to nodes as the cluster changes, which makes rebalancing clean. In my telecom/billing context Couchbase is used exactly this way — a fast, distributed operational store where the KV path is the hot path. The mental model: fast because memory-first, scalable because vBucket-sharded, flexible because documents.

28Couchbase · advanced

Couchbase scales and rebalances

Why it mattersThe vBucket + services model is how Couchbase scales elastically — a real distributed-systems story.

You scale by adding nodes and rebalancing: because data is in 1024 vBuckets, rebalance redistributes vBuckets (and their replicas) across the new node set, moving the minimum data and updating the cluster map clients use to route keys — done online. A distinctive feature is Multi-Dimensional Scaling (MDS): Couchbase's services — Data (KV), Index, Query (SQL++), Search, Analytics, Eventing — can run on separate nodes, so you scale each independently (more Query nodes for query load without touching Data nodes). Each vBucket has configurable replicas on other nodes, and on failure auto-failover promotes a replica vBucket to active so the cluster keeps serving.

MDS is the architecturally interesting part — isolating and scaling services independently means a heavy analytical query workload doesn't starve the low-latency KV path, and you right-size each service to its load. Rebalancing as an online vBucket redistribution is what makes elastic scaling and node replacement smooth. Things I plan for: rebalance moves data and consumes resources (schedule it), replica count sets failure tolerance (and costs RAM/disk), and auto-failover has a threshold to avoid flapping on transient blips — the same node-failure-detection tradeoff as Kubernetes eviction timeouts. It's a genuinely elastic distributed system, and MDS is its differentiator versus one-size-fits-all nodes.

29Couchbase · advanced

You query with N1QL / SQL++

Why it mattersCouchbase's SQL-for-JSON is its bridge between NoSQL flexibility and familiar querying.

Beyond key-value access, Couchbase offers N1QL (now SQL++) — a SQL dialect over JSON: SELECT/JOIN/WHERE/aggregate against collections, including nesting/unnesting arrays. Queries run on the Query service, which uses Global Secondary Indexes (maintained by the Index service) to avoid scanning every document — so, like any database, an N1QL query is only fast if a suitable GSI covers its predicates. There's also a Search service (full-text) and an Analytics service (ad-hoc analytical queries over operational data without impacting it). So Couchbase gives you the KV fast path and a SQL query path over the same documents.

The design choice I articulate is when to use KV vs N1QL: if you know the key, a direct KV GET is the fastest, cheapest path — always prefer it for hot, known-key operations; use N1QL when you need to query by attributes or join, and then index for those queries the same way you would in Postgres (a query without a covering GSI is a slow scan). The MDS point returns — put Query and Index on their own nodes so query load doesn't hurt the KV latency operational traffic depends on. So Couchbase lets one system serve both the low-latency operational path and richer queries, but I'm deliberate: KV for hot keys, indexed N1QL for query patterns, Analytics for ad-hoc — matching the access path to the need, not defaulting to SQL because it's familiar.

30Couchbase · advanced

Durability & persistence in Couchbase

Why it mattersMemory-first means durability is a deliberate choice — critical for money/billing data.

Because Couchbase is memory-first, a write by default is acknowledged once it's in the active node's memory, and it's persisted to disk and copied to replicas asynchronously afterward. That's fast, but a naive write could be lost if that node crashes before persistence/replication. Couchbase addresses this with durability requirements set per write: levels like majority (ack only after the write is in memory on a majority of replica nodes), and persistToActive / majorityAndPersist (also require it on disk) — so you trade latency for stronger guarantees per operation. Replicas provide redundancy and failover targets; async persistence uses a write queue to disk.

The crucial point is that Couchbase's default — ack-on-memory — is a performance choice, not a durability guarantee, so for data I can't lose (billing, payments) I explicitly set a durability level (majority, or persist-to-disk) and accept the added latency, matching the guarantee to the value of the data. It's the same RPO conversation as everywhere: how much am I willing to lose, and what latency will I pay to lose less? I flag this as a common footgun — teams enjoy the default speed and are surprised by loss on a node crash — so I make durability level an explicit, per-use-case decision: strong for financial writes, relaxed for tolerant data. Memory-first is a feature with a knob, and knowing the knob is the seniority signal.

31Couchbase · advanced

XDCR & cross-datacenter (multi-region)

Why it mattersXDCR is how Couchbase does multi-region / active-active — a real resilience design.

XDCR — Cross Data Center Replication — asynchronously replicates data between separate Couchbase clusters, typically in different regions. It's flexible: unidirectional (to a DR site) or bidirectional / active-active (both clusters take writes and replicate to each other), at bucket/collection granularity, with optional filtering. Because it's async between independent clusters, replicas across sites are eventually consistent, and active-active means concurrent writes to the same document in two clusters can conflict — resolved by a policy (revision/sequence-based, or timestamp/last-writer-wins). This gives geo-distributed low latency (users hit the nearest cluster) and DR (a whole region can fail and another serves).

XDCR is Couchbase's answer to the active-active multi-region problem I've designed for — write locally in each region, replicate cross-region asynchronously, tolerate eventual consistency, handle conflicts by policy. The honest tradeoffs are the standard multi-region ones: cross-region latency makes synchronous impossible, so you accept an RPO window (replication lag = potential loss on a regional failure) and must design for conflicts (LWW can silently drop a concurrent update, so conflict-prone data needs care or single-region ownership per key). I use it for geo-locality and DR where the data model tolerates eventual consistency, and keep strongly-consistent, conflict-sensitive operations region-pinned. It's the same CAP tradeoff as DynamoDB Global Tables — active-active buys availability and locality at the cost of strong consistency, and the architecture job is deciding which data can live with that.
