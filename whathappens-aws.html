Service 01 — Managed Kubernetes

Amazon EKS

Upstream Kubernetes with the control plane operated by AWS. The interesting parts are where Kubernetes meets AWS: pods getting real VPC IPs, assuming IAM roles, and turning Services into ELBs.

01EKS · core

You create an EKS cluster

Why it mattersThe control-plane / data-plane split is the foundation of everything EKS.

Analogy You rent the engine room of a ship fully crewed and maintained (the control plane AWS runs), but you still bring and steer your own cargo — the containers on deck (your nodes) are yours to load, balance, and keep afloat.

When you create an EKS cluster, AWS stands up and fully manages the Kubernetes control plane — API server, etcd, scheduler, controller-manager — running redundantly across multiple Availability Zones, patched and scaled by AWS, exposed to you as a single managed API endpoint. You never see or SSH those nodes. What you bring is the data plane: the worker nodes that run your pods — EC2 via managed node groups, self-managed nodes, or serverless Fargate. So EKS is "managed control plane, your data plane," and you pay a per-cluster hourly fee plus the cost of your nodes.

Two details seniors add: the control plane runs in an AWS-owned account and reaches into your VPC through cross-account ENIs, and its API endpoint has an access mode you choose — public, public+private, or private-only — which is a real security lever (a private-only endpoint keeps kubectl traffic off the internet). The newer EKS Auto Mode blurs the old line by letting AWS manage nodes, scaling, and core add-ons too — closer to ‘managed data plane’ for teams who don’t want to run Karpenter and the CNI themselves.

The split is the whole point: AWS takes the operationally hardest, most failure-sensitive part — a highly-available etcd and API server — off your plate, while you keep control of the compute where workloads run. Control-plane HA is AWS's problem (multi-AZ, no single point of failure); node capacity, autoscaling, patching, and networking are yours. It's the same "managed infra, not managed workload" line as RDS: EKS gives you conformant upstream Kubernetes with the control plane handled, but your cluster's reliability still depends on how you run the data plane. And because it's real Kubernetes, everything from the platform volumes — kubectl apply, the scheduler, controllers — applies unchanged.

Check yourself Someone wants kubectl to never traverse the public internet and the API server unreachable from outside the VPC — what EKS setting delivers that, and what’s the operational catch? Set the cluster endpoint access to private-only (disable public access); the API endpoint then resolves to a private IP reachable only from the VPC/peered networks. The catch: your CI, bastions, and admins must now reach it over VPN/Direct Connect/peering or a jump host, so you need that connectivity in place or you lock yourself out.

02EKS · core

A worker node joins the cluster

Why it mattersHow nodes are provisioned, authorized, and scaled is core EKS operations — and a classic lockout gotcha.

Analogy A new employee can’t just walk in: they need the right uniform and onboarding script (AMI + bootstrap), a company badge (the node IAM role), and their name on the door list (access entry) — miss the list and they’re in the lobby forever.

A node needs three things to join: the right AMI and bootstrap (the EKS-optimized AMI runs a script pointing the kubelet at the cluster endpoint and CA), an IAM role (the node instance role, to register and pull images), and authorization in the cluster — historically the aws-auth ConfigMap mapping the node's IAM role to a Kubernetes identity, now the newer EKS access entries API. Managed node groups automate all this (AWS provisions, bootstraps, and rolls/patches them); self-managed you wire yourself; Fargate runs pods with no nodes at all. For scaling, Cluster Autoscaler or Karpenter add and remove nodes as pods need capacity.

The hardening detail I’d add is IMDSv2 and the hop limit: set the instance metadata hop limit to 1 so ordinary (non-host-network) pods can’t reach the node’s metadata endpoint and steal the node instance-role credentials via SSRF — which is also why you push app permissions to IRSA/Pod Identity, not the node role. And the bootstrap itself has modernised: AL2023 nodes use nodeadm driven by a config object rather than the old AL2 bootstrap.sh arguments.

The join flow is where AWS meets Kubernetes — IAM (the node identity and the aws-auth/access-entry mapping, the classic "my nodes won't join" or "I locked myself out of the cluster" gotcha) and autoscaling. I default to managed node groups for the automation (rolling updates that respect PodDisruptionBudgets), and reach for Karpenter when I want fast, right-sized provisioning — it picks instance types to fit pending pods rather than scaling fixed groups. Fargate when I want zero node management and per-pod isolation, accepting its constraints. The access-entry/aws-auth mapping is the thing I treat carefully, because a bad edit there can lock everyone out of the cluster.

Check yourself Why do EKS hardening guides tell you to set the EC2 metadata (IMDS) hop limit to 1 on worker nodes? A hop limit of 1 means a packet to the metadata endpoint from inside a container (an extra network hop) exceeds its TTL and fails, so pods can’t reach IMDS and assume the broad node instance role — closing an SSRF/credential-theft path and forcing per-pod permissions through IRSA/Pod Identity instead.

03EKS · advanced

A pod gets an IP (the VPC CNI)

Why it mattersEKS's networking model is unique, and its IP-density limits bite in production.

Analogy Every pod gets a real apartment with its own street address drawn from the building’s block of numbers — wonderful until the block runs out and new tenants (pods) are left standing on the pavement marked Pending.

EKS's default networking is the AWS VPC CNI, and it's distinctive: every pod gets a real VPC IP, from the same subnet range as the nodes, attached as secondary IPs on the node's elastic network interfaces (ENIs). So pods are first-class on your VPC network — a pod IP is routable, reachable, and shows in VPC flow logs — with no overlay/encapsulation like Calico or Flannel. The catch is density: each instance type supports a limited number of ENIs and IPs, so pods-per-node is capped by that (the "max pods" limit), and you can exhaust VPC IPs fast. Prefix delegation (assigning /28 prefixes instead of single IPs) raises density, and security groups for pods let you attach SGs at pod granularity.

Beyond prefix delegation, two levers matter at scale. The CNI keeps a warm pool of pre-attached IPs governed by WARM_IP_TARGET/WARM_ENI_TARGET — tune it down and you conserve scarce VPC IPs, up and you schedule pods faster. And custom networking lets pods draw IPs from a different subnet than the nodes — typically a non-routable secondary CIDR like 100.64.0.0/10 — so you escape exhausting your primary routable space entirely.

The tradeoff is native VPC integration versus IP exhaustion. Real VPC IPs mean pods integrate cleanly with VPC networking, security groups, and observability — no overlay overhead, and other AWS resources can reach a pod directly — but I must plan the VPC CIDR and subnet sizing for pod scale (a common incident is running out of IPs and pods stuck Pending with no address), and use prefix delegation for dense nodes. It's a real design decision at cluster creation: size subnets for peak pod count, not node count. This is also why pod-to-pod and pod-to-AWS-service networking "just works" on EKS — the pod is genuinely on the network.

Check yourself Your routable VPC CIDR is nearly full but you must keep adding pods. How can custom networking let pods keep getting IPs without consuming more of that primary space? Add a secondary CIDR to the VPC (e.g. the non-routable 100.64.0.0/10 range) and configure VPC CNI custom networking (via ENIConfig) so pods draw their IPs from that secondary subnet instead of the node subnet — pods still get real VPC IPs, but out of space that doesn’t drain your limited routable range.

04EKS · advanced

A pod assumes an AWS IAM role (IRSA / Pod Identity)

Why it mattersGiving pods scoped AWS access without node-wide keys is the EKS security keystone — and where EKS meets IAM.

Analogy Instead of the whole floor sharing one master keycard (the node role), each worker shows their personal company badge (the ServiceAccount token) to the key desk (STS), which hands back a card that opens only their own office and expires by lunchtime.

A pod often needs AWS permissions (read S3, write DynamoDB). The wrong way is baking in keys or using the node's instance role (every pod on the node gets the same broad access). The right way is per-pod IAM. IRSA (IAM Roles for Service Accounts) uses OIDC federation: the cluster has an OIDC provider registered in IAM; you annotate a Kubernetes ServiceAccount with an IAM role ARN; the pod gets a short-lived projected OIDC token; and the AWS SDK exchanges it via STS AssumeRoleWithWebIdentity for temporary credentials scoped to that role. The newer EKS Pod Identity simplifies this with an agent and association API — no per-cluster OIDC setup, easier at scale. Either way, a pod gets exactly the role it needs, with temporary, auto-rotated creds.

The security hinges on the role’s trust-policy condition: it must pin the OIDC sub to the exact system:serviceaccount:<ns>:<name> and aud to sts.amazonaws.com — a too-loose condition (a wildcard, or only checking aud) lets any pod in the cluster assume that role, a classic misconfiguration. EKS Pod Identity sidesteps per-cluster OIDC entirely: an on-node agent serves creds over a link-local endpoint, takes precedence in the SDK credential chain, and makes a role reusable across clusters.

This is least privilege and short-lived credentials applied to Kubernetes workloads — the same principle as the Vault/virtual-key story, realized natively on AWS. IRSA/Pod Identity means no long-lived AWS keys in the cluster, per-workload scoping (this pod reads this bucket, nothing else), and automatic rotation via STS — so a compromised pod is bounded to its role, not the whole node. I keep the node instance role minimal (just enough to be a node) and push all application permissions to IRSA/Pod Identity. It's the cleanest example of EKS meeting IAM, and exactly what I'd point to when asked how workloads get cloud permissions securely.

Check yourself An IRSA role’s trust policy only checks the OIDC aud claim (sts.amazonaws.com) and not the sub. Why is that a privilege-escalation risk? Every ServiceAccount token in the cluster carries the same aud, so checking only aud means any pod can assume that role — a compromised unrelated workload gets its permissions. The sub condition (system:serviceaccount:ns:name) is what scopes the role to one specific ServiceAccount; without it the role is effectively cluster-wide.

05EKS · advanced

A Service or Ingress provisions an AWS load balancer

Why it mattersHow Kubernetes objects become real AWS load balancers is the key EKS-to-AWS integration point.

Analogy You pin a work order to the board (‘I need an ALB’) and a dedicated clerk (the controller) quietly builds the real thing to match — and crucially won’t declare a new desk ‘open for customers’ until the receptionist can actually route callers to it.

When you create a Service of type LoadBalancer or an Ingress in EKS, the AWS Load Balancer Controller (running in the cluster, watching those objects) provisions a real AWS load balancer to match. A Service of type LoadBalancer → a Network Load Balancer (L4); an Ingress → an Application Load Balancer (L7, with host/path routing). The controller manages target registration: with target-type IP, it registers pod IPs directly as targets (possible because the VPC CNI gives pods real IPs — the LB talks straight to pods, skipping the node hop), versus target-type instance (traffic to a NodePort, then kube-proxy). It wires health checks, security groups, and TLS (ACM certs) from annotations on the k8s object.

The detail that makes rollouts truly zero-downtime is pod readiness gates: in IP target mode the Load Balancer Controller injects a gate so a new pod isn’t counted Ready until it’s actually registered and healthy in the ALB/NLB target group — otherwise a rolling update could kill old pods before the LB knows the new ones exist, dropping traffic. You can also attach an existing target group to pods directly with the TargetGroupBinding CRD, and the ecosystem is converging on the Kubernetes Gateway API for this.

This is the seam where a Kubernetes abstraction becomes AWS infrastructure — you declare intent in Kubernetes and the controller reconciles an ALB/NLB into existence, the same declarative model as everything else. The choices I make: IP target-type (direct-to-pod, fewer hops, works with pod readiness) versus instance; ALB for HTTP routing (path/host rules, one ALB fronting many services via Ingress groups to save cost), NLB for raw TCP/low-latency/static-IP; TLS terminated at the ALB with ACM. It ties the EKS, load-balancer, and networking stories together: the k8s object, the AWS LB, and the pod IPs the VPC CNI made routable.

Check yourself Without readiness gates, how can a rolling update on EKS drop requests even though Kubernetes thinks every new pod is ‘Ready’? Kubernetes marks a pod Ready as soon as its probes pass, but the ALB/NLB may not have registered and health-checked it yet; the rollout then terminates old pods while the LB still has no healthy new targets, so traffic lands nowhere. The readiness gate holds the pod ‘not Ready’ until the load balancer target is confirmed healthy, keeping old pods in service until the new ones truly receive traffic.

06EKS · advanced

An EKS cluster is upgraded

Why it mattersVersion upgrades are a recurring, high-stakes reality — and the order and API-deprecation checks are what keep them safe.

Analogy Climbing a ladder you can’t skip rungs on, while the floors below you expire on a timer: stay too long on an old rung and you’re forced into a rushed, expensive scramble to catch up.

Kubernetes releases roughly quarterly and EKS supports a sliding window of versions, so you upgrade regularly. The order matters: first the control plane (AWS upgrades it in place, one minor version at a time — you can't skip), then the managed add-ons (CoreDNS, kube-proxy, the VPC CNI — kept compatible), then the data plane (node groups rolled to the new Kubernetes/AMI). Kubernetes allows limited version skew (kubelet can be a couple minors behind the API server, not ahead), which is why the control plane goes first. Managed node group upgrades cordon-and-drain nodes respecting PodDisruptionBudgets and roll new ones in.

Two concrete things the answer skips. Versions drop out of standard support into extended support (more months, but at a higher per-cluster hourly price, and you’re auto-enrolled) — so letting a cluster age literally costs more. And you don’t hunt deprecated APIs by hand: tools like kube-no-trouble (kubent) or Pluto scan manifests, and EKS cluster insights flags upgrade blockers in-console. For a risky multi-version jump, standing up a blue-green cluster and shifting traffic can beat an in-place upgrade.

I treat upgrades as a routine, staged, tested process, not a scary event — precisely because you can't skip minors and support windows expire (a cluster left too long forces rushed multi-step or AWS-forced upgrades). So I upgrade regularly, in non-prod first, watching for deprecated API removals — the thing that actually breaks apps, a removed API version in the new release — and I make sure workloads have PDBs so the data-plane node drain stays graceful (the drain scenario from the platform volume, in AWS). The sequence — control plane, add-ons, nodes — and API-deprecation checking are the two things that separate a smooth upgrade from an outage.

Check yourself How do you find out before upgrading whether a new Kubernetes version will break your workloads, rather than discovering it after? Scan your manifests and live objects for removed/deprecated API versions with a tool like kube-no-trouble (kubent) or Pluto, and check EKS cluster insights, which flags known upgrade blockers for the target version — then fix the API versions in non-prod first. API removal (not the control-plane bump itself) is what actually breaks apps.

07EKS · advanced

Karpenter provisions right-sized capacity

Why they ask It’s the modern EKS autoscaler, and ‘how do nodes actually appear?’ separates people who’ve run it from people who’ve only read about it.

Analogy Cluster Autoscaler is a car park with fixed-size floors you add or remove whole; Karpenter is a valet who sees the exact cars waiting and conjures a bay that fits them — then reshuffles cars to close half-empty floors.

Karpenter watches for unschedulable (Pending) pods directly, reads their combined CPU/memory/architecture/zone/taint requirements, and provisions a right-sized EC2 instance to fit them — calling the EC2 Fleet API in seconds rather than scaling fixed Auto Scaling Groups the way Cluster Autoscaler does. You give it one or more NodePools (allowed instance families, zones, capacity type, limits) and an EC2NodeClass (AMI, subnets, security groups, node role), and it picks the cheapest instance that satisfies the pending pods.

Its second job is consolidation: Karpenter continuously looks for nodes it can remove, or replace with cheaper/smaller ones, by repacking pods — so the cluster stays bin-packed as workloads come and go. It leans hard on Spot (draining ahead of the reclaim notice) and on instance-type diversity, and it respects PodDisruptionBudgets and do-not-disrupt annotations when it moves pods.

The trade I’d name is agility and cost versus churn: Karpenter’s workload-aware, ASG-free provisioning gives faster scheduling and tighter bin-packing (real savings with Spot and diverse types), but aggressive consolidation means more node movement — so I bound it with disruption budgets, a consolidation policy (WhenEmptyOrUnderutilized with a stabilization window), and sensible NodePool limits. I keep a small on-demand NodePool for system and stateful pods, and make sure PDBs and graceful termination are set, because Karpenter will move pods to pack nodes — which is exactly the drain story, driven by cost.

Check yourself How does Karpenter decide what instance to launch when pods are Pending, and how does that differ fundamentally from Cluster Autoscaler? Karpenter reads the actual resource and constraint requirements of the pending pods and provisions a right-sized instance directly via the EC2 Fleet API — choosing family, size, zone, and Spot/on-demand to fit them most cheaply. Cluster Autoscaler can only grow or shrink pre-defined, fixed-shape Auto Scaling Groups, so it’s coarser and bound to the instance types you configured in advance.

Service 02 — The virtual network

AWS Networking (VPC)

Your own software-defined datacenter network. Everything else sits inside it, so the CIDR, the public/private split, the two firewall layers, and how you connect and stay private are foundational.

08VPC · core

A VPC is created and a packet routes

Why it mattersThe VPC is the foundation every AWS architecture sits inside — and the CIDR is the one decision that's painful to change.

Analogy Designing a town before building it: you fix the postcode range (CIDR), carve streets into districts (subnets, one per borough/AZ), and post a signpost at each junction (the route table) — and widening the postcode later is the one change that means digging up roads.

A VPC is your isolated virtual network in a region, defined by a CIDR block (say 10.0.0.0/16). You carve it into subnets, each in one Availability Zone (so subnet choice = AZ placement). Each subnet has a route table deciding where packets go: a local route for the VPC's own CIDR (so everything in the VPC can talk) plus routes to gateways. To reach the internet, a subnet's route table points 0.0.0.0/0 at an Internet Gateway. So a packet from an instance matches local for in-VPC destinations, or follows the default route to the IGW for the internet, where the IGW does public-IP translation.

Three facts that save incidents: route tables use longest-prefix match, so a more specific route always wins over 0.0.0.0/0 (how you carve exceptions). The CIDR isn’t fully unfixable — you can add secondary CIDR blocks later (and a non-routable 100.64.0.0/10 for pods) — though planning right up front is still far cleaner. And AZ names are randomised per account (my us-east-1a isn’t yours), so for cross-account placement you use the stable AZ IDs (use1-az1).

The model I give is "a VPC is a software-defined datacenter network you fully control" — CIDR, subnets, routing, gateways — and the route table is the heart of it: routing is explicit and per-subnet, which is what actually makes a subnet "public" or "private" (does its route table have a path to an IGW?). I design the CIDR deliberately up front — big enough for growth and for EKS pod IPs, non-overlapping with other VPCs and on-prem so I can peer later — spread subnets across AZs for availability, and treat the route table as the thing that encodes network intent. Get the CIDR wrong and you're rebuilding; it's the one decision that's genuinely painful to change.

Check yourself A subnet has a default route 0.0.0.0/0 → NAT but you also add 10.50.0.0/16 → a peering connection. For a packet to 10.50.1.5, which route wins and why? The peering route wins, because route tables use longest-prefix (most-specific) match: 10.50.0.0/16 is more specific than 0.0.0.0/0, so the packet goes over the peering connection, not the NAT. Specificity, not order, decides.

09VPC · core

Public vs private subnets & NAT

Why it mattersThe public/private split with NAT is the standard secure-network blueprint.

Analogy A building where residents can go out the back door to run errands but no stranger can come in that way (NAT) — and the back door has a hard limit on how many people can be mid-errand to the same shop at once before it jams.

A public subnet has a route to the Internet Gateway and its instances can have public IPs, so they're directly reachable from and to the internet (load balancers, bastions). A private subnet has no route to the IGW, so instances have no inbound internet path — where you put databases, app servers, most workloads. But private instances often still need outbound internet (pull packages, call APIs), so you route their 0.0.0.0/0 to a NAT Gateway in a public subnet: it lets outbound connections through and returns responses but blocks unsolicited inbound. NAT Gateway is managed, per-AZ, billed per hour plus per GB.

The real NAT scaling gotcha isn’t bandwidth (a NAT Gateway scales to ~100 Gbps) — it’s SNAT port exhaustion: a single NAT Gateway can hold only ~55,000 simultaneous connections to one unique destination (same IP+port), surfacing as the ErrorPortAllocation metric. Many connections to one busy endpoint can exhaust it, and adding NAT Gateways doesn’t help a single destination. For IPv6, you skip NAT entirely: an egress-only internet gateway gives stateful outbound without translation.

The pattern is public subnets for the things that must face the internet (ALB, NAT), private subnets for everything else, with NAT giving private workloads egress without exposure — defense in depth by network placement. Two flags: NAT Gateway is a real cost line (per-GB processing adds up, so for S3/DynamoDB I use VPC Gateway endpoints to skip NAT entirely), and NAT is per-AZ for HA (one per AZ, or you create a cross-AZ dependency and blast radius). The "three-tier VPC" — public/private/data subnets across AZs with NAT per AZ — is my default blueprint, and I optimize NAT cost with endpoints. It's the network expression of least exposure.

Check yourself Thousands of instances all hammer one external API through a NAT Gateway and you start seeing connection failures, yet bandwidth is nowhere near the limit. What’s the likely cause? SNAT port exhaustion: a NAT Gateway supports ~55k simultaneous connections to a single unique destination (IP+port), and all that traffic to one endpoint exhausts the port pool (watch ErrorPortAllocation). Adding NAT Gateways won’t help one destination; you need more destination diversity, connection reuse/pooling, or to front the target differently.

10VPC · core

Security groups vs NACLs

Why it mattersThe stateful/stateless distinction is a constant source of confusion and a core interview point.

Analogy A security guard who remembers who he let in and automatically lets them back out (stateful SG) versus a turnstile that checks every single passage in each direction with no memory (stateless NACL) — forget the exit rule on the turnstile and people get trapped inside.

Two firewall layers. A security group is attached to an instance/ENI (or pod, on EKS), is stateful (allow an inbound request and the response is automatically allowed out — no matching outbound rule needed), and is allow-only (you can only permit, never explicitly deny; default deny). A network ACL is attached to a subnet, is stateless (you must allow both directions explicitly, since return traffic isn't tracked — mind ephemeral ports), and supports both allow and deny rules, evaluated in numbered order. So SGs are your primary, fine-grained, instance-level control; NACLs are a coarse, subnet-level backstop.

A subtlety that surprises people: security groups do connection tracking, so an already-established flow keeps working even after you remove the rule that allowed it — the change applies to new connections, not existing tracked ones (so don’t expect deleting a rule to cut a live session). And SGs have real quotas (by default 60 inbound + 60 outbound rules each, up to 5 SGs per ENI), which is a genuine ceiling when you try to express fine-grained access with long IP lists — another reason to reference SGs from SGs rather than enumerate CIDRs.

The fact to state crisply is "security groups are stateful and instance-level; NACLs are stateless and subnet-level." In practice I do almost all access control with security groups — they're stateful (simpler), and you can reference one SG from another (allow the app-tier SG to reach the DB-tier SG), which expresses tiers cleanly without hardcoding IPs. NACLs I reserve for coarse subnet-wide rules or explicit denies (block a CIDR), because their statelessness is error-prone — the classic bug is allowing inbound but forgetting to allow the ephemeral-port range for responses. SG-referencing-SG for tiering is the senior move; NACLs as a rarely-touched backstop.

Check yourself You delete the inbound rule that was allowing an active SSH session to an instance — why might that session stay connected, and what would actually drop it? Because security groups are stateful and track established connections: removing the rule stops new connections but the existing tracked flow continues until it ends or idles out. To cut it immediately you’d terminate the session at the host (or rely on a stateless NACL deny, which is re-evaluated per packet).

11VPC · advanced

You connect VPCs and reach on-prem

Why it mattersMulti-VPC and hybrid connectivity is core enterprise-architecture territory.

Analogy Private roads between estates (peering) don’t let you cut through a neighbour’s drive to reach a third house; build one central roundabout everyone connects to (Transit Gateway) and suddenly everywhere links to everywhere — from one place you control.

Several tools by shape. VPC peering connects two VPCs directly but is non-transitive — if A peers B and B peers C, A can't reach C through B — so it doesn't scale to many VPCs. Transit Gateway is the hub-and-spoke answer: a central router that VPCs (and VPN/Direct Connect) attach to, giving transitive routing across many networks from one place. For hybrid: Site-to-Site VPN (encrypted over the internet, quick, lower bandwidth) or Direct Connect (a dedicated private physical link, consistent low latency and high bandwidth). PrivateLink (interface endpoints) exposes a specific service across VPCs without full network peering.

Two things interviewers probe. Direct Connect is not encrypted — it’s a private link, not a confidential one — so for sensitive data you run a VPN over it (a public VIF) or use MACsec on supported ports. And Transit Gateway isn’t just ‘transitive routing on’: its route tables (associations and propagations) are how you segment — e.g. keep prod and dev spokes from reaching each other, or force all inter-VPC traffic through an inspection VPC. It bills per attachment-hour plus per-GB, so the hub has a cost shape too.

The progression I describe: peering for a couple of VPCs, Transit Gateway once you have many (it replaces an unmanageable mesh of peerings with a hub and centralizes routing and inspection), VPN for quick or backup hybrid links, Direct Connect when hybrid bandwidth/latency/consistency matters (often DX plus a VPN backup). The non-transitivity of peering is the gotcha that pushes people to Transit Gateway. And for exposing just one service across accounts without joining networks, PrivateLink is cleaner and more secure than peering (service-level, not network-level). Non-overlapping CIDRs everywhere is the precondition — which is exactly why VPC CIDR planning up front matters.

Check yourself Compliance says traffic between on-prem and AWS must be encrypted in transit. You already have Direct Connect — is that enough, and if not, what do you add? Not enough: Direct Connect is a private but unencrypted link. 12VPC · advanced

A private service is reached without the internet (VPC endpoints)

Why it mattersKeeping AWS-service traffic private is a security, cost, and compliance win at once.

Analogy Instead of your staff leaving the building to post letters at the public post office (NAT to the internet), you install a private mail chute straight into the postal network inside your own lobby — the mail never touches the street.

Normally an instance calling S3 or another AWS service routes out through the NAT Gateway over public AWS endpoints. VPC endpoints keep that traffic inside the AWS network. Two kinds: Gateway endpoints (for S3 and DynamoDB) add a route so traffic to those services goes directly, privately, and free — no NAT, no internet. Interface endpoints (powered by PrivateLink) put an ENI with a private IP in your subnet for a service, so calls resolve to a private address and never leave the VPC (hourly + per-GB cost). Either way, private subnets use AWS services with no internet path.

The make-or-break detail for interface endpoints is private DNS: enable it and the service’s normal public hostname (secretsmanager.<region>.amazonaws.com) resolves to the endpoint’s private IP inside the VPC, so your SDKs need no code change; disable it (or lack enableDnsHostnames) and you must call the clunky endpoint-specific DNS name instead. Note the reach difference too: Gateway endpoints (S3/DynamoDB) work only from inside the VPC — not from on-prem or peered VPCs — whereas interface endpoints can be reached across peering/VPN/DX.

I use VPC endpoints for three reasons — security (traffic never traverses the internet, and you can restrict a bucket to only your VPC endpoint via policy), cost (Gateway endpoints for S3/DynamoDB eliminate NAT data-processing charges, often a big saving), and compliance (regulated workloads that must not egress). So for an EKS cluster in private subnets talking to S3, DynamoDB, ECR, Secrets Manager, STS, I add the relevant endpoints so nothing needs a NAT or IGW. It's the "private by default" posture: the workload reaches exactly the AWS services it needs over private links, and the network has no general internet egress at all. Ties straight to the S3 security story.

Check yourself You add an interface VPC endpoint for Secrets Manager, but your app — unchanged — still reaches it over the public path via NAT. What’s the most likely missing piece? Private DNS on the endpoint isn’t enabled (or the VPC lacks enableDnsSupport/enableDnsHostnames), so the standard service hostname still resolves to a public IP. Turn on private DNS and the normal endpoint name resolves to the endpoint’s private IP inside the VPC — no app change — and traffic stays off the internet.

13VPC · debugging

You debug ‘why can’t A reach B’

Why they ask Connectivity debugging is the most common real VPC task, and a structured method beats guessing — interviewers want the checklist, not a lucky fix.

Analogy A blocked delivery has a fixed line-up of suspects: wrong address book (route table), a locked building door (NACL), a locked office door (security group), or no road at all (missing route) — you check each layer in order instead of kicking the door.

A packet from A to B must survive every layer, so I walk them in order. Routing: does A’s subnet route table have a path to B (a local route, a peering/TGW route, a NAT/IGW for the internet)? NACL (subnet, stateless): is the traffic allowed in both directions, including the ephemeral return ports? Security group (instance, stateful): does B’s inbound SG allow A — by CIDR or by referencing A’s SG — and does A’s outbound allow it? Then the non-network suspects: is B actually listening, is there a host firewall, is DNS resolving to the right address?

VPC Flow Logs turn this from guesswork into evidence: they record accepted and rejected flows per ENI (source, destination, port, protocol, and an ACCEPT/REJECT action). A REJECT on B’s ENI points at a security group or NACL; traffic that never appears at all points at routing — it never got there. Reachability Analyzer goes further: it statically analyses your config and names the exact hop (which SG rule or missing route) that blocks a path, without sending a packet.

The architect value is a repeatable mental checklist — route table → NACL (both directions, ephemeral ports) → security group (stateful, SG-references-SG) → is the service listening — plus knowing which tool proves which layer: Flow Logs for ‘what actually happened’ (a REJECT versus silence distinguishes a firewall drop from a routing gap), Reachability Analyzer for ‘what the config permits’ before you even deploy. I centralise Flow Logs to CloudWatch or S3 and query with Athena/Log Insights, and I treat ‘silence in the logs’ as the key tell that the packet never arrived — a routing or endpoint problem, not a firewall one.

Check yourself A connection from an app server to a database times out. VPC Flow Logs on the database’s ENI show no entries for that traffic — not even a REJECT. What layer is the problem, and what is it not? If nothing — not even a REJECT — reaches the DB’s ENI, the packet never arrived, so it’s a routing problem (a missing or wrong route-table entry, peering/TGW route, or wrong subnet), not a security-group or NACL block: a firewall drop would show as an explicit REJECT on the ENI. Fix the route, not the SG.

Service 03 — Who can do what

AWS IAM

The authorization brain of AWS. One evaluation rule explains every access puzzle; roles and temporary credentials replace long-lived keys; and boundaries, SCPs, and federation are how least privilege holds at organizational scale.

14IAM · core

An API request is authorized by IAM

Why it mattersThe policy-evaluation model is the foundation of all AWS security — and the key to debugging access.

Analogy A bouncer with a strict rulebook: a single ‘no’ from anyone with authority ends it, no amount of ‘yes’ overrides a ‘no’, and silence means no — you don’t get in just because nobody said you couldn’t.

Every AWS API call is authenticated (who are you), then authorized against the request context: the principal, the action (s3:GetObject), the resource, and conditions (IP, MFA, tags). IAM gathers all applicable policies — identity-based (attached to the user/role) and resource-based (attached to the resource, like a bucket policy) — and evaluates with a strict rule: default deny (implicit deny if nothing allows), an explicit Allow grants it, and an explicit Deny anywhere overrides any allow. So: explicit deny? → deny. Else an allow? → allow. Else → deny.

The twist the base answer skips is cross-account evaluation: within one account, an allow in either an identity policy or the resource policy can suffice; but across accounts you need both sides to allow — an identity policy in the caller’s account and a resource policy (or role trust) in the resource’s account. The full precedence to recite: an explicit Deny anywhere wins first, then the request must pass the SCP, the resource/identity policy, any permission boundary, and any session policy — all of them — or it’s denied.

The model to state precisely is "default deny; explicit allow grants; explicit deny always wins." That single rule explains most access puzzles — why a user with an admin policy is still blocked (an explicit deny or an SCP), and why access needs an allow somewhere (nothing is permitted by default). I use identity policies for "what can this principal do" and resource policies for "who can touch this resource" (essential for cross-account, since a resource policy can grant access to a principal in another account). And I debug denials by walking the evaluation — which policy allows, is there a deny, an SCP, a boundary — rather than guessing. Principal / action / resource / condition is the four-part frame for every rule.

Check yourself A principal in account A has s3:GetObject in its identity policy for a bucket in account B, but gets AccessDenied. The bucket has no policy mentioning account A. Why — and what’s needed? Cross-account access requires both sides to allow: account A’s identity policy and account B’s resource (bucket) policy must each grant it. With no bucket policy allowing account A’s principal, B never consents, so it’s denied — unlike same-account, where one allow can be enough. Add a bucket policy granting A’s principal (and the KMS key policy too, if SSE-KMS).

15IAM · core

A role is assumed (STS & temporary credentials)

Why it mattersRoles and temporary credentials are the heart of modern AWS security — long-lived keys are the anti-pattern.

Analogy A day-pass, not a permanent key: you show who you are at the desk (trust policy), they check what the pass is good for (permission policy), and hand you a wristband that stops working by the end of the session — lose it and it’s worthless tomorrow.

A role is an identity with permissions but no permanent credentials — a principal assumes it and gets temporary credentials from STS (the Security Token Service). Assuming checks two policies: the role's trust policy (who may assume it — an account, a service, a federated identity) and its permission policy (what it can do once assumed). STS returns short-lived credentials (access key, secret, session token) that expire in minutes to hours. EC2 instance profiles, Lambda execution roles, and EKS IRSA all work this way — the workload assumes a role and gets rotating temporary creds, never a stored long-lived key.

Operational edges worth knowing: role chaining (assuming a role from already-assumed-role creds) is hard-capped at a 1-hour session and can’t be extended, which surprises people doing multi-hop automation. Prefer regional STS endpoints over the single global one (lower latency, smaller blast radius if a region wobbles). And the RoleSessionName you pass shows up in CloudTrail — set it meaningfully so ‘who did this’ is answerable when many principals share a role.

The principle is "prefer roles and temporary credentials over long-lived access keys, always." Long-lived IAM user keys are the thing that leaks in a repo and causes a breach; temporary STS credentials auto-expire, are scoped, and are issued just-in-time. So every workload gets a role (instance profile, Lambda role, IRSA/Pod Identity on EKS), humans get roles via SSO/federation, and cross-account access is a role assumption with a trust policy — not shared keys. The trust-policy-vs-permission-policy distinction is the thing people miss: trust says who can assume, permissions say what they can then do. It's the same short-lived-credential theme as Vault and the LLM gateway's virtual keys — issue scoped, expiring credentials, never store durable secrets.

Check yourself Your automation assumes role X, then uses those credentials to assume role Y, and you ask for a 4-hour session on Y but only get 1 hour. Why? This is role chaining (assuming a role using credentials that are themselves from an assumed role), which AWS hard-caps at a 1-hour session regardless of the role’s max session duration — it can’t be extended. Restructure so the final role is assumed directly (e.g. from a user/instance/OIDC identity) if you need a longer session.

16IAM · advanced

Cross-account and federated access

Why it mattersEnterprise AWS is many accounts and external identities — federation is how it holds together.

Analogy Rather than issuing a house key to every visitor forever, you let their own employer vouch for them at the door each morning and hand them a day-pass — one authoritative identity source, no sprawl of permanent keys to lose.

Two patterns. Cross-account: a role in account B has a trust policy allowing a principal in account A to assume it, so users/workloads in A get scoped access to B's resources with no B credentials — the standard way to share across an AWS Organization (often with an external ID to prevent the confused-deputy problem). Federation: instead of IAM users, an external identity provider vouches for a user — SAML (corporate directory/SSO) or OIDC (web identity) — and they assume a role via STS (AssumeRoleWithSAML / WithWebIdentity). IAM Identity Center (SSO) is the managed front end for workforce federation across accounts. And EKS IRSA is exactly OIDC federation — the cluster's OIDC provider vouches for a pod's service account.

The detail that separates two genuinely different protections people conflate: the external ID guards the third-party SaaS confused-deputy case (a vendor assuming a role in many customers’ accounts — the external ID proves the call is for your account), whereas aws:SourceArn/aws:SourceAccount conditions guard the AWS-service confused deputy (e.g. ensuring only your CloudTrail/S3 can make a service call against your KMS key). Same threat shape, two different keys depending on who the deputy is.

The mental model is "don't create IAM users; federate." Humans come in through SSO/Identity Center mapped to roles per account; applications and cross-account access use role assumption with trust policies; external/web identities use OIDC. This keeps identity in one authoritative place (your IdP), gives everyone temporary credentials, and scales to hundreds of accounts without a sprawl of long-lived users. The external ID on cross-account roles is the detail I'd mention for confused-deputy protection. And recognizing IRSA as "just OIDC federation" ties the EKS and IAM stories together — it's the same mechanism, applied to pods.

Check yourself When do you protect a role with an external ID versus with aws:SourceArn/aws:SourceAccount conditions — aren’t they the same confused-deputy fix? Same threat, different deputy. Use an external ID when a third-party SaaS vendor assumes a role across many customers’ accounts — it proves the assumption is meant for your account. Use aws:SourceArn/aws:SourceAccount when an AWS service acts on your behalf (CloudTrail→SNS, S3→KMS) — they pin the call to the specific source resource/account you expect.

17IAM · advanced

Permissions are scoped down (boundaries, SCPs, intersection)

Why it mattersThe layered guardrails and how they combine is advanced-but-essential IAM — and where most "denied despite an allow" puzzles end.

Analogy Your bank account has a balance (what you’re granted) but also a daily ATM cap, a per-store spend limit, and a parental control — your real spending power is wherever all the limits overlap, and any one ‘blocked’ beats every ‘allowed’.

Several controls narrow what a principal can actually do, and effective permissions are the intersection of all of them (with any explicit deny winning). An identity policy grants. A permission boundary caps the maximum a principal can have (even if its identity policy grants more). Service Control Policies (SCPs), set at the AWS Organizations level, cap the maximum for entire accounts/OUs — a guardrail no one in the account can exceed, not even root, and SCPs don't grant, they only limit. A session policy further narrows a specific assumed-role session. So a call is allowed only if the identity policy allows it AND the boundary allows it AND the SCP allows it AND no explicit deny exists.

Two additions. SCPs got a resource-side sibling in late 2024: Resource Control Policies (RCPs) set an org-wide ceiling on what resource-based policies can grant (e.g. ‘no bucket in this org may be shared outside the org’) — SCPs cap identities, RCPs cap resources. And a gotcha: SCPs don’t apply to the management account (so don’t run workloads there expecting guardrails), and they only filter — they never grant.

The model I articulate: "grants come from identity/resource policies; boundaries, SCPs, and session policies only ever subtract — effective permission is the intersection." SCPs are the org-wide guardrail for non-negotiables (deny leaving approved regions, deny disabling CloudTrail, deny certain services) — they can't grant, only fence. Permission boundaries I use to delegate safely (let a team create roles, but bounded so they can't escalate). This layered model is how you run least privilege at organizational scale: developers get freedom within guardrails they can't breach. And "why am I denied despite an allow" almost always ends at an SCP, a boundary, or an explicit deny — the intersection rule biting.

Check yourself You want an org-wide guarantee that no S3 bucket anywhere in the organisation can be made accessible to an external account, no matter what a team sets as a bucket policy. SCPs cap identities — what do you use? A Resource Control Policy (RCP) at the organisation/OU level: it caps what resource-based policies (like bucket policies) can grant, so even if a team writes a bucket policy sharing externally, the RCP’s ceiling denies it. SCPs only bound what identities in your org can do; RCPs bound what your resources can grant to anyone.

18IAM · advanced

Access is granted by tags (ABAC)

Why they ask ABAC is how access scales to thousands of resources without a policy per team — and tag-based authorization is increasingly the expected answer to ‘how do you avoid policy sprawl?’

Analogy RBAC hands out a labelled key for every room; ABAC instead says ‘your badge opens any room whose colour matches your badge’ — one rule covers every current and future room, as long as both are tagged.

ABAC (attribute-based access control) writes policies in terms of tags rather than named resources. A single policy can say ‘allow these actions on resources whose Project tag equals the principal’s Project tag’, with a condition comparing aws:ResourceTag/Project to aws:PrincipalTag/Project. Now a new resource created with the right tag is automatically accessible to the right people — no policy edit — which is how you scale access across many teams and thousands of resources with a handful of policies.

The attributes come from the principal’s tags, and for federated users from session tags passed at AssumeRole time (the IdP asserts Project=atlas and STS carries it into the session). The catch is governance: ABAC is only as trustworthy as your control over who can set the tags — if a principal can tag itself or a resource, it can grant itself access — so you must lock down iam:TagRole and resource tag permissions, and enforce a consistent, un-forgeable scheme with tag policies and SCPs.

I reach for ABAC when RBAC would explode into a policy-per-team-per-environment matrix: one tag-matching policy replaces hundreds, and access follows correctly-tagged resources automatically — a big operational win in multi-tenant or many-team accounts. The discipline I insist on: the tags that drive authorization must be protected (a workload must not be able to re-tag itself to escalate), ideally injected as session tags from a trusted IdP rather than self-set, with SCP/tag-policy guardrails on tagging. I combine ABAC for the scalable bulk with RBAC for the few coarse, high-privilege roles. ‘Tag equals tag’ is the elegant part; ‘who controls the tags’ is the real design question.

Check yourself Your ABAC policy grants access when aws:PrincipalTag/Project matches aws:ResourceTag/Project. Why can this become a privilege-escalation hole, and how do you close it? If a principal can set its own tags, or a resource’s Project tag, it can make the two match and grant itself access — the policy trusts tags it doesn’t control. Close it by denying self-tagging and scoping iam:Tag* and resource tag permissions, injecting principal tags as session tags from a trusted IdP (not self-set), and enforcing tag hygiene with tag policies and SCPs.

19IAM · advanced

A role is passed to a service (iam:PassRole)

Why they ask iam:PassRole is the quiet permission behind most IAM privilege-escalation findings — interviewers probe whether you grasp that handing a role to a service is itself a sensitive act.

Analogy Hiring a contractor and handing them your master keyring to do the job: the dangerous permission isn’t the contractor’s — it’s your right to hand over that keyring. Give someone the right to pass powerful keyrings and they can act as anyone.

When you launch an EC2 instance with an instance profile, create a Lambda with an execution role, or give ECS a task role, you are passing a role to that service — the service then assumes it and acts with its permissions. AWS gates that act with a separate permission on the caller: iam:PassRole. You may create the resource only if you’re also allowed to pass that specific role to that specific service, scoped by the role ARN and an iam:PassedToService condition.

This is why PassRole is a classic escalation path: a user with broad iam:PassRole plus the ability to run a service can pass a high-privilege role (say an admin role) to a Lambda or EC2 instance they control, and inherit its power — without ever holding those permissions directly. So you scope PassRole tightly: which roles, to which services, never Resource: *. Its sibling concept is the service-linked role — a predefined, service-owned role a service creates for its own API calls, which you don’t pass or edit.

I treat iam:PassRole as a privilege-granting permission, not a bookkeeping detail: audits should flag any identity with PassRole on *, and I scope it to an explicit allow-list of role ARNs plus iam:PassedToService, so a developer can pass only the app roles meant for EC2/Lambda, never an admin role. It pairs directly with the boundaries story — a permission boundary is how you let a team create and pass roles without being able to escalate past the cap. Knowing that ‘launch this service with that role’ silently requires PassRole is the detail that separates someone who’s debugged a ‘why can’t I start this Lambda’ from someone who hasn’t.

Check yourself A developer can create Lambda functions and has iam:PassRole on *, but holds no admin permissions themselves. Why is that effectively admin, and how do you fix it? They can create a Lambda and pass an existing high-privilege (admin) role to it, then invoke it — the function runs with that role, so they’ve escalated to admin without holding it directly. Fix by scoping iam:PassRole to a specific allow-list of low-privilege role ARNs (with an iam:PassedToService condition), never Resource: *.

Service 04 — Keys & encryption

AWS KMS

Central, audited, unexportable keys. Envelope encryption is the pattern under every "encrypted at rest," key policies are the authorization twist, and multi-region keys plus caching are what make it work at scale and across regions.

20KMS · core

Data is encrypted with KMS (envelope encryption)

Why it mattersEnvelope encryption is the core KMS pattern and a frequent architecture question.

Analogy You don’t mail the bank vault to encrypt a parcel — the vault stamps you a single-use padlock (a data key), you lock the parcel yourself, then lock that padlock’s spare key inside a tiny box only the vault can reopen, and tape it to the parcel.

A KMS key (the CMK / KMS key) never leaves KMS — it lives in a FIPS-validated HSM and can't be exported. So you don't encrypt large data directly with it (that'd mean sending all your data to KMS). Instead: envelope encryption. You call GenerateDataKey; KMS returns a fresh data key twice — once plaintext, once encrypted under your CMK. You encrypt your actual data locally with the plaintext data key, discard the plaintext key, and store the encrypted data key alongside the ciphertext. To decrypt, you send the encrypted data key to KMS, which uses the CMK to decrypt it and returns the plaintext data key, and you decrypt locally. The CMK only ever wraps small data keys.

Worth distinguishing the key types and ownership the base answer glosses. KMS keys can be symmetric (the usual GenerateDataKey envelope flow) or asymmetric (RSA/ECC) — asymmetric lets you hand out a public key so external parties encrypt-to-you or verify signatures without any KMS access. And ownership matters for control and cost: AWS-managed keys (policy and ~annual rotation run by AWS, free), customer-managed keys (you own the policy, rotation, cross-account sharing — small monthly cost), and invisible AWS-owned keys.

The elegance to explain: envelope encryption gives the security of an unexportable, centrally-controlled, audited master key without routing bulk data through KMS — you do bulk crypto locally with data keys, and KMS only guards the small key that unlocks them. That's why every AWS service (S3, EBS, RDS) uses it under the hood. The security property: control of the CMK is control of the data — disable the CMK and the encrypted data keys can't be decrypted, so data is effectively inaccessible (a powerful kill-switch and access boundary), and every use is logged in CloudTrail. Data-key caching is the optimization when you'd otherwise call KMS too often.

Check yourself An external partner must be able to encrypt data that only you can decrypt, but you refuse to give them any AWS/KMS access at all. Which KMS key type fits, and why? An asymmetric KMS key: you publish the public key, the partner encrypts with it offline (no AWS credentials needed), and only you — holding the private key that never leaves KMS — can Decrypt. A symmetric key can’t do this, because encrypting with it requires calling KMS/holding the key.

21KMS · advanced

A KMS key is used by a service (SSE-KMS)

Why it mattersHow services integrate KMS — and its double-authorization model — is everyday practical KMS.

Analogy The locked filing room (SSE-KMS) opens automatically as you fetch a folder — but only if your badge works on both the room door (S3) and the cabinet lock (the KMS key); a badge for just the room gets you a frustrating ‘access denied’ at the cabinet.

When you enable SSE-KMS on S3 (or EBS, RDS), the service does envelope encryption for you transparently: on write it gets a data key, encrypts, stores the encrypted data key; on read it asks KMS to decrypt the data key and decrypts — invisible to the caller, provided the caller is authorized to use the key. Authorization is the twist: KMS access is governed primarily by the key policy (attached to the key), which must allow the principal — unlike most services where IAM alone suffices, a KMS key requires its key policy to grant access (IAM then further scopes it). Grants delegate limited, temporary key use programmatically. Encryption context (extra key-value AAD) can be required and logged for binding.

At scale the operational fix the answer omits is S3 Bucket Keys: enable them and S3 derives a short-lived bucket-level data key instead of calling KMS per object, cutting GenerateDataKey/Decrypt calls (and KMS cost + throttling risk) by up to ~99% on busy buckets — the S3-layer cousin of data-key caching. For a higher assurance bar there’s also DSSE-KMS (dual-layer server-side encryption) applying two independent layers.

The operational gotcha I flag is the double authorization: to read an SSE-KMS-encrypted object you need both S3 permission AND kms:Decrypt on the key, and the key policy must permit it — the classic "I have S3 access but get AccessDenied" is a missing KMS permission. So I design key policies deliberately (who administers the key vs who uses it), use grants for temporary/service delegation, and use encryption context to bind ciphertext to purpose (so a data key for tenant A can't decrypt tenant B's data). Cross-account encrypted sharing also needs the key policy to allow the other account. KMS authorization living on the key, not just IAM, is what seniors get right and juniors trip on.

Check yourself A bucket with SSE-KMS and millions of small objects is racking up large KMS bills and occasional throttling on reads. What’s the first lever to pull? Enable S3 Bucket Keys: S3 then uses a time-limited bucket-level key to envelope-encrypt objects instead of calling KMS for every object, reducing KMS GenerateDataKey/Decrypt requests (and thus cost and throttling) by up to ~99% — with no change to who can decrypt.

22KMS · advanced

Key rotation & key policy

Why it mattersRotation and access-control detail are the governance layer of KMS.

Analogy Changing the lock’s internal pins while keeping the same keyhole label (the key ID): every door that referenced that label keeps working, old keys are retained to open old locks, and throwing a key away comes with a mandatory cooling-off period because it’s forever.

KMS supports automatic rotation: enable it and KMS rotates the cryptographic backing material (about annually) while the key ID and ARN stay the same — so applications and stored encrypted data keys keep working, because KMS retains old backing keys to decrypt old data and uses the new one for new encryption. Seamless, no re-encryption. You can also do manual rotation (create a new key, update an alias to point at it — which is why aliases exist: a stable name that can point to different keys). Access is controlled by the key policy (authoritative), optionally with IAM and grants. Deleting a key is deliberately dangerous — KMS enforces a waiting period (7–30 days, disabled meanwhile) because deletion is irreversible and orphans all data encrypted under it.

Rotation has modernised: you’re no longer stuck with fixed ~annual — you can set a custom rotation period (as short as 90 days) and trigger on-demand rotation. But imported key material (BYOK) and asymmetric keys can’t be auto-rotated — you rotate those manually. And a sharp edge: a key policy that grants no usable admin can orphan the key — unlike most resources there’s no implicit root backstop unless the policy itself grants the account root, so a bad policy can lock everyone out of the key.

Automatic rotation gives compliance-friendly key hygiene for free and transparently — old data stays decryptable, no re-encryption — because rotation changes the backing key, not the key's identity. I use aliases everywhere so applications reference a stable name, not a key ID, making manual rotation or key swaps painless. And I treat key deletion with the respect the waiting period implies: disabling (reversible) is my first move if I think a key is unused, and only after the window do I delete — a deleted CMK means its data is gone forever. Key policy is where I enforce separation of duties (admins can't necessarily decrypt; users can't change the policy).

Check yourself Why can a careless edit to a KMS key policy lock you out of the key in a way that a careless IAM policy on, say, an S3 bucket usually doesn’t? KMS key access is governed primarily by the key policy, and there’s no implicit root/admin backstop unless the key policy itself grants it — so a policy that leaves no principal able to administer the key orphans it (you can’t use or fix it, short of AWS Support). Always keep the account root (or a break-glass admin) in the key policy; most other resources fall back to account-level IAM, which KMS does not.

23KMS · advanced

KMS at scale — multi-region keys & quotas

Why it mattersThe advanced KMS concerns — DR, cross-region, throttling, cost — matter at platform scale.

Analogy A spare safe in another city that opens with the same combination (shared key material) — so a locked parcel shipped there opens fine — but each city’s safe keeps its own visitor list, so who may open it is decided locally.

Two advanced realities. Multi-region keys: a KMS key is regional by default (data encrypted in us-east-1 can only be decrypted there), which breaks cross-region DR and replication; multi-region keys are a set of related keys in different regions sharing the same key material and key ID, so data encrypted in one region can be decrypted in another — essential for cross-region replicated data (an encrypted S3 object replicated elsewhere, an active-active dataset). And request quotas: KMS API calls (Encrypt/Decrypt/GenerateDataKey) are rate-limited per region and metered per call, so a high-throughput system calling KMS on every operation can get throttled and run up cost — the fix is data-key caching (reuse a data key for many operations within a bounded window), which envelope encryption already helps by minimizing CMK calls.

The nuance people get wrong: multi-region keys share key material and the same key ID, but each regional replica has its own independent key policy, grants, aliases, and tags — they are not a single synchronised object, so you can (and should) scope each region differently. There’s also a primary↔replica relationship: one region is primary for managing material, and you can promote a replica to primary if you need to re-centre (useful in a region-loss scenario).

Multi-region keys are the KMS piece of a cross-region DR or active-active design — without them, your encrypted data can't be read in the failover region, so I plan them wherever encrypted data crosses regions (ties to the active-active, DynamoDB Global Tables, and S3-replication stories). And at scale I treat KMS as a rate-limited, per-call-priced dependency: for high-volume encryption I use data-key caching so I'm not calling KMS per object (a real throughput and cost lever), and I monitor for throttling. The two failure modes I design against are "can't decrypt in the DR region" (fixed by multi-region keys) and "KMS-throttled under load" (fixed by caching) — both the kind of thing that only shows up in production or a DR test.

Check yourself With a multi-region KMS key, if you tighten the key policy on the key in eu-west-1, does that automatically restrict the replica in us-east-1? No. Multi-region keys share key material and key ID, but each regional replica has an independent key policy, grants, and aliases — they’re not synchronised. You must update each region’s policy separately, which is also the feature: you can scope access per region (and promote a replica to primary if the primary region is lost).

24KMS · advanced

A service is granted temporary key use (grants & caching)

Why they ask Grants and data-key caching are the two mechanisms that make KMS work for programmatic, high-volume, and cross-account use — beyond the static key-policy model.

Analogy A key policy is the building’s permanent access list; a grant is a time-limited visitor pass you hand a contractor for one job, revocable the moment they’re done — and data-key caching is photocopying the one key you were given so you don’t queue at the key desk for every door.

A grant is a programmatic, fine-grained, revocable delegation of key use: ‘this principal may Decrypt with this key, optionally only with this encryption context, until I revoke it.’ AWS services use grants under the hood — an EBS volume, a DynamoDB table, a Lambda gets a grant to use your key for its lifetime — because, unlike editing the key policy, grants are additive, scoped, time-bounded, and retired/revoked individually, ideal for temporary programmatic access without rewriting policy. Creating one returns a grant token to bridge the brief eventual-consistency window.

Data-key caching solves throughput and cost: rather than calling GenerateDataKey/Decrypt per object, the AWS Encryption SDK caches a data key and reuses it across many operations, bounded by limits you set — max messages, max bytes, and a max age. That’s a deliberate security-for-performance trade: a longer-lived cached key means fewer KMS calls (dodging throttling and per-call cost) but a wider blast radius if that key leaks — so you tune the caps to your risk tolerance.

I use grants for service and cross-account delegation that must be temporary and revocable — they keep the key policy stable while handing out scoped, expiring access, and binding a grant to an encryption context means a grant to decrypt tenant A’s data can’t touch tenant B’s. Data-key caching is my lever when a workload would otherwise hammer KMS (the throttling-and-cost failure mode from the multi-region scenario): I set conservative max-age and max-messages caps so I capture most of the saving with a bounded exposure window. Grants (who, temporarily) and caching (how often you call) are the two answers to ‘KMS doesn’t scale for us’ that aren’t just ‘raise the quota’.

Check yourself Why use a KMS grant instead of editing the key policy to give a service temporary decrypt access, and what does data-key caching trade away for its cost savings? A grant is scoped, additive, and individually revocable/expiring, so you delegate temporary programmatic access without mutating (and risking) the key policy — and you can bind it to an encryption context. Data-key caching reuses one data key across many operations to cut KMS calls (throttling and cost), trading a wider blast radius if that cached key leaks — which you bound with max-age/max-messages/max-bytes caps.

AWS API Gateway

Auth, throttling, quotas, caching, and safe releases as a managed service — the AWS cousin of the gateway pattern. The architecture calls are which flavor, where auth lives, and when an ALB is the cheaper front door instead.

25API GW · core

A request hits API Gateway

Why it mattersIt's the managed front door for APIs — the lifecycle and the REST/HTTP/WebSocket split are basic-but-essential.

Analogy A managed hotel concierge desk for your APIs: it checks your reservation (auth), limits how often you can ring (throttle), translates your request into the kitchen’s format, and relays it — but it’ll hang up on you if the kitchen takes too long to answer.

API Gateway fronts your APIs. Flavors: REST APIs (full-featured — request validation, API keys, usage plans, caching, WAF), HTTP APIs (newer, cheaper, lower-latency, fewer features, JWT authorizers), and WebSocket APIs (stateful bidirectional). A request flows through a managed pipeline: it hits the endpoint, is authorized (IAM, Cognito, a Lambda authorizer, or API key), throttled against limits, optionally validated and transformed (mapping templates), then integrated with a backend — most often a Lambda function, but also an HTTP endpoint or an AWS service directly — and the response is transformed and returned. It handles TLS, scaling, and the API lifecycle for you.

A production fact that bites: integrations have a timeout — historically a hard 29 seconds (now raisable above that on REST APIs via an account quota increase, though HTTP APIs stay at 30s) — so a slow backend surfaces as a 504 at the gateway, not a hang. Also pick the endpoint type deliberately: edge-optimized (CloudFront-fronted, for globally dispersed clients), regional (callers in-region, or you front your own CDN), or private (reachable only via an interface endpoint). And for Lambda, proxy integration passes the raw request through, versus non-proxy mapping templates.

I frame API Gateway as managed API management plus a serverless front door — auth, throttling, request validation, caching, and a stable endpoint with no servers, which is why it pairs perfectly with Lambda for serverless APIs. The choice within it: HTTP APIs for most modern JSON/JWT APIs (cheaper, faster — my default), REST APIs when I need the extra features (API keys + usage plans for a partner API, request/response transformation, edge caching, WAF). It's the AWS-managed cousin of the API-gateway pattern from the agentic volume — the same cross-cutting concerns (auth, throttle, route), delivered as a service. The tradeoff is per-request cost and some latency versus running your own.

Check yourself A REST API in front of a Lambda that occasionally runs ~40 seconds returns 504 even though the Lambda eventually finishes successfully. Why, and what are the options? API Gateway enforces an integration timeout (historically a hard 29s), so it gives up and returns 504 before the ~40s Lambda finishes — the work completes but the client already got an error. Options: request a quota increase to raise the REST integration timeout, or (better) make the call asynchronous — return 202 with a job ID and let the client poll/get notified — so no request is held open that long.

26API GW · advanced

Authorization at the edge (authorizers)

Why it mattersWhere and how auth happens is the security core of API Gateway.

Analogy A doorman who writes down your face and verdict on a sticky note so he doesn’t re-check you for a few minutes — fast, until he keys the note to ‘anyone in a suit’ and lets in the next person wearing one.

API Gateway authorizes requests before they reach your backend, several ways. IAM authorization (the caller signs with SigV4 — for internal/service-to-service AWS callers). Cognito user pools (validate a Cognito token). Lambda authorizers (a function you write that inspects a token or the whole request and returns an allow/deny policy — for custom auth, e.g. validating a third-party JWT or opaque token; results are cached by token to avoid calling it every request). And API keys with usage plans (identify a client and enforce quotas — note API keys are for metering/identification, not strong auth). So auth is offloaded to the edge, and your backend only sees authorized requests.

The caching the answer praises has a sharp edge: a Lambda authorizer’s result is cached keyed by the identity source (the token, or the header(s) you configure), and the returned IAM policy is cached too — so if your identity source is too coarse or the policy you return uses a wildcard method ARN, a cached allow can leak across users or routes. Pick the cache key to be the thing that actually identifies the caller, scope the returned policy to the specific method, and know TOKEN authorizers key on one token while REQUEST authorizers can key on multiple request parameters.

The principle is authorize at the edge so backends aren't exposed to unauthenticated traffic and don't each reimplement auth — the same "gateway owns auth" idea as the LLM/agentic gateway. I pick by caller: IAM/SigV4 for AWS-internal, a JWT authorizer (HTTP APIs validate JWTs natively) or Cognito for user-facing, a Lambda authorizer for custom/legacy token schemes (leaning on its caching so it's not a per-request latency tax). API keys I use only for identifying and rate-limiting clients via usage plans, never as the actual security — a common mistake is treating an API key as authentication. Auth at the gateway plus a backend that still validates (defense in depth) is the posture.

Check yourself A Lambda authorizer with caching enabled occasionally authorizes one user as if they were another. What’s the classic cause? The authorizer cache key (identity source) is too coarse — e.g. a header that isn’t unique per user — so a cached allow/policy from one caller is reused for a different caller within the TTL. Fix by keying the cache on the actual per-user credential (the real token) and returning a tightly-scoped policy (specific method ARN, not a wildcard), so a cache hit can’t over-grant.

27API GW · advanced

Throttling, caching & stages

Why it mattersThe traffic-management and deployment features are the production side of API Gateway.

Analogy A theme-park queue system with several gates: a park-wide capacity, a per-ride limit, and your ticket’s own daily quota — whichever is tightest is the one that stops you, and a ‘come back later’ slip (HTTP 429) is how it says so.

API Gateway protects backends and manages releases. Throttling uses a token-bucket (a steady rate plus a burst) at the account, API, and method level, and per-client via usage plans tied to API keys (give partner A 100 rps, partner B 1000) — excess gets a 429. Caching (REST APIs) stores responses for a TTL keyed by request parameters, cutting backend load and latency for cacheable GETs. And deployment uses stages: you deploy an API to a named stage (dev, prod), each with its own config, throttle settings, and endpoint, and you can canary on a stage (route a percentage of traffic to a new deployment and watch before promoting).

Two precision points. Throttling is layered and the most restrictive wins — account-level (a soft, raisable default) → stage/method → per-key usage plan — and a throttle returns 429 Too Many Requests. Stage variables let one API definition point different stages at different backends (e.g. a Lambda alias per stage), which is how you wire dev/prod cleanly. And the cache isn’t free: it’s a provisioned, paid cache you size in GB per stage, so caching is a cost/latency trade, not a free win.

Throttling is a first-class protection I set deliberately — it shields the backend from spikes and abusive clients and enforces fair use per client via usage plans (the multi-tenant quota mechanism), the same rate-limiting concern as the LLM gateway's per-tenant budgets. Caching I use for read-heavy, cacheable endpoints as a cheap latency/cost win, mindful of staleness. Stages plus canary give me safe releases at the API layer (percentage rollout with rollback — the canary pattern from the delivery volume, native here). So API Gateway isn't just routing — it's the traffic-management and safe-release control point, which is exactly why you put a managed gateway in front rather than exposing backends directly.

Check yourself One client reports constant 429s while your account-wide traffic is low and other clients are fine. Where do you look? At the per-client usage plan tied to that client’s API key — throttling is layered and the most restrictive limit applies, so a low per-key rate/quota in their usage plan produces 429s regardless of spare account/stage capacity. Raise (or correct) that usage plan’s rate/burst/quota for the client.

API Gateway vs ALB vs direct

Why it mattersChoosing the right front door is a real architecture decision with cost and feature tradeoffs.

Analogy Choosing between a full-service airport (API Gateway: passport control, quotas, screening — priced per passenger) and a plain bus terminal (ALB: cheap, high-volume, just gets you to a gate) — the gap narrows now that the bus terminal added an ID check of its own.

They overlap but fit different needs. API Gateway is managed API management — auth, throttling, per-client quotas, request validation, caching, transformation, serverless-friendly (great with Lambda) — priced per request, excellent at low-to-moderate volume and for feature-rich APIs, but expensive at very high request rates. An ALB is an L7 load balancer — host/path routing to targets (containers, EC2, IP, even Lambda) — priced per hour + capacity units, far cheaper at high sustained volume, the natural fit for containerized/EKS HTTP services, but it lacks API-management features (no per-client quotas, no built-in API keys, thinner auth). Going direct (NLB or straight to the service) is for raw performance without L7 features.

The ‘ALB has no auth’ line is dated: an ALB can authenticate at the listener via native OIDC/Cognito actions and can target Lambda too — so for simple user login in front of containers it may suffice without API Gateway. The decision still turns on cost shape: API Gateway is roughly per-request (so it climbs with volume), while an ALB is per-hour plus capacity units (cheap at high sustained throughput) — so at very high RPS the ALB usually wins on cost, and at low-moderate volume with rich API-management needs, API Gateway does.

My rule of thumb: API Gateway when I need API-management features (partner APIs with quotas, request validation, usage plans), serverless/Lambda backends, or low-moderate traffic; ALB when I'm fronting containerized services on EKS/ECS, need cheap L7 routing at high sustained volume, and don't need API management (the EKS Ingress→ALB path); NLB/direct for ultra-low-latency L4. And they compose — I've fronted an ALB with API Gateway, or put CloudFront/WAF in front of either. The axes are cost-at-scale (per-request vs per-hour), feature set (API management vs plain routing), and backend (Lambda vs containers). Reaching for API Gateway reflexively at high volume is a costly mistake; so is using an ALB when you actually need per-client quotas.

Check yourself A team defaults to API Gateway in front of an EKS service doing sustained tens of thousands of requests per second, with no need for per-client quotas or API keys. What’s the likely problem and the better fit? API Gateway’s roughly per-request pricing makes it expensive at that sustained volume, for API-management features they don’t use. An ALB (per-hour + capacity units) is far cheaper at high throughput, is the natural EKS Ingress target, and — if they just need user login — can even do OIDC/Cognito auth at the listener. Reserve API Gateway for where its quotas/keys/validation actually earn their per-request cost.

29API GW · advanced

A WebSocket API keeps a connection open

Why they ask WebSocket APIs invert the request/response model API Gateway is known for — a clean test of whether you understand stateful, server-push connections at the managed edge.

Analogy REST is posting letters, each one self-contained; a WebSocket is an open phone line the gateway holds for you, handing you a connection ID so you can ring that specific caller back later — without them asking first.

A WebSocket API maintains a persistent, bidirectional connection, and API Gateway routes messages (not URL paths) to backends via route selection: built-in $connect and $disconnect routes fire when a client joins or leaves, $default catches unmatched messages, and custom routes dispatch on a field in the message body (for example an action field). Each connection gets a connectionId, which you typically store (in DynamoDB) on $connect and remove on $disconnect.

The key inversion is server push: to send a message to a client, the backend calls the @connections management API — PostToConnection — with that connectionId, so the server initiates, not the client. API Gateway holds the many open sockets so your backend (often Lambda) stays stateless and event-driven; it bills per message plus connection-minutes, and idle/duration limits apply — connections aren’t infinite.

I choose a WebSocket API when I genuinely need server-initiated push or low-latency bidirectional flow — live dashboards, chat, notifications — and I design around its statefulness: persist connectionIds in DynamoDB keyed for fan-out, and handle the fact that $disconnect is not guaranteed to fire (so TTL-expire stale connections). The honest alternative I’d weigh is whether plain request/response with polling, Server-Sent Events, or AppSync subscriptions fits better, since WebSockets add real connection-state and limits. It’s the same managed-edge concerns — auth on $connect, throttling — as REST/HTTP APIs, applied to a long-lived socket instead of a one-shot request.

Check yourself In an API Gateway WebSocket API, how does the server send an unsolicited message to one connected client, and what state must you manage for fan-out? The backend calls the @connections management API — PostToConnection — with the target’s connectionId, so the server initiates the push. You must persist connectionIds (typically in DynamoDB) as clients connect and remove/expire them on $disconnect — which may not always fire, so add a TTL — then iterate those IDs to fan a message out to many clients.

Service 06 — Distributing traffic

AWS Load Balancers

ALB, NLB, and Gateway LB for three layers of need. The routing model, the type choice, the health-check-and-drain mechanics behind zero-downtime deploys, and the fact that an ELB is a DNS-fronted fleet, not a box.

30ELB · core

A request hits an ALB (L7)

Why it mattersThe ALB is the workhorse L7 balancer — its routing model is bread-and-butter.

Analogy A multilingual front-desk clerk who opens every letter (terminates TLS), reads who it’s for and routes it (host/path rules), and keeps a line open to the back office — but if the clerk holds the office line longer than the office keeps it, the next handoff drops.

An Application Load Balancer works at layer 7 (HTTP/HTTPS). A request arrives at a listener (a port, e.g. 443, terminating TLS with an ACM certificate). The listener has rules evaluated in order that route by host header, path, HTTP method, headers, or query string — so /api/* goes to one target group, app.example.com to another. A target group is a set of backends (EC2, IP targets like pods, or Lambda) with a health check; the ALB only sends traffic to healthy targets, load-balancing across them (round-robin or least-outstanding-requests). It supports sticky sessions, redirects, and fixed responses at the LB itself.

The classic ALB production bug: the ALB has an idle timeout (default 60s) and reuses keep-alive connections to targets — if the backend’s keep-alive is shorter than the ALB’s idle timeout, the backend closes a connection the ALB still thinks is good, and the next request on it returns an intermittent 502. The fix is to set the backend keep-alive longer than the ALB idle timeout. Note too the ALB speaks HTTP/2 to clients but HTTP/1.1 to targets.

The ALB is my default for HTTP services because L7 awareness lets one load balancer front many services via host/path rules (consolidating cost and TLS), integrate ACM for managed certs, and route intelligently — and on EKS it's what the Ingress provisions, registering pod IPs directly as targets. The pieces I design: listener + rules for routing, target groups per service with meaningful health checks (hit a real readiness endpoint, not just a TCP port — echoing the k8s readiness lesson), and TLS termination with ACM. Content-based routing at L7 is the ALB's superpower; when I don't need it (raw TCP, extreme performance, static IP), that's when I drop to NLB.

Check yourself An app behind an ALB throws sporadic 502s under normal load with nothing wrong in the app logs. What connection-level mismatch should you check first? The backend’s keep-alive / idle timeout is shorter than the ALB’s idle timeout (default 60s): the backend closes a pooled connection the ALB still intends to reuse, so the next request on it fails as a 502. Set the backend keep-alive greater than the ALB idle timeout so the ALB, not the backend, decides when to close.

31ELB · core

NLB vs ALB vs Gateway Load Balancer

Why it mattersChoosing the right load balancer type is a fundamental design decision.

Analogy Three couriers: one reads the address on the envelope and sorts by content (ALB/L7), one just forwards sealed boxes at blistering speed with a fixed depot address (NLB/L4), and one secretly routes everything past an inspector first (Gateway LB).

Three types for three layers. The ALB (L7) does HTTP-aware routing (host/path), TLS, WebSockets — for web/API traffic. The Network Load Balancer (L4, TCP/UDP) operates at the connection level for ultra-low latency and extreme throughput (millions of requests/sec), can have a static IP / Elastic IP per AZ (useful when clients must allow-list a fixed IP), and preserves the client source IP — for high-performance, non-HTTP, or IP-sensitive workloads. The Gateway Load Balancer (L3/4) is specialized: it transparently inserts third-party network appliances (firewalls, IDS/IPS) into the traffic path using GENEVE. So: ALB for HTTP features, NLB for L4 speed/static-IP/source-IP, GWLB for security appliances.

Two modern facts shift old advice. NLBs now support security groups (added 2023) — previously a reason people put an ALB in front — so you can firewall an NLB directly. And watch the client-IP-preservation hairpin: with source-IP preservation on, a target behind the NLB can’t reach the NLB’s own endpoint from the same instance (the loopback breaks). The composite pattern worth naming is ALB-behind-NLB: an NLB for a static/Elastic IP in front of an ALB for L7 routing, getting both.

I pick by what the traffic needs. HTTP with routing/TLS/host-path → ALB (the common case). Raw TCP/UDP, a static IP for allow-listing, the real client IP, or millions of connections at lowest latency → NLB. Inserting inline security appliances → GWLB. On EKS this maps directly: Ingress → ALB (L7), Service type LoadBalancer → NLB (L4). A subtle interview-worthy point: NLB preserves the source IP and gives a stable IP, which ALB doesn't (ALB IPs change and it replaces the source IP with its own, so you rely on X-Forwarded-For) — so IP-sensitive or allow-list scenarios push you to NLB. Matching LB type to the actual requirement is the decision.

Check yourself A client must allow-list a single static IP and you need host/path (L7) routing. Neither NLB nor ALB alone gives both — what do you do? Put an NLB in front of an ALB: the NLB provides the static/Elastic IP the client allow-lists (ALB IPs change), and it forwards to the ALB as its target, which then does the L7 host/path routing. You get a fixed entry IP plus full layer-7 features — the standard ALB-behind-NLB composition.

32ELB · advanced

Health checks & connection draining

Why it mattersThese are the exact mechanics behind zero-downtime deploys and graceful scaling.

Analogy A maitre d’ who stops seating new diners at a table that’s being cleared but lets the current guests finish their meal (draining) — and whether waiters serve tables in other rooms for free, or you pay a surcharge to send them across, depends on which restaurant you’re in.

A load balancer continuously health-checks each target and only routes to healthy ones — a target that fails is pulled out automatically. When a target is deregistered (a deploy, a scale-in, an instance leaving), connection draining / deregistration delay kicks in: the LB stops sending new connections but lets in-flight requests finish for a configured window before fully removing it — so you don't sever active requests. Cross-zone load balancing spreads traffic evenly across targets in all AZs. Sticky sessions pin a client to one target when needed. Health-check tuning (interval, threshold, path) decides how fast a bad target is detected and a recovering one re-added.

A cost/behaviour asymmetry people miss: cross-zone load balancing is ON and free on an ALB, but OFF by default on an NLB — and enabling it on an NLB incurs inter-AZ data-transfer charges, so with it off a zone with few targets can get hot-spotted. The other knob worth naming is slow start: ramp traffic gradually to a newly-healthy target over a window so a cold instance (empty caches, JIT warm-up) isn’t slammed the instant it passes its health check.

These are the same zero-downtime primitives as the Kubernetes rolling-update story, one layer down — health checks so traffic only goes to ready targets, and deregistration delay so removing a target drains gracefully instead of dropping requests. On EKS the ALB/NLB (via the Load Balancer Controller) does exactly this against pod-IP targets, which is why a rolling deploy is smooth: new pods pass health checks before receiving traffic, old pods drain before deregistering. I set the health check to a real readiness endpoint (not a shallow TCP check that says "up" while the app can't serve), tune the deregistration delay to my longest request, and use cross-zone balancing for even load. Health checks + draining are the mechanism that makes deploys and autoscaling invisible to users.

Check yourself On an NLB with uneven targets per AZ, one zone’s few targets are overloaded while another zone’s sit idle. What default explains it, and what’s the trade to fix it? Cross-zone load balancing is off by default on NLBs, so each LB node spreads traffic only across targets in its own AZ — a zone with fewer targets gets hot-spotted. Enabling cross-zone balances them, but introduces inter-AZ data-transfer charges, so it’s a cost-vs-evenness trade (whereas on an ALB cross-zone is always on and free).

33ELB · advanced

The load balancer scales and fails over

Why it mattersUnderstanding the LB as a distributed, DNS-fronted fleet explains its behavior and its limits.

Analogy The load balancer isn’t a building you can pin to a map — it’s a phone number (DNS) that rings whichever of a shifting pool of operators is on duty, which is exactly why you can pull a whole broken call-centre offline without anyone redialing.

An ELB isn't a single box — it's a managed, distributed fleet of load-balancer nodes spread across the AZs you enable, and AWS scales that fleet up and down with your traffic automatically. Critically, you're given a DNS name, not a fixed IP (for the ALB), because the underlying nodes and their IPs change as the fleet scales — so clients always resolve the name fresh (via Route 53 / DNS with a low TTL), and that indirection is what lets AWS grow, shrink, and replace nodes transparently. It's multi-AZ for availability. The one caveat: scaling the fleet takes a little time, so a sudden, massive spike (a flash sale, a load test from zero) can briefly outpace it — historically you'd request pre-warming; NLBs handle sudden spikes far better than ALBs.

This is why the LB gives you a DNS name resolving to one IP per enabled AZ node — clients should honour all returned addresses, not pin one. Two practical levers: an NLB has a static IP per AZ, so it doesn’t need pre-warming the way an ALB’s shifting fleet does; and Route 53 ARC zonal shift lets you deliberately evacuate a single impaired AZ by pulling that AZ’s LB IP out of DNS — a one-click ‘drain this zone’ for grey failures, without a full regional failover.

The mental model to state is "an ELB is a horizontally-scaled fleet behind a DNS name, not an IP" — which explains why you never hardcode its IP (it changes), why you reach it via a Route 53 alias record (next track), and why it's inherently multi-AZ and self-scaling. The practical implications: for anticipated sudden spikes I either warm up the ALB, use an NLB (scales to sudden load better, gives a static IP), or pre-scale; and I enable all relevant AZs so the fleet is spread. This ties the load-balancer and DNS stories together — the LB's DNS name is exactly what a Route 53 alias points at, and the DNS indirection is fundamental to how the LB stays elastic.

Check yourself One AZ is having a grey failure (slow, not dead) and the LB nodes there are still serving degraded traffic. How can you pull just that AZ out quickly, short of a region failover? Use a Route 53 ARC zonal shift: it temporarily removes the impaired AZ’s load-balancer IP from DNS, so new connections steer to the healthy AZs’ nodes — a fast, targeted ‘evacuate this zone’ for grey failures the health checks don’t cleanly catch, without failing the whole region over.

34ELB · advanced

TLS is terminated at the load balancer (SNI & mTLS)

Why they ask Where TLS ends, how one listener serves many certs, and whether the client is authenticated are everyday ALB security decisions the basic ‘the listener terminates TLS’ answer skips.

Analogy One receptionist (a single HTTPS listener) fronting many companies: the visitor states which company they’re here for as they arrive (the SNI hostname) and the receptionist presents that company’s badge — and on high-security floors, also checks the visitor’s own ID (mTLS).

An ALB listener on 443 terminates TLS: it decrypts so it can read L7 (host/path) to route, then opens a connection to the target — re-encrypting to the backend if that target group uses HTTPS (end-to-end), or sending plain HTTP inside the VPC (terminate-at-edge). Because termination needs a certificate and one listener fronts many hostnames, the ALB uses SNI: the client puts the hostname in the TLS ClientHello, and the ALB selects the matching certificate from several attached to the listener — so one listener serves a.example.com and b.example.com with different certs.

A security policy on the listener pins the allowed TLS versions and cipher suites (how you drop TLS 1.0/1.1). And the ALB supports mutual TLS (mTLS): it can require and verify a client certificate against a trust store (a CA bundle in S3) at the edge, then pass the validated client-cert details to the backend — so device/service client authentication happens at the load balancer, not re-implemented in every app.

My default is terminate TLS at the ALB with an ACM certificate (auto-renewed, never exported) and route at L7; I re-encrypt to targets only when compliance or in-VPC zero-trust requires true end-to-end, accepting the extra handshake cost. SNI is what lets me consolidate many HTTPS sites behind one ALB (cost, and one place for certs), and I set a modern security policy to enforce TLS 1.2+/1.3. mTLS at the ALB is the clean way to do service/device client-cert auth without burdening backends — the LB verifies against the trust store and forwards the identity. ‘Where does TLS end, which cert, which TLS versions, and is the client authenticated’ is the four-part answer I’d give, versus just ‘it terminates TLS’.

Check yourself One ALB listener on port 443 serves three different domains, each with its own certificate. What TLS mechanism makes that possible on a single listener, and how does the ALB pick the right cert? SNI (Server Name Indication): the client includes the target hostname in the TLS ClientHello before the handshake completes, so the ALB reads it and selects the matching certificate from the multiple certs attached to that one listener — letting a single listener (and IP) serve many HTTPS domains with distinct certs.

35Route 53 · core

A name is resolved via Route 53

Why it mattersRoute 53 as authoritative DNS is the entry point to every AWS-hosted app.

Analogy A phone directory that can give different numbers to insiders and the public for the same name (split-horizon), and — via special operators — can even look up numbers in your old on-prem phone book when asked from inside the building.

Route 53 is AWS's DNS service, acting as the authoritative nameserver for your domain. You create a hosted zone (public, internet-facing, or private, resolvable only inside your VPCs) and add records — A/AAAA, CNAME, MX, TXT, and AWS's special alias records. When someone resolves your domain, the recursive resolver walks to Route 53 as the authoritative source (the same DNS hierarchy from the platform volume — root → TLD → Route 53), which returns the answer with a TTL. Route 53 runs on a global anycast network so queries hit a nearby edge and it's highly available. It also does domain registration and health checks.

Two capabilities the base answer skips. Split-horizon DNS: a private hosted zone with the same name as a public one shadows it inside the VPC, so internal clients get internal addresses while the world gets the public ones. And Route 53 Resolver endpoints bridge hybrid DNS — an inbound endpoint lets on-prem resolve AWS private names, an outbound endpoint plus forwarding rules lets VPC workloads resolve on-prem names. (The in-VPC resolver itself lives at the VPC CIDR base +2.)

I place Route 53 as the authoritative half of the DNS story from the platform networking volume — it's where the domain's truth lives, and every request to your app starts by resolving a name here. The AWS-specific superpowers are the alias record and the routing policies that turn DNS into a traffic-management layer, not just a lookup. For a private hosted zone, it's also internal service discovery inside a VPC. The two knobs I always think about: TTL (how long resolvers cache, trading propagation speed against query volume — the same TTL lesson, and it governs how fast DNS-based failover takes effect) and whether a zone is public or private. Route 53 is where global traffic routing begins.

Check yourself Inside the VPC, api.example.com must resolve to a private ALB, but public internet users of the same name must reach a public endpoint. How do you serve both from one name? Split-horizon DNS: create a private hosted zone for example.com associated with the VPC, with api.example.com pointing at the private ALB, alongside the public hosted zone with the public record. Inside the VPC the private zone wins (resolvers see the private answer); outside, only the public zone is visible — one name, two answers by vantage point.

36Route 53 · advanced

Routing policies (traffic management)

Why it mattersRoute 53's routing policies are how DNS becomes a global traffic-steering tool.

Analogy A smart switchboard that can route calls by coin-flip percentages (weighted), by who answers fastest (latency), by the caller’s country (geolocation), or straight to the backup line when the main goes dead (failover) — and you can stack these rules.

Beyond simple name→IP, Route 53 offers routing policies deciding which answer to return per query. Simple (one record). Weighted (split traffic by percentage across records — for canary/blue-green or A/B, send 10% to the new stack). Latency-based (return the endpoint in the region with lowest latency to the user — global apps). Geolocation (answer by the user's continent/country — compliance/localization) and geoproximity (by distance, with bias). Failover (return the primary, or the secondary if the primary's health check fails — active-passive DR). Multivalue (return several healthy records for simple client-side load balancing). You can nest them (geolocation, then weighted within a region).

A few sharp edges: latency-based routing uses AWS’s own measured latency tables between regions and resolver locations — not live geographic distance — so it can route in ways that look odd but reflect real network latency, and the tables update over time. Set a record’s weight to 0 to drain it (and if all weights are 0, Route 53 returns them all). The newer IP-based routing steers by client CIDR (useful for ISP/known-network steering), and remember multivalue is not a load balancer — it has no latency or proximity awareness, just returns several healthy answers.

Routing policies turn Route 53 from a phone book into a global load balancer and deployment tool. Weighted routing is how I do DNS-level blue-green/canary across whole stacks or regions (shift a percentage, watch, promote) — the coarse-grained cousin of the ALB/canary story. Latency-based sends each user to their nearest region. Geolocation handles data-residency/compliance ("EU users must hit the EU stack"). Failover plus health checks is the mechanism for active-passive DR. And they compose — latency to pick a region, then weighted within it for a canary. This is a core piece of multi-region architecture (ties to active-active): DNS is the outermost layer that decides which regional stack a user even reaches.

Check yourself You want to gracefully take one stack out of a weighted routing set without deleting its record or abruptly changing the others. What’s the clean move? Set that record’s weight to 0: Route 53 stops returning it (draining it from rotation) while the other weighted records keep their proportions, and you can restore it later by raising the weight again — no deletion, no re-tuning the rest. (Caveat: if you zero every weight in the set, Route 53 returns them all.)

37Route 53 · advanced

Health checks & DNS failover (the TTL caveat)

Why it mattersDNS-based failover is powerful but has a caching caveat that catches people out.

Analogy A backup generator wired to a switch that most of the building obeys — but some offices keep a copy of the old wiring diagram pinned to the wall (cached DNS) and keep flipping the dead switch long after you cut over.

Route 53 health checks monitor endpoints (an HTTP check, a TCP check, or the status of other health checks / CloudWatch alarms) from multiple global locations. Combined with failover or multivalue routing, an unhealthy endpoint is removed from DNS answers — so if your primary region's health check fails, Route 53 starts returning the secondary, achieving DNS-level failover across regions. The crucial caveat: DNS answers are cached by resolvers and clients for the record's TTL, so failover is not instant — clients that cached the old (now-dead) address keep using it until the TTL expires. So you set a low TTL on records you want to fail over quickly (say 60 seconds), trading more DNS queries for faster failover.

Three refinements. On alias records you can skip a separate health check by turning on Evaluate Target Health — the alias inherits the AWS target’s own health. For private/internal endpoints the health checkers (which are public) can’t reach them, so you use a CloudWatch-alarm health check, and calculated health checks combine children with AND/OR. And the caching caveat is worse than the record TTL implies: browsers and OS resolvers often pin DNS longer than the TTL, so real-world failover is minutes, reinforcing ‘not seconds-scale’.

DNS failover is the outermost, cross-region safety net — but I always state its limit: it's only as fast as your TTL plus how well clients honor it (some cache longer than they should), so DNS failover is minutes-scale, not seconds-scale, and it's not a substitute for in-region HA (Multi-AZ, healthy targets). So I use low TTLs (~60s) on failover-critical records and combine layers: in-region HA handles instance/AZ failure fast, and Route 53 health-checked failover handles whole-region loss more slowly. This is exactly the TTL-vs-failover tradeoff from the platform DNS scenario, now concrete — the same knob that controls propagation controls how fast you can fail over, and it's why the classic "we failed over but traffic kept hitting the dead region" incident happens: stale DNS caches.

Check yourself Your endpoint is a private internal service that Route 53’s public health checkers can’t reach. How do you still drive DNS failover on its health? Use a CloudWatch-alarm-based health check: monitor the private endpoint with a CloudWatch metric/alarm (from inside your network), and point the Route 53 health check at that alarm’s state. Route 53 then fails over based on the alarm, even though its public health checkers can’t probe the private endpoint directly.

38Route 53 · advanced

Alias records & the top of a multi-region stack

Why it mattersAlias records are an AWS-specific must-know, and Route 53 is where multi-region design begins.

Analogy A universal adapter at the top of the house that plugs your bare domain straight into AWS gear and auto-follows it as the gear’s plugs change — but if you need the lights to switch buildings in seconds, you add a direct hotline that never caches.

A CNAME maps a name to another name, but it can't be used at a zone apex (the bare domain, example.com) and costs an extra lookup. Route 53's alias record solves both: it's an AWS-specific record pointing a name directly at an AWS resource — an ALB, CloudFront distribution, S3 website, API Gateway, or another Route 53 record — including at the zone apex, and Route 53 resolves it to the resource's current IPs automatically. Alias queries to AWS resources are free, and alias records can evaluate the target's health. This is why you point your domain at an ALB with an alias (not a CNAME): it works at the apex, tracks the LB's changing IPs (recall the LB is a DNS-fronted fleet), and costs nothing.

The honest limit of this whole DNS-topped stack is speed of failover — it’s TTL-bound and client-cache-bound (minutes). When you need seconds, AWS Global Accelerator sits alongside/above Route 53: it gives two static anycast IPs at the AWS edge and shifts traffic between regional endpoints on health in seconds, independent of DNS TTLs. One alias gotcha to land: an alias to an AWS resource requires the target’s hosted-zone ID (console fills it, IaC must get it right).

The practical rule: use alias records to point at AWS resources, especially at the zone apex where CNAME can't go — it's the correct, free, apex-capable way to connect your domain to an ALB, CloudFront, or S3, and it auto-tracks the resource's IPs (essential, since an ALB's IPs change under it). Stepping back, Route 53 sits at the very top of a multi-region architecture: alias + routing policies + health checks are how a user is steered to the right regional stack and failed over when one dies — the outermost layer above the load balancers, which sit above the clusters, which sit above the data stores. It ties the whole series together, and for an active-active or DR design, Route 53 is where the global traffic decision is made.

Check yourself DNS-based failover is too slow (TTL/caching) for a workload that must shift regions in seconds. What AWS service gives near-instant regional failover, and how? AWS Global Accelerator: clients connect to two static anycast IPs at the AWS edge (so there’s nothing for resolvers to cache against failover), and Global Accelerator health-checks your regional endpoints and reroutes traffic between them in seconds — bypassing the Route 53 TTL/cache limit that makes DNS failover minutes-scale.

39Route 53 · advanced

A zone is signed with DNSSEC

Why they ask DNSSEC proves DNS answers weren’t forged — it’s a compliance ask and a chain-of-trust question that tests whether you grasp that DNS can otherwise be spoofed.

Analogy Plain DNS is an unsigned note left at a desk — anyone could have written it; DNSSEC is a tamper-evident wax seal, where each authority vouches for the next’s seal, so a forged answer (cache poisoning) is detected and thrown out.

DNS by itself has no authenticity — a resolver can be tricked into caching a forged answer (cache poisoning). DNSSEC adds cryptographic signatures: Route 53 signs the records in a hosted zone (producing RRSIG records) and publishes the public key (DNSKEY), and a validating resolver checks the signature before trusting the answer. Route 53 uses a KMS asymmetric key for the key-signing key, so the private signing key stays in KMS and never leaves.

Trust is a chain from the root down: each parent zone vouches for its child by publishing a DS (Delegation Signer) record — a hash of the child’s key — so for example.com you must add a DS record at the registrar (the .com parent) to complete the chain. That’s the operational sharp edge: DNSSEC is powerful but unforgiving — a botched key rollover or a mismatched/expired DS record makes validating resolvers reject your entire domain, a self-inflicted outage plain DNS can’t suffer.

I enable DNSSEC when there’s a real spoofing or compliance driver, and I respect that it converts a class of silent attacks into a class of loud operational risks: signing is easy, but the DS record at the registrar and key rollovers are where domains go dark, so I automate and monitor them and rehearse rollover. It protects only the resolver-to-authoritative path (integrity and authenticity of answers), not confidentiality — that’s DoH/DoT’s job — and it only helps clients behind validating resolvers. Route 53’s KMS-backed signing key keeps the private key unexportable (tying back to the envelope/asymmetric-key story), which is the part I’d highlight as done right.

Check yourself You enable DNSSEC signing in Route 53, but validating resolvers still don’t treat the zone as secure. What step is almost certainly missing, and why does getting it wrong risk an outage? The DS record at the parent — your registrar for .com — is missing: without it the chain of trust from the root to your zone is broken, so resolvers can’t validate. It’s risky because a wrong, mismatched, or expired DS (or a bad key rollover) makes validating resolvers reject all answers for the domain, taking it down for those users.
