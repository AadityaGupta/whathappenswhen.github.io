Track 01 — Under the hood

JVM & runtime

Every performance and memory conversation starts here: how bytecode becomes fast native code, how the heap is collected, why the JVM behaves inside a container, and what a cold start really costs.

01JVM

The JVM starts and runs your code

Why it mattersInterpretation → JIT is the foundation under every performance discussion.

Analogy A new cook reads each recipe step aloud at first (interpret), but the dishes ordered constantly get committed to muscle memory (JIT) — and if a memorized shortcut turns out wrong for tonight’s order, they fall back to reading the card again (deoptimize).

javac compiles source to platform-neutral bytecode. At runtime the classloaders load classes lazily on first use — bootstrap, platform, and application loaders in a delegation hierarchy — then verify, link, and initialize each (running static initializers). Execution begins in the interpreter, reading bytecode op by op.

The JVM profiles as it runs. Hot methods — called often, or loops iterating many times — are handed to the JIT. HotSpot uses tiered compilation: quick C1 first for fast warmup, then the heavily-optimizing C2 for the hottest code, using the live profile to inline, drop dead code, and speculate. If a speculation proves wrong, it deoptimizes back to the interpreter and recompiles.

One detail the warmup story hides: C2’s native output lives in a fixed-size code cache, and if it fills — common with huge apps, swarms of lambdas, or agents instrumenting everything — the JIT silently stops compiling and the whole process quietly drifts back toward interpreted speed, so watch CodeCache usage and ReservedCodeCacheSize. And a method already deep in a long loop doesn’t wait to be re-called to speed up: on-stack replacement (OSR) swaps the optimized version in mid-loop.

The practical consequences: Java is slow for the first requests and fast once warm — the warmup curve — which bites cold starts and short-lived processes; and "measure in a warm, production-like state, not the first run," which is why microbenchmarks use JMH. The bytecode layer is also why one language runs everywhere and why agents and profilers can instrument code without source.

Check yourself A long-running service that was fast for weeks gradually slows down, with no code change and no heap growth — what JVM-internal limit might be throttling it? A full code cache: once it fills, HotSpot stops JIT-compiling new or recompiled methods and they run interpreted, so throughput degrades with no heap or GC symptom; raise ReservedCodeCacheSize and monitor code-cache usage.

02JVM

A garbage collection runs

Why it mattersGC pauses and heap tuning are the core of JVM performance work.

Analogy A city that sweeps its crowded young districts constantly (minor GC) but the quiet old quarter only rarely: most residents move out almost as soon as they arrive, so cleaning the nursery often and the retirement home seldom is simply where the garbage actually is.

Objects are allocated cheaply by bumping a pointer in a thread-local allocation buffer. The heap is generational, on the weak-generational hypothesis that most objects die young. New objects go in the young gen (Eden); a minor GC copies the few survivors, and objects that survive enough collections are promoted to the old gen, collected less often. GC finds live objects by tracing references from GC roots (stacks, statics) — anything unreachable is garbage.

The cost is pause time. Classic collectors stop the world while they work. G1, the default, splits the heap into regions and targets a pause goal, doing much of the work concurrently. ZGC (generational in 21) and Shenandoah keep pauses sub-millisecond by doing nearly all work concurrently, trading some throughput and CPU.

Two things the textbook version skips. GC isn’t on a timer — it fires on allocation failure, when Eden can’t satisfy a request, so your allocation rate sets GC frequency. And in G1 an object larger than half a region is a humongous object, allocated straight into old-gen across contiguous regions; a flood of them (big byte arrays, large strings) fragments the heap and forces expensive full GCs even when it looks half-empty. Even ‘concurrent’ collectors like ZGC keep brief stop-the-world pauses for root scanning — concurrent means mostly, not zero.

I pick the collector by the goal — G1 for balanced throughput and latency, ZGC when tail latency matters on large heaps. Tuning is mostly sizing the heap and generations while watching allocation rate: high allocation churn is the usual cause of frequent GC, so the real fix is often to allocate less, not to enlarge the heap. Read GC logs and allocation profiles, don't guess.

Check yourself Your service allocates many large byte arrays and suffers surprise full-GC pauses on G1 though the heap looks half-empty — what G1-specific cause fits? Humongous allocations — arrays bigger than half a G1 region go into special humongous regions, and enough of them fragment the heap and trigger full GCs despite apparent free space; shrink the objects or raise G1HeapRegionSize so they’re no longer humongous.

03JVM

You hit an OutOfMemoryError

Why it mattersKnowing which region blew up, and how to diagnose it, separates seniors from guessers.

Analogy An alarm that names the floor on fire: ‘heap’, ‘metaspace’, ‘unable to create native thread’ — the first job is always to read which memory ran out, not to blindly enlarge everything and hope.

OOME isn't one thing — the message names the region. "Java heap space" means live objects exceeded the max heap: either a genuine leak (a growing static map, an unbounded cache, unclosed resources) or an undersized heap for the load. "Metaspace" means class metadata filled — too many generated classes, or classloader leaks from redeploys that never release loaders. "unable to create native thread" is an OS thread/memory limit. "Direct buffer memory" is off-heap NIO.

To diagnose the heap: capture a heap dump (automatically with -XX:+HeapDumpOnOutOfMemoryError), open it in a tool like Eclipse MAT, and follow the dominator tree and the GC-root reference chain that's retaining the leak.

A subtlety: you often hit GC overhead limit exceeded before true exhaustion — the JVM gives up when it spends over 98% of time in GC reclaiming under 2% of the heap, a tell that the heap is full, not merely slow. And an OutOfMemoryError can strike any thread at any point — one may die mid-update holding a lock — leaving the JVM in an unpredictable state, which is why the production-safe move is usually not to catch it but to fail fast with -XX:+ExitOnOutOfMemoryError, paired with +HeapDumpOnOutOfMemoryError for the postmortem.

OOME is a symptom, so I distinguish leak from under-provisioning by the heap-usage trend: a leak shows a sawtooth that ratchets upward and never falls back after GC. Bounded caches with eviction, try-with-resources, and container-aware heap limits prevent most of it. And the container angle from the platform side: the heap must be set below the container memory limit, or the kernel OOM-kills the process before the JVM can even throw the error.

Check yourself Should application code ever catch (OutOfMemoryError e) and try to carry on — why or why not? Almost never: it can fire on any thread mid-operation (possibly holding a lock or leaving state half-written), so the JVM’s integrity is suspect; the safe pattern is to dump the heap and exit (-XX:+ExitOnOutOfMemoryError), letting the orchestrator replace the pod cleanly rather than limp on in a corrupted state.

04JVM

The JVM runs inside a container

Why it mattersCgroup awareness is a production must-know — it's where the JVM meets Kubernetes limits.

Analogy A guest sizing their appetite to the whole restaurant’s kitchen rather than the small plate they ordered — help yourself as if the full buffet were yours inside a 1-CPU, 512-MB box and the manager (the kernel) throws you out.

Modern JVMs, with -XX:+UseContainerSupport (on by default), read the cgroup limits rather than the host's resources. Memory sizing keys off the cgroup memory limit — and by default the JVM only takes a fraction of it (about 25% via MaxRAMPercentage) unless you raise it. CPU is subtler: Runtime.availableProcessors() reflects the cgroup CPU quota, and that number drives GC thread counts, the ForkJoinPool common pool size, and default thread pools — so a container capped at one CPU sees far fewer processors than the node has.

Two sharp edges. MaxRAMPercentage caps only the heap — metaspace, thread stacks (~1 MB each × thread count), direct buffers and the code cache live outside it, so a heap set to 75% of the limit still gets OOM-killed once non-heap grows; account for it with Native Memory Tracking (-XX:NativeMemoryTracking). And CPU detection is fragile: availableProcessors() reads the cgroup quota, but with CPU shares (not quota) or an old JDK misreading cgroup v2 it can be wrong — override deliberately with -XX:ActiveProcessorCount.

The classic incident is a pod OOM-killed by Kubernetes because the JVM sized its heap off the host, not the limit — fixed with UseContainerSupport plus a deliberate MaxRAMPercentage, leaving headroom for non-heap: metaspace, thread stacks, direct buffers, code cache. And a tight CPU quota silently shrinks GC and pool parallelism and can cause CFS throttling stalls, so I size CPU requests and limits knowing the JVM reacts to them. This is exactly where the Java runtime and the k8s resource model meet.

Check yourself You set -XX:MaxRAMPercentage=75 on a 1 GB container and still get OOM-killed by Kubernetes with the heap well under 750 MB — what’s eating the rest? Non-heap memory — metaspace, per-thread stacks (× thread count), direct/NIO buffers and the JIT code cache — all sit outside the heap cap, so 75% heap plus growing off-heap exceeds the cgroup limit and the kernel kills the process; leave headroom (lower the percentage) and measure with Native Memory Tracking.

05JVM

A cold JVM warms up (or you go native)

Why it mattersCold-start latency drives serverless, autoscaling, and scale-to-zero decisions.

Analogy An athlete who needs a warm-up lap before top speed: fine for a long race, murder for a 100-metre sprint that’s over before they’re loose — so for sprints (serverless, scale-to-zero) you either keep them jogging or swap in a robot that’s fast from the gun (native image).

Fresh code runs interpreted, then C1-compiled, and only the hottest paths reach C2 after enough profiling — so the first requests are markedly slower and latency settles as it warms. That's fine for long-running services but painful for scale-to-zero, serverless, or frequently-restarted pods that may die before they're warm.

The options: keep instances warm or pre-warm with synthetic traffic; AppCDS to share and speed class loading; CRaC to checkpoint an already-warm JVM and restore in milliseconds; or GraalVM native image, which ahead-of-time compiles to a native binary with near-instant startup and low memory — at the cost of no JIT peak throughput, closed-world assumptions (reflection and proxies must be declared, which Spring Boot AOT largely handles), and longer builds.

The ‘native gives up peak throughput’ claim is softening: profile-guided optimization (PGO) feeds a representative run’s profile back into the native build, narrowing the gap to C2 on hot paths. The closed-world reflection pain is easing too, via the GraalVM reachability-metadata repository that ships config for common libraries. And watch Project Leyden, which is bringing AOT caches to the standard JVM — a middle path that front-loads warmup without going fully native.

It's a throughput-versus-startup trade. For steady high-throughput services I keep the JIT for peak performance; for spiky autoscaling, functions, or CLIs I reach for native image or CRaC to kill cold-start latency. Spring Boot 3's AOT processing makes the native path realistic, but I validate the reflection/closed-world constraints early, because they bite late.

Check yourself A latency-sensitive, bursty function cold-starts too slowly on the JVM, but you also can’t absorb native image’s throughput and build-time costs — what intermediate options exist? CRaC (checkpoint a warmed JVM, restore in milliseconds), AppCDS/AOT caches and emerging Project Leyden front-load class loading and warmup while keeping the JIT, and PGO can recover much of native image’s lost peak throughput — so you’re not forced to choose startup or throughput outright.

06JVM

Classes load, and metaspace fills

Why they ask Classloader isolation and metaspace leaks are where redeploys, plugins, and ‘why are there two of the same class’ bugs come from.

Analogy Librarians in a strict chain of command: a request for a book goes up to the head librarian first (parent-first delegation), and only if no senior has it does a junior fetch it — which is exactly why nobody can smuggle in a counterfeit core-Java class.

Classes load lazily on first use through a chain of classloaders — bootstrap, platform, application — using parent-first delegation: a loader asks its parent before trying itself, so core java.* classes always come from the trusted bootstrap loader and can’t be spoofed. A class’s identity is the pair (fully-qualified name, defining classloader), so the same bytecode loaded by two different loaders yields two incompatible types — the root of a baffling ClassCastException: Foo cannot be cast to Foo and of every plugin-isolation design.

The metadata for every loaded class — its methods, fields, constant pool — lives in metaspace, which is native (off-heap) memory, unbounded by default unless you set -XX:MaxMetaspaceSize. Metaspace is reclaimed only when a whole classloader becomes unreachable, which is why the classic leak is a repeated hot-redeploy (or a framework spinning up new loaders) that never releases the old ones: class count and native memory climb until OutOfMemoryError: Metaspace.

The model I bring: classloaders are both an isolation mechanism (app servers, OSGi, plugins each get their own so versions don’t collide) and a leak mechanism (a lingering reference — a thread-local, a JDBC driver registered in a parent, a stray static — pins an entire loader and all its classes). I diagnose metaspace leaks by watching loaded-class and classloader counts across redeploys, and I always set MaxMetaspaceSize so a leak fails fast instead of starving the host. It’s also why native image’s closed world — no dynamic class loading — both constrains and simplifies.

Check yourself After several hot redeploys without restarting, a dev server dies with OutOfMemoryError: Metaspace though the heap is fine — what’s the mechanism? Each redeploy creates a new classloader for the app’s classes, and something (a thread-local, a registered driver or shutdown hook, a static referencing an old instance) keeps the previous loader reachable, so its classes’ metadata is never unloaded; metaspace (native memory) grows per redeploy until it’s exhausted — a classloader leak, not a heap leak.

Track 02 — Threads & memory model

Concurrency in Java 21+

The area Java 21 changed most. Virtual threads and structured concurrency, plus the evergreen correctness questions — the memory model, locks, and pool saturation — that a senior is still expected to reason about precisely.

07Concurrency

You run a task on a virtual thread

Why it mattersThe headline Java 21 feature — it reshapes how you scale I/O-bound work.

Analogy A few permanent desks (carrier threads) but millions of freelancers (virtual threads) who only occupy a desk while actually typing — the moment one waits on a phone call (I/O) they vacate the desk for someone else, so a waiting freelancer costs almost nothing.

A virtual thread is scheduled by the JVM, not the OS. You have a small pool of OS threads — carrier threads, a ForkJoinPool — and can have millions of virtual threads. When a virtual thread runs it's mounted on a carrier; when it hits a blocking operation the JDK has instrumented — blocking I/O, a lock, sleep — it unmounts, its stack is parked on the heap, and the carrier is freed to run another. When the I/O completes it remounts and resumes. So blocking a virtual thread is cheap: it doesn't hold an OS thread.

The gotcha is pinning: if a virtual thread blocks inside a synchronized block or a native/foreign call, it can't unmount and it pins its carrier, cutting throughput. The classic fix is ReentrantLock instead of synchronized around blocking sections. (Recent JDKs have largely removed synchronized pinning, but it's still the thing to check.)

Two things to carry beyond ‘blocking is cheap now.’ With millions of them, ThreadLocals become a memory hazard — a few KB each × millions — so prefer scoped values for per-task context. And because you no longer pool (one virtual thread per task), the way you bound load on a fragile downstream is a Semaphore around the call, not a small thread pool. To hunt pinning in production, enable the JFR event jdk.VirtualThreadPinned rather than guessing.

Virtual threads make the simple, readable thread-per-request blocking style scale to huge concurrency for I/O-bound work — async-like scalability without async's callback complexity. In Spring Boot 3.2+ it's a flag, spring.threads.virtual.enabled=true. I stress: they help I/O-bound, not CPU-bound work; don't pool them (create one per task); and watch for pinning and for unbounded concurrency overwhelming a downstream — you still need limits.

Check yourself If you don’t pool virtual threads, how do you stop a million of them from hammering a downstream that can only handle 50 concurrent calls? Bound the concurrency, not the threads — a Semaphore (or a rate limiter) with ~50 permits around the downstream call lets you still create one virtual thread per task while capping how many hit the dependency at once; the blocked virtual threads cost almost nothing while they wait for a permit.

08Concurrency

A thread blocks on I/O

Why it mattersIt's the "why does thread-per-request hit a ceiling" question that motivates both Loom and reactive.

Analogy A call centre where every agent handles one customer start to finish, including the long holds while the customer digs for their account number — agents sit idle on hold, so you run out of agents long before anyone is actually busy.

A platform thread is a thin wrapper over an OS thread, and each one costs real memory — a stack, around 1 MB by default — plus scheduling overhead. In the classic thread-per-request model, a request that calls a database or another service blocks its thread while it waits: the thread sits idle, holding memory, doing nothing. Under high concurrency with slow downstreams you run out of threads (or memory) long before you run out of CPU — you're blocked, not busy — and adding threads eventually costs more in context-switching and memory than it buys.

The two escapes: go non-blocking/reactive, where a small event-loop pool never blocks and work is driven by callbacks; or use virtual threads, where blocking is cheap because the OS thread is released during the wait.

Put numbers on it: each platform thread’s ~1 MB stack means a few thousand is the practical ceiling before memory and scheduler overhead dominate — versus millions of virtual threads. Little’s Law makes the demand concrete: threads needed ≈ request rate × average latency, so a downstream that slows from 50 ms to 500 ms needs 10× the threads for the same throughput — exactly when a fixed pool tips over. Shrinking -Xss buys a few more threads but courts StackOverflowError, so it’s a weak lever.

The model I bring: for I/O-bound work, thread count — not CPU — is the scaling ceiling in the blocking model. That single fact explains why we historically tuned huge thread pools, why WebFlux emerged, and why virtual threads are such a big deal: they keep the simple blocking code and remove the ceiling. I choose by the workload's blocking profile, not by fashion.

Check yourself A thread-per-request service handles 1,000 req/s fine until a downstream slows from 50 ms to 500 ms, then it falls over — why, in one law? Little’s Law: concurrent in-flight requests ≈ rate × latency, so 1,000/s × 0.5 s = 500 threads busy instead of 50 — a 10× jump that exhausts a fixed pool even though CPU is idle; the requests are blocked, not busy, which is the ceiling virtual threads remove.

09Concurrency

You use structured concurrency

Why it mattersJava 21's answer to leaked, orphaned subtasks — and a signal of modern-Java fluency.

Analogy A parent at a fair under one rule: no child leaves until all are back, and if one gets lost everyone regroups at once — no kid wanders off to find their own way home (an orphaned task), and one scraped knee ends the outing for all.

Structured concurrency (a preview API in 21, via StructuredTaskScope) treats a group of concurrent subtasks as one unit of work with a clear scope. You open a scope, fork several subtasks (each on its own virtual thread), then join — and the scope guarantees all subtasks complete or are cancelled before you leave it. A policy like ShutdownOnFailure cancels the siblings the moment one fails and propagates the error; ShutdownOnSuccess returns the first success and cancels the rest. Scoped values pass immutable context down into subtasks efficiently, replacing thread-locals for that job.

Heads-up on the API, which is still settling: later JDKs (24/25) replaced the subclass style (new StructuredTaskScope.ShutdownOnFailure()) with a factory — StructuredTaskScope.open(Joiner.allSuccessfulOrThrow()) — so pin your examples to the JDK you’re on. The quietly huge payoff is observability: because the scope makes the parent’s relationship to its forked subtasks explicit, a thread dump shows the task tree, so you can finally see which subtask is stuck — impossible with a flat pile of executor threads.

It fixes the classic mess of manual executors — orphaned tasks that outlive their request, error handling that loses one failure while awaiting another, cancellation that doesn't propagate. Concurrent code reads like structured sequential code: the subtasks' lifetime is bounded by the enclosing block, so no leaks and clean cancellation. It pairs naturally with virtual threads (cheap to fork many). I'd note it's still stabilizing across JDK versions, so confirm the API level, but the direction — bounded, observable, cancellable task trees — is clear.

Check yourself Beyond cancellation, what operational advantage does structured concurrency give over submitting the same subtasks to a shared ExecutorService? Observability and bounded lifetime: the scope records the parent→child relationship, so a thread dump shows the real task hierarchy (which subtask of which request is blocked), and every subtask is guaranteed to finish or be cancelled before the enclosing block exits — no orphans outliving the request, unlike an opaque shared executor.

10Concurrency

Two threads race on shared state

Why it mattersThe Java Memory Model question — this is correctness, not just speed.

Analogy Two people editing a shared doc from separate caches: one scribbles a change on their private copy and the other simply never sees it (visibility), or both grab the running total, add to it, and save — clobbering each other’s increment (atomicity). Different bugs, different fixes.

Two hazards, and people conflate them. A race on a compound action — check-then-act, or a read-modify-write like i++ — can interleave and corrupt state: an atomicity problem. Separately there's visibility: without synchronization, one thread's write to a field may never be seen by another, because the JMM lets values sit in CPU caches/registers and lets the compiler reorder. So a thread can loop forever on a flag another "set."

The Java Memory Model defines happens-before: certain actions establish an ordering that guarantees visibility. volatile makes a field's writes visible to later reads and blocks reordering around it (but doesn't make compound ops atomic). synchronized and locks give both mutual exclusion and happens-before. For lock-free atomicity there are atomics — AtomicInteger, VarHandle — built on CAS.

Two canonical consequences the answer leaves implicit. Double-checked locking — the classic lazy singleton — is broken without a volatile field, because another thread can see a non-null reference to a half-constructed object (writes reordered). Conversely, the JMM’s final-field guarantee lets you publish an immutable object safely with no synchronization: once a constructor finishes, its final fields are guaranteed visible — the real reason immutability is easy mode. For the false-sharing cousin, @Contended pads a hot field onto its own cache line.

I reason in JMM terms, not intuition: "is this field published safely, and is this action atomic?" The safe defaults sidestep most of it — immutability (final fields, records), confinement, and using java.util.concurrent (concurrent collections, atomics) rather than hand-rolling. And I'd name false sharing as the subtle performance cousin: independent variables on the same cache line ping-pong between cores.

Check yourself Why does the textbook double-checked-locking singleton need its instance field marked volatile to be correct? Without volatile, the write that stores the new instance can be reordered before the object’s fields are fully initialized, so a second thread sees a non-null reference to a half-constructed object; volatile establishes happens-before and forbids that reordering, so a reader sees a fully-built instance or null.

11Concurrency

Threads contend on a lock

Why it mattersLock mechanics and deadlock are staple senior-concurrency questions.

Analogy A single-key bathroom: when no one’s waiting, grabbing the key is instant; the moment a queue forms people sit down to wait (park), an attendant has to wake the next one each time, and the whole hallway moves at the speed of one toilet.

synchronized uses an object's monitor. Uncontended it's cheap — a lightweight CAS on the object header. Under contention, threads that can't acquire it block and are parked by the OS, and the lock inflates to a heavyweight monitor — now you pay context-switch and scheduling costs and throughput drops as threads serialize. ReentrantLock is similar but explicit, with tryLock and timeouts, interruptible acquisition, and fairness options; for read-heavy data, ReadWriteLock or StampedLock let readers proceed in parallel. Deadlock is threads acquiring multiple locks in different orders, each waiting on one the other holds — a cycle; livelock and starvation are cousins.

Modern corrections worth stating. The old ‘biased → thin → fat’ lock story is dated: biased locking was disabled by default and deprecated for removal (JDK 15+), so today it’s essentially thin (CAS) inflating to fat (OS monitor) under contention. For read-mostly data, StampedLock’s optimistic read is the real weapon — it takes no lock, just a version stamp you validate afterward — but it is not reentrant, a trap if you’re used to synchronized. And you don’t debug deadlocks by staring: ThreadMXBean.findDeadlockedThreads() or a thread dump names the exact cycle.

The goal is to reduce contention, not just lock correctly — a hot lock is a scalability wall (Amdahl's law: the serial section caps your speedup). So I prefer lock-free atomics or concurrent collections, shrink critical sections, and partition state (lock striping) so threads don't fight over one lock. Deadlock I prevent with a global lock-ordering discipline or timeouts. And it connects to Loom: a hot synchronized block both serializes and can pin a carrier thread, so it's doubly worth removing.

Check yourself You switch a hot read path from synchronized to StampedLock for its optimistic read and start getting mysterious lock-ups when methods call each other — what’s the likely cause? StampedLock is not reentrant — a thread that already holds its write lock and then re-acquires it via a nested call deadlocks against itself, unlike synchronized/ReentrantLock; keep critical sections flat, or use a reentrant lock if you genuinely need re-entry.

12Concurrency

A thread pool saturates

Why it mattersPool sizing and rejection policy are where production incidents are quietly made.

Analogy A kitchen with a fixed line of cooks and a ticket rail: orders wait on the rail (queue) until a cook frees up, and only when the rail jams do you call in extra cooks — so an infinite rail means you never call anyone and simply drown in tickets.

A ThreadPoolExecutor has core and max threads and a work queue. Tasks run on core threads; when those are busy tasks go to the queue; only when the queue is full does it add threads up to max; and when max threads and the queue are both full, the rejection policy fires — abort (throw), caller-runs (backpressure onto the submitter), or discard. Two traps: an unbounded queue means it never creates threads beyond core and never rejects — it just grows memory until OOM; and too few threads for a blocking workload means tasks pile up and latency explodes.

The dangerous part is what the convenience factories hide. Executors.newFixedThreadPool pairs a fixed thread count with an unbounded LinkedBlockingQueue (the OOM trap), and newCachedThreadPool uses a SynchronousQueue with unbounded max threads (a thread-explosion trap) — which is why seasoned teams construct ThreadPoolExecutor explicitly with a bounded queue and a chosen rejection policy. A SynchronousQueue has zero capacity, handing each task straight to a thread or rejecting; allowCoreThreadTimeOut lets an idle pool shrink back toward zero.

Sizing is modeling, not guessing. CPU-bound work: threads ≈ cores. I/O-bound: more, per Little's Law (concurrency = arrival rate × service time) — exactly the pressure virtual threads relieve. I always bound the queue and pick a rejection policy deliberately, because unbounded queues turn a slowdown into an OOM, and caller-runs gives natural backpressure. I'd also flag the shared ForkJoinPool.commonPool() used by parallel streams and default CompletableFuture: blocking work there starves the whole JVM, so give blocking work its own pool.

Check yourself Why do experienced teams avoid Executors.newFixedThreadPool() and newCachedThreadPool() and build a ThreadPoolExecutor by hand instead? Both hide unbounded behaviour: newFixedThreadPool has an unbounded queue (a slowdown silently grows memory to OOM instead of rejecting), and newCachedThreadPool allows unbounded threads (a burst spawns threads until the machine dies); an explicit ThreadPoolExecutor lets you bound the queue and pick a deliberate rejection policy.

13Concurrency

You compose work with CompletableFuture

Why they ask Async composition — fan-out, chaining, error handling — is the everyday pre-Loom concurrency API, and interviewers probe the sharp edges.

Analogy A kitchen passing tickets down a line: thenApply is ‘plate what the last cook handed you’; thenCompose is ‘send this to another station and wait for their ticket’ — confuse the two and you get a dish wrapped inside another dish (a future of a future).

A CompletableFuture represents a value that will arrive, with a pipeline of callbacks. The composition vocabulary: thenApply transforms the result with a plain function; thenCompose flat-maps — it chains a step that itself returns a future, avoiding a nested CompletableFuture<CompletableFuture<T>>; thenCombine joins two independent futures; and allOf/anyOf fan out and wait for all (or the first). Error handling is explicit: exceptionally recovers from a failure, while handle and whenComplete see both outcomes — an exception anywhere short-circuits the chain to the nearest handler, much as it propagates down a stack.

The two traps interviewers wait for. First, which thread runs the callback: the non-Async variants may run on the thread that completed the future (or the caller), while …Async variants run on the common ForkJoinPool by default — so blocking work there starves parallel streams and other futures unless you pass your own Executor. Second, calling get()/join() blocks the calling thread, collapsing all that async work back into a synchronous wait.

I frame CompletableFuture as declarative async: build the dependency graph with thenCompose/thenCombine/allOf and let it run, rather than blocking on intermediate get()s. The non-negotiables I state: pass an explicit, right-sized Executor to the Async methods (never silently lean on the common pool), always attach error handling (a swallowed exception in a future is a silent failure), and set a timeout (orTimeout). And the honest Java-21 context: for simple fan-out/aggregate, structured concurrency on virtual threads is now often clearer than a tangle of chained futures — CompletableFuture earns its place as a reusable, non-blocking pipeline.

Check yourself Your pipeline uses thenApply on a method that itself returns a CompletableFuture, and you end up with a CompletableFuture<CompletableFuture<Order>> — what should you have used? thenCompose — it flat-maps, chaining a step that returns a future so the result stays a flat CompletableFuture<Order>; thenApply wraps whatever the function returns, so returning a future from it nests one future inside another (the async analogue of map vs flatMap).

A Spring Boot app boots

The container wires a dependency

Why it mattersBean scope, proxies, and circular deps are constant sources of subtle bugs.

Analogy Furnishing a house once and sharing it among everyone who lives there (singletons): fine for the sofa, a disaster for the toothbrush — put personal, per-visitor state on a shared bean and every concurrent request scribbles over the same field.

Spring builds a graph of bean definitions and instantiates them, injecting collaborators (constructor injection preferred). Beans are singletons by default — one shared instance per context — so they must be stateless and thread-safe, because that one instance serves all concurrent requests. Some beans are wrapped in proxies (for @Transactional, @Async, @Cacheable, security) — a CGLIB or JDK dynamic proxy that intercepts calls to add behavior. A circular dependency (A needs B, B needs A) can't be satisfied by constructor injection and fails fast; Spring can resolve it for setter/field injection via early references, but it's a design smell.

Constructor injection is my default — it makes dependencies explicit, supports immutability (final fields), and surfaces cycles at startup instead of hiding them. The singleton default is the thing juniors trip on: putting mutable request state in a singleton field is a data race across requests. And knowing beans are proxied explains a whole class of "why didn't my annotation fire" bugs — which leads straight to the self-invocation gotcha with @Transactional.

16Spring MVC

A request hits Spring MVC

Why it mattersThe DispatcherServlet flow is the backbone of every servlet-stack Spring app.

Analogy A hotel concierge desk (DispatcherServlet) with a fixed number of staff: a guest’s request occupies one staffer for its entire errand, including the long wait while they phone another department — run low on staff and the lobby backs up, however empty the hotel is.

The request first passes the servlet filter chain (including Spring Security's filters). It reaches the DispatcherServlet — the front controller — which consults handler mappings to find the @Controller method matching the URL and verb. It runs interceptors, binds and validates the request, and uses message converters (Jackson) to deserialize the JSON body into your DTO, invokes your handler, then serializes the return value back to JSON, sets the status, and writes the response. Exceptions route to exception resolvers. Crucially, in the classic MVC stack this runs on a server-pool thread, thread-per-request — occupied for the whole request, including any blocking downstream call.

Before virtual threads, MVC already had an escape: return a Callable, DeferredResult or CompletableFuture and the servlet container releases the request thread while the work proceeds, re-dispatching when the result is ready — async MVC, the servlet-3 way to stop a slow downstream pinning Tomcat threads. And overload has two knobs, not one: once all max-threads are busy, new connections queue in accept-count (the OS backlog); only when that fills are connections refused — so a too-small accept-count turns a brief spike into connection resets.

That thread-per-request model is why the container's thread pool size (Tomcat max-threads) is a key scaling knob and why slow downstreams exhaust it — the connection-pool-exhaustion cascade in Java form. It's also the exact reason virtual threads (Boot 3.2+) and WebFlux exist: the same DispatcherServlet flow, but the request thread either becomes cheap (virtual) or is never blocked (reactive). Filters versus interceptors matters too — cross-cutting concerns like auth belong in the filter chain.

Check yourself In classic MVC, how can a controller let a slow downstream call run without holding a Tomcat request thread for the whole wait — short of going fully reactive? Return an async type — Callable, DeferredResult, or CompletableFuture — and Spring hands the work off, freeing the servlet thread immediately and re-dispatching when it completes (async MVC); or, in Boot 3.2+, enable virtual threads so the blocking wait itself becomes cheap.

17Spring Boot

@Transactional is invoked

Why it mattersSelf-invocation and the checked-exception rollback default are the most common Spring bugs.

Analogy A manager (the proxy) who opens the ledger before you start and closes it after — but only if your request came through their door; shout the task to a colleague across your own desk (this.method()) and the manager never hears it, so nothing is recorded.

@Transactional is implemented by an AOP proxy around your bean. When an outside caller invokes the method through the proxy, the proxy asks the transaction manager to begin a transaction (bind a connection, autocommit off), calls your method, and commits on normal return or rolls back on exception. Default propagation is REQUIRED — join an existing transaction or start one. The rollback default is the trap: Spring rolls back on unchecked exceptions (RuntimeException, Error) but not checked exceptions unless you set rollbackFor.

The famous gotcha is self-invocation: if a method in the same bean calls another @Transactional method directly (this.other()), the call doesn't go through the proxy, so the annotation is ignored entirely — no transaction. Same for @Async and @Cacheable. And @Transactional on private or non-public methods doesn't work — the proxy can't intercept.

Three levers the basic story omits. readOnly = true isn’t just documentation: Hibernate sets flush mode to MANUAL and skips dirty checking (less memory, no accidental writes), and it can route to a read replica. The isolation attribute lets you ask the DB for REPEATABLE_READ or SERIALIZABLE when a use case needs it. And the sharp one: REQUIRES_NEW suspends the outer transaction and borrows a second connection while the first is still held — nest a few and you can deadlock yourself by draining the pool.

I make people say why it's a proxy, because that one fact explains self-invocation, the checked-exception default, and the public-method-only rule. The fixes: call through an injected bean (or self-inject), set rollbackFor for checked exceptions, and understand propagation — REQUIRES_NEW opens a nested independent transaction with its own connection, a pool-exhaustion risk if overused. Keep transactions short and never do remote calls inside them.

Check yourself Why can sprinkling @Transactional(propagation = REQUIRES_NEW) through a call chain quietly cause a deadlock under load? Each REQUIRES_NEW suspends the caller’s transaction but keeps its connection and borrows a second one for the inner transaction; a chain holds several connections per request, so under concurrency the pool empties and threads block waiting for connections that other threads’ suspended transactions are holding — a self-inflicted pool deadlock.

19JPA / Hibernate

You touch a lazy association

Why it mattersLazyInitializationException and N+1 are the top JPA production issues.

Analogy A book full of ‘see appendix’ notes (lazy proxies): cheap to carry, but try to read a note after the library has closed (the session ended) and you’re stuck — and reading one note per page across 500 pages is 500 separate trips to the stacks (N+1).

JPA associations are lazy by default. When you load an entity, Hibernate populates a proxy or a lazy collection wrapper for the association — the data isn't fetched until you access it. Two failure modes follow. LazyInitializationException: you access the association after the persistence context (session) has closed — typically in the controller or view, after the @Transactional service method returned — so there's no session to load it. The N+1 problem: you load N entities, then loop and touch a lazy association on each, firing one query per element — 1 + N queries instead of one.

The fixes: fetch what you need in the query — a JOIN FETCH or an @EntityGraph — or return a DTO projection so you never touch lazy state outside the transaction. Batch fetching turns N+1 into a few IN queries.

Three senior-level corrections. Only collections are lazy by default — @ManyToOne and @OneToOne are EAGER by default, a hidden source of surprise joins, so many teams mark them LAZY explicitly. A JOIN FETCH on a collection combined with pagination (setMaxResults) can’t page in SQL, so Hibernate silently fetches everything and paginates in memory (the HHH000104 warning). And fetching two collections at once throws MultipleBagFetchException — use Sets, or split into separate queries / @BatchSize.

The rule I set is fetch explicitly for the use case — lazy by default plus fetch-what-you-need per query — and never rely on open-session-in-view, which papers over LazyInit by holding the session open into rendering, at the cost of longer-held connections and hidden N+1. N+1 is silent in dev and lethal at production data volume, so I catch it with SQL logging and query-count assertions in tests. This is exactly where ORM convenience meets real query cost.

Check yourself You add JOIN FETCH on a one-to-many and keep your Pageable, and suddenly a huge query loads the whole table into memory — why? You can’t paginate a collection join in SQL (the join multiplies rows, so LIMIT would cut mid-entity), so Hibernate fetches all matching rows and applies the offset/limit in memory — the HHH000104 warning; page the root ids first, or use @BatchSize/a second query, instead of fetch-joining the collection with pagination.

20JPA / Hibernate

A persistence context flushes

Why it mattersDirty checking and flush timing surprise people — "I never called save()."

Analogy A notepad that watches what you scribble and, at the end, automatically mails only the lines you changed (dirty checking) — you never say ‘send’ (save()); it diffs your page against the carbon copy it kept when you opened it.

Inside a transaction the persistence context is a first-level cache and unit of work: managed entities you load or persist are tracked. Hibernate does dirty checking — at flush time it compares each managed entity to its loaded snapshot and generates UPDATEs for what changed, which is why simply setting a field on a managed entity persists without any explicit save(). Flush — sending pending SQL to the DB — happens automatically before a query that might need the changes, and at commit; it is not the same as commit (flush pushes SQL, commit ends the transaction). The first-level cache also means loading the same entity twice in one context returns the same instance and may skip a query.

The costs the convenience hides. Dirty checking keeps a snapshot of every managed entity, so reading 100k rows in one transaction roughly doubles their memory — for bulk work use a StatelessSession, read-only mode, or periodic flush()+clear() to drain the context. And flush order is fixed — all inserts, then updates, then deletes, regardless of the order you wrote the code — which produces baffling constraint-violation errors when a delete you expected to run first is actually deferred behind an insert.

People are surprised twice — that mutating a managed entity writes without save(), and that flush order and timing are Hibernate's call. I stress controlling it: keep entities detached when you don't want auto-updates, be deliberate with flush modes, and remember the L1 cache is per-transaction — not a shared cache (that's the L2 cache, separate). It also explains ordering surprises, since Hibernate may reorder and batch SQL at flush, and why long transactions accumulate a large dirty context — more memory and longer-held locks.

Check yourself A batch job that loads and updates 200k entities in one transaction slows to a crawl and balloons memory though each update is tiny — the JPA cause and fix? The persistence context keeps every managed entity plus a dirty-checking snapshot, so memory and flush-scan cost grow with the number loaded; fix it by flush()+clear()ing in batches (e.g. every 50), using a StatelessSession, or doing it as a bulk UPDATE query that bypasses the context entirely.

The HikariCP pool is exhausted

Why it mattersConnection-pool sizing is the Java side of a classic production incident.

Analogy A small rack of shared power tools (connections): borrow, use, return promptly and ten is plenty for a big crew; but hold a drill while you wander off to take a phone call (a remote call inside the transaction) and the whole crew is soon standing idle, waiting.

Every DB operation borrows a connection from the pool — HikariCP by default, small, around 10 max. A thread that needs a connection when none is free waits up to connectionTimeout (about 30 s by default), then fails with "unable to obtain connection." Exhaustion happens when connections are held too long — a slow query, a transaction kept open across a remote call, or a connection leak (borrowed and never returned because of a missing close or failed transaction cleanup). As the pool drains, request threads block waiting, latency climbs, and it cascades exactly like the generic pool-exhaustion story.

The leak and sizing story misses connection freshness. A connection sitting idle in the pool can be silently killed by the database’s wait_timeout or a firewall/LB idle timeout, and you only find out when a borrow hands you a dead socket (‘connection reset’); the fix is maxLifetime (and keepaliveTime) set comfortably below that external timeout so Hikari retires connections first. And the famous counterintuitive heuristic — roughly (core_count × 2) + effective_spindles, often just a handful — is why ‘smaller is faster’ holds.

The counterintuitive lesson is that a bigger pool is usually the wrong fix — the pool should be sized to what the database can actually handle concurrently (often small; there's a well-known "smaller pool, faster" result), because past that you just move contention into the DB. I right-size against the DB's max connections, sharing that budget across all instances — N pods × pool size must not exceed the DB limit — keep transactions short and never hold a connection across a network call, and turn on leakDetectionThreshold to catch leaks. It's the same discipline as the platform pool-cascade, one layer down.

22JPA / Hibernate

Two transactions update the same row

Why they ask The lost-update problem is a correctness bug under concurrency, and choosing optimistic vs pessimistic locking is a core data-design decision.

Analogy A shared wiki page: optimistic locking is ‘edit freely, but on save we check nobody changed it since you opened it — if they did, redo’; pessimistic is ‘check the page out so nobody else can edit until you’re done.’ One bets conflicts are rare, the other prevents them up front.

Without a guard, two transactions that both read a row, modify it, and write back cause a lost update: the second silently overwrites the first’s change. Optimistic locking adds a @Version column; every update becomes UPDATE … WHERE id = ? AND version = ? and bumps the version, so if someone else already incremented it the affected-row count is zero and JPA throws OptimisticLockException — no database locks held, you just retry. It assumes conflicts are rare and makes the no-conflict path free.

Pessimistic locking instead takes a real database lock up front — LockModeType.PESSIMISTIC_WRITE issues SELECT … FOR UPDATE, so other writers block until you commit. It prevents the conflict outright but holds a lock for the transaction’s duration, serializing access and risking lock waits and deadlocks — the price of certainty. It suits short, hot, high-contention updates (an inventory decrement, a balance) where a retry storm would be worse than a brief wait.

My rule: optimistic by default — a @Version field costs nothing when there’s no conflict and scales far better because it holds no locks — and pessimistic only for genuinely hot rows where conflicts are frequent and retries would thrash. Optimistic locking demands a retry strategy on the caller (catch the exception, re-read, re-apply, bounded attempts), which also makes it a natural fit behind idempotent, retryable operations. I connect it to isolation levels: both are really answers to the same lost-update problem that the DB’s default READ_COMMITTED doesn’t prevent on its own.

Check yourself A balance-update endpoint occasionally loses an increment under concurrent requests. You add a @Version column — what new thing must the calling code now handle? Retry on OptimisticLockException: with versioning, a concurrent update makes one transaction’s UPDATE … WHERE version = ? match zero rows and fail, so the caller must catch that, re-read the fresh row, re-apply the change, and retry (bounded) — the version turns a silent lost update into an explicit, recoverable conflict.

You insert ten thousand rows

Why they ask Bulk writes are where ORM defaults quietly send one round trip per row — a 100× difference a senior is expected to spot.

Analogy Posting a thousand letters one taxi ride to the post office at a time, versus filling one van and driving once: the letters are identical — it’s the round trips to the database that cost, and batching is loading the van.

By default, persisting N entities can issue N separate INSERT statements — each its own network round trip, dominated by latency, not by the work. Two gotchas sink naive batching. And in a long loop you must flush() and clear() the persistence context periodically (e.g. every batch_size rows), or the growing dirty-checked context defeats the point by eating memory and slowing each flush.

The lens is round trips, not row count, drive bulk-write cost — the same latency-amortization idea as any batched remote call. For true bulk I decide between ORM batching (keeps lifecycle callbacks and validation) and dropping to a set-based path — a bulk INSERT/UPDATE JPQL, JdbcTemplate.batchUpdate, or COPY — which is far faster but bypasses the persistence context and its callbacks. Whichever I pick, I verify with SQL logging and statement counts that batching actually engaged, because one wrong setting (an IDENTITY key, an unset driver flag) silently reverts to one row at a time.

A request crosses the Spring Security filter chain

Why it mattersThe filter chain is the basis of every Spring Security question.

Analogy A row of single-task gates in a fixed order: one checks for an existing pass, the next inspects your ID and clips on a day-badge (stored on a ThreadLocal), a later one checks that badge against the room you’re entering — scramble the order and the whole screening breaks.

Spring Security plugs into the servlet filter chain via one delegating filter, behind which sits the SecurityFilterChain — an ordered list of single-purpose filters. Early filters load any existing SecurityContext from the session. An authentication filter (form login, Basic, or a bearer JWT) extracts credentials and calls the AuthenticationManager and its providers, producing an Authentication stored in the SecurityContextHolder — a ThreadLocal. Later the AuthorizationFilter checks the request against your rules (roles/authorities, method security) and either lets it reach the controller or rejects it, and an exception-translation filter turns auth failures into 401/403 or a login redirect.

Three things the single-chain picture omits. You can have several SecurityFilterChain beans, each guarded by a securityMatcher and tried in @Order — the standard way to run stateless JWT for /api/** and form login for the web UI side by side. Spring Security 6 made the context explicit-save (requireExplicitSave): the filter no longer auto-persists the SecurityContext, which quietly broke some custom-login code on upgrade. And because the holder is a ThreadLocal, @Async loses it unless you use MODE_INHERITABLETHREADLOCAL or a context-propagating decorator.

Two things to say precisely. First, it's a chain of single-responsibility filters, so I configure it declaratively with the Spring Security 6 lambda DSL and SecurityFilterChain beans, not the old adapter. Second, the SecurityContext lives in a ThreadLocal, which is why it "just works" per request in thread-per-request MVC — and why it needs explicit propagation in reactive (ReactiveSecurityContext) and care with @Async and virtual threads. I'd map stateless (JWT, no session) versus stateful (session cookie) here, because it changes which filters and which CSRF stance apply.

Why it mattersSpring-specific token validation — the everyday stateless-auth mechanism.

Analogy A bouncer who checks a tamper-proof wristband himself instead of radioing head office each time: he keeps a copy of the venue’s official stamp (the public key) and verifies the band’s seal on the spot — fast, but he can’t un-admit someone whose band was revoked after they got in.

Configured as an OAuth2 resource server, Spring extracts the Bearer token and hands it to a JwtDecoder. For asymmetric tokens the decoder fetches the identity provider's public keys from its JWKS endpoint (discovered from the issuer), caches them, and picks the key by the token's kid to verify the signature — no call to the auth server per request. It then validates the standard claims — exp, iss, and aud — and maps claims (scopes/roles) into Spring authorities via a converter, producing a JwtAuthenticationToken in the SecurityContext that your authorization rules and method security use.

The stateless win has a cost the answer only hints at: you can’t revoke a valid JWT before it expires. When you need instant revocation, the alternative is opaque tokens + introspection (a /introspect call back to the auth server per request — stateful but revocable), or a short-lived access token backed by a revocable refresh token. Two operational details: allow a small clock-skew leeway on exp/nbf so minor drift doesn’t reject valid tokens, and when the decoder meets an unknown kid it refetches JWKS — rate-limit that, or a bad-token storm becomes a self-DDoS on your IdP.

This is stateless auth done right — signature-verified, self-contained tokens, keys rotated via JWKS/kid without redeploying, validated at the edge and re-checked in services for defense in depth. What I insist on: always validate aud and iss (skipping them is a real vulnerability), pin the algorithm, keep lifetimes short because revocation is hard (the stateless trade-off), and map authorities explicitly so authorization is predictable. It's the framework realization of the generic JWT mechanism from the platform volume — same guarantees, Spring plumbing.

Check yourself A user is deactivated but their JWT keeps working for several more minutes — why, and what are your options if that’s unacceptable? A JWT is self-contained and valid until exp, so nothing checks a revocation list per request — the stateless trade-off; options are very short lifetimes (shrink the window), opaque tokens with introspection, or a server-side revocation/deny-list checked on sensitive operations, each trading some statelessness for immediacy.

26Security

CSRF, and session vs stateless

Why it matters"Why did you disable CSRF?" trips anyone who doesn't hold the threat model.

Analogy A bank that auto-recognises you by a signet ring you always wear (the session cookie): convenient, but a con artist can slip you a pre-addressed envelope to sign — the bank sees your ring and obeys. A token you type in by hand each time can’t be abused that way.

CSRF — cross-site request forgery — exploits ambient credentials: if auth lives in a cookie the browser sends automatically, a malicious site can trigger a state-changing request to your app and the browser attaches the cookie, so the request looks authentic. The defense is a CSRF token the server issues and the legitimate client echoes in a header or field — a value a cross-site request can't know. It only matters for browser, cookie/session-based auth on state-changing methods.

For a stateless API authenticated by a Bearer token in the Authorization header, there's no ambient credential — the browser doesn't auto-attach a bearer token — so CSRF doesn't apply, which is why you disable Spring's CSRF protection for pure token APIs. Related session concerns: session fixation (rotate the session ID on login, which Spring does by default) and Secure/HttpOnly/SameSite cookie flags.

For SPAs that do use cookies, the pattern is the double-submit cookie: CookieCsrfTokenRepository.withHttpOnlyFalse() so JavaScript can read the token and echo it in a header. Beware a real upgrade gotcha: Spring Security 6 changed CSRF handling (deferred token loading plus CsrfTokenRequestAttributeHandler with BREACH protection), which silently broke some SPA setups on migration. And don’t lean on SameSite alone — Lax still permits top-level GET navigations and has subdomain gaps, so it’s defense in depth, not a replacement for a token.

The principle I state is: CSRF risk exists exactly when the browser supplies credentials automatically. So session-cookie apps need CSRF protection (with SameSite cookies as defense in depth); token-in-header APIs don't. Disabling CSRF isn't "turning off security," it's recognizing the threat model doesn't apply — but only if you're truly not using cookies for auth. Getting that mapping wrong is how you either break your SPA or leave a cookie app exposed.

Check yourself A cookie-authenticated SPA needs CSRF protection, but its JavaScript can’t read an HttpOnly CSRF cookie to echo it — what’s the standard Spring approach? Use the double-submit cookie via CookieCsrfTokenRepository.withHttpOnlyFalse(): Spring writes a non-HttpOnly CSRF cookie the SPA’s JS reads and sends back in a header, and the server compares the two; a cross-site attacker can’t read the cookie value to forge the matching header, so the request is rejected.

@PreAuthorize guards a method

Why they ask Method security is defense-in-depth below the URL layer — and because it’s proxy-based, it inherits the same self-invocation trap as @Transactional.

Analogy Not just a guard at the building’s front door (URL rules) but a second check at each office door that reads your badge and what you’re carrying (the method’s arguments) before letting you in — so even someone already inside can’t open a room they lack rights to.

I treat request-level security (URL rules in the filter chain) and method security as complementary layers: the filter chain is the coarse front gate, while @PreAuthorize on the service layer is fine-grained, argument-aware authorization that still protects a method reached from a different entry point. The cautions I name: keep SpEL rules simple and tested (complex expressions in annotations are easy to get subtly wrong and hard to review), centralize reusable checks behind a custom permission evaluator rather than copy-pasting SpEL, and remember the self-invocation and public-method constraints so a ‘guarded’ method isn’t silently unguarded.

Reactive & scaling

The other scaling model: how WebFlux serves huge concurrency on a handful of event-loop threads with built-in backpressure — and the single mistake that brings the whole thing down.

28Reactive

A request flows through WebFlux

Why it mattersThe event-loop model and backpressure are a distinct approach to scaling.

Analogy A sushi conveyor belt, not a waiter per diner: a few chefs (event-loop threads) keep plates moving for a whole room, and if a diner eats slowly the belt is told to slow down (backpressure) rather than piling plates until they topple.

WebFlux runs on a small pool of event-loop threads (Reactor Netty by default) — roughly one per core — that must never block. A handler returns a Mono or Flux — a lazy pipeline that does nothing until subscribed. The framework subscribes, and as data becomes available (the DB responds, the downstream returns) callbacks run on event-loop threads, assembling the response without any thread sitting idle waiting. Because producer and consumer are decoupled, Reactive Streams provides backpressure: a slow consumer signals demand upstream so a fast producer can't overwhelm it.

Two mechanics you’ll be asked to show you know. Threading is set by two operators people constantly confuse: subscribeOn chooses the thread the source/subscription runs on (position-independent), while publishOn switches the thread for everything downstream of it. And backpressure only works when the source can be slowed; a hot or unbounded source (a WebSocket, Flux.interval, sensor data) can’t, so you pick a strategy explicitly — onBackpressureBuffer, Drop, or Latest — deciding whether to buffer, shed, or keep only the newest when the consumer falls behind.

The win is scaling to very high concurrency with few threads, plus built-in backpressure — great for I/O-bound, streaming, or fan-out-heavy services with slow downstreams. The costs are real: a steep learning curve, harder debugging (no linear stack traces), and everything in the path must be non-blocking end to end. I'm honest that virtual threads now cover much of the "scale blocking I/O" use case with far simpler code, so I reach for WebFlux specifically when I need streaming or explicit backpressure — not reflexively.

Check yourself What’s the practical difference between subscribeOn and publishOn in a Reactor pipeline? subscribeOn chooses the Scheduler the subscription and source emission run on and affects the whole chain regardless of placement; publishOn switches the thread only for operators downstream of its position — so use publishOn to move work onto another scheduler partway through, and subscribeOn to control where the source itself executes.

29Reactive

You block the event loop

Why it mattersIt's the number-one reactive production disaster — subtle and catastrophic.

Analogy A sushi belt kept moving by just three chefs: if one stops to hand-carve a whole fish (a blocking call), that’s a third of the kitchen frozen — a couple more such stalls and the belt halts for the entire room, though it looked fine at lunch’s slow trickle.

Because WebFlux has only a handful of event-loop threads, a single blocking call in a reactive pipeline — a JDBC call, a synchronous HTTP client, a Thread.sleep, even a heavy CPU crunch — parks one of those precious threads. Do it under load and you starve the event loop: with every loop thread stuck, the whole application stops processing any request, not just the blocking one. It's catastrophic and non-obvious, because it works fine at low traffic and collapses under load.

Two sharper points. Offloading to Schedulers.boundedElastic() isn’t a free pass — it’s bounded (default ~10× cores), so shovelling lots of blocking work there just moves the saturation wall, it doesn’t remove it. And because work hops threads, ThreadLocal doesn’t follow a reactive chain — MDC logging, the SecurityContext, and trace IDs vanish — so you carry them in the Reactor Context and bridge them with the Micrometer context-propagation library instead of assuming a ThreadLocal is present.

This is the fragility tax of reactive — the model only holds if the entire path is non-blocking, and one careless dependency poisons it. The fixes: use non-blocking clients end to end; if you must call blocking code, offload it with subscribeOn(Schedulers.boundedElastic()) so it runs off the loop; and mandate BlockHound in tests to detect accidental blocking on reactive threads at development time. I treat "is every library in this path non-blocking?" as a gating question before choosing WebFlux — and it's a strong argument for virtual threads when the workload is simply blocking I/O at scale, because there blocking is safe and cheap.

Check yourself After moving to WebFlux, your log lines lose their correlation/MDC IDs and SecurityContextHolder comes back empty in places — why, and what’s the fix? Reactive pipelines hop between threads, so anything in a ThreadLocal (MDC, Spring’s SecurityContext) is lost; propagate it through the Reactor Context and wire the Micrometer context-propagation bridge, which restores the registered ThreadLocals around each operator so logging, security and tracing work across thread switches.

30Reactive

A reactive app queries the database (R2DBC)

Why they ask It’s the piece that makes WebFlux end-to-end non-blocking — and the honest comparison against virtual threads + JDBC is a sharp architect question.

Analogy JDBC is a phone call you must stay on the line for until the answer comes (blocking a thread); R2DBC is texting the question and getting pinged when the reply lands — you’re free to do other things between, which is the only way a three-thread event loop survives.

A reactive stack is non-blocking only if every hop is — and classic JDBC is fundamentally blocking, so a JDBC call inside WebFlux parks a precious event-loop thread and poisons the model. R2DBC (Reactive Relational Database Connectivity) is the non-blocking alternative: queries return Mono/Flux, results stream with backpressure, and the driver uses async I/O so no thread waits on the database. A reactive pool (r2dbc-pool) manages connections the way Hikari does for JDBC.

The trade-off is real: R2DBC is not JPA/Hibernate. There’s no persistence context, no lazy loading, no dirty checking, no automatic relationship graph — Spring Data R2DBC is a lighter mapper where you write more explicit queries and assemble relationships yourself. You gain non-blocking, streaming reads (great for pumping large result sets with backpressure); you give up the ORM conveniences and a huge body of mature tooling.

I’m blunt about when it’s worth it. Reach for R2DBC when you’ve already committed to WebFlux for streaming or backpressure and need the database to not break the chain — otherwise its cost (younger ecosystem, no JPA, harder queries) rarely pays off just for throughput. The Java-21 reframing I state plainly: virtual threads let you keep ordinary blocking JDBC and JPA and still scale I/O-bound load, so for many teams ‘thread-per-request on virtual threads + JDBC’ now beats ‘WebFlux + R2DBC’ on simplicity for the same scalability — R2DBC earns its place specifically where you need reactive streaming and end-to-end backpressure, not merely high concurrency.

Check yourself A team put WebFlux in front of a normal Spring Data JPA repository and throughput collapsed under load — what’s wrong, and what are the two valid fixes? JPA/JDBC is blocking, so every repository call parks an event-loop thread and starves the loop under load; fix it either by going non-blocking end-to-end with R2DBC, or — to keep JDBC/JPA — by dropping WebFlux here and running thread-per-request on virtual threads, where blocking is cheap (at minimum, offload the blocking calls to boundedElastic).

31Actuator

Actuator probes health, readiness, liveness

Why it mattersCorrect probe wiring is what makes a Spring Boot app behave in Kubernetes.

Analogy Two different questions a hospital asks: ‘are you beyond saving?’ (liveness — if yes, call it) versus ‘are you well enough for visitors right now?’ (readiness — if not, hold visitors but keep treating) — mix them up and you ‘resuscitate’ someone who was merely busy.

Actuator exposes /actuator/health, aggregated from health indicators — DB, disk, broker, custom. Spring Boot distinguishes liveness and readiness via health groups and the ApplicationAvailability state, exposed at /actuator/health/liveness and /readiness, which map to Kubernetes probes. Liveness answers "is the app broken beyond recovery?" — if it fails, restart the pod. Readiness answers "can it take traffic right now?" — if it fails (still warming up, a dependency is down), pull it from the Service endpoints but don't restart. Boot flips readiness to OUT_OF_SERVICE automatically during startup and graceful shutdown.

Beyond liveness/readiness there’s a startupProbe: a slow-booting app (big context, cache warm-up) can fail liveness and get killed before it ever finishes starting, so the startupProbe guards the boot window and only then hands over to liveness. Two more: don’t expose health details publicly — management.endpoint.health.show-details and ideally a separate management port keep internals off the public surface; and the app can drive its own state by publishing an AvailabilityChangeEvent (flip to OUT_OF_SERVICE while draining a queue, say).

This is the readiness-versus-liveness distinction from the platform side, realized in the app — and the classic self-inflicted outage is a shared-dependency check in the liveness probe, so when the DB blips every pod fails liveness and restarts at once. So I keep liveness cheap and local ("is the process wedged") and put dependency checks in readiness ("don't route to me"). Correct probes plus graceful shutdown are what make rolling deploys and autoscaling actually zero-downtime.

Check yourself A heavy app with a 90-second startup goes into a crash loop the moment you add a liveness probe — what did the probe configuration miss? A startupProbe: without it the liveness probe starts checking during the long boot, fails before the app is ready, and Kubernetes restarts it — forever; a startupProbe (or a generous initialDelaySeconds) protects the startup window, and only after it passes does liveness take over.

32Production

A Spring Boot app shuts down gracefully

Why it mattersGraceful shutdown is the difference between clean deploys and dropped requests.

Analogy Closing a shop for the night properly: lock the front door to new customers, but let the people already inside finish checking out before you kill the lights — and if someone’s taking forever, the landlord (Kubernetes) eventually cuts the power anyway (SIGKILL).

On SIGTERM (what Kubernetes sends before SIGKILL), the JVM runs shutdown hooks and Spring closes the ApplicationContext. With graceful shutdown enabled (server.shutdown=graceful), the embedded server stops accepting new requests but lets in-flight ones finish up to a timeout (spring.lifecycle.timeout-per-shutdown-phase) before closing. SmartLifecycle beans stop in phases, connection pools and listeners close, and readiness flips to OUT_OF_SERVICE so traffic is drained first. Only after that, or at the timeout, does the process exit — and if it exceeds the grace period, Kubernetes SIGKILLs it.

The subtle race the happy path hides: flipping readiness to unready doesn’t stop traffic instantly — it takes a beat for endpoints to update and every kube-proxy/ingress to stop routing, so a pod can get SIGTERM and start refusing while requests are still arriving toward it. The standard cure is a preStop sleep of a few seconds before SIGTERM, covering the propagation lag. Also remember non-HTTP work — Kafka/JMS listeners, @Async tasks, schedulers — needs its own graceful stop, and the whole budget must fit inside terminationGracePeriodSeconds with room for your longest request.

The sequence that makes it truly zero-downtime is: readiness goes unready → the load balancer / endpoints stop sending new traffic → in-flight requests drain → then exit — all inside the pod's terminationGracePeriodSeconds. The common bug is a grace period shorter than your longest request (or no graceful config at all), so deploys drop requests. This is the app-side counterpart to the SIGTERM / preStop / drain mechanics on the Kubernetes side — both halves have to agree on the timing.

Check yourself Even with server.shutdown=graceful, a few requests still 502 during every rollout — what race is happening and what’s the usual fix? There’s a lag between readiness flipping unready and all proxies/endpoints actually stopping routing, so traffic still arrives after the pod begins shutting down; add a preStop hook that sleeps a few seconds (keeping the app accepting during it) so endpoint changes propagate before SIGTERM, all within terminationGracePeriodSeconds.

34Resilience

A downstream dependency fails

Why it mattersResilience patterns are core architect material — and where a blip becomes an outage or not.

Analogy Not one safety device but a stack that must be ordered right: a fuse (timeout) so nothing runs forever, a breaker (circuit breaker) that trips after repeated faults, and a retry switch wired outside the breaker — so a retry respects a tripped breaker instead of fighting it.

The tool in Spring is Resilience4j, applied around a downstream call. A timeout caps how long you wait so a slow dependency can't tie up your thread. A circuit breaker tracks the recent failure rate; when it crosses a threshold it opens and fails fast for a cooldown instead of hammering a dead dependency, then goes half-open to test recovery before closing. A retry re-attempts transient failures — with exponential backoff and jitter, and ideally only for idempotent operations. A bulkhead limits concurrent calls to one dependency so it can't consume all your threads, a rate limiter caps call rate, and a fallback gives a degraded response when all else fails.

Composition order is a real design decision, not incidental. Resilience4j’s default aspect order wraps Retry(CircuitBreaker(RateLimiter(TimeLimiter(Bulkhead(call))))) — retry outside the circuit breaker, so retries stop once the breaker opens instead of hammering it. Bulkheads come in two flavours: a semaphore bulkhead just caps concurrency on the caller’s thread, while a thread-pool bulkhead runs the call on a separate pool — the only one that can actually interrupt a blocking call to enforce a TimeLimiter. And the breaker’s sliding window can be count-based or time-based, which changes how fast it reacts.

The framing is that every remote call fails eventually, so resilience is designed in, not bolted on. The interplay matters: a naive retry without a circuit breaker amplifies an outage (retry storm), and a circuit breaker without a timeout can still be tied up — so I compose them: timeout + bounded retries with backoff + circuit breaker + bulkhead, with a sensible fallback. It's the application-level realization of the same cascading-failure toolkit from the platform volume, and it's what turns a downstream outage into graceful degradation instead of a cascade.

Check yourself Why does Resilience4j wrap retry outside the circuit breaker by default, rather than retrying inside it? So that once the breaker is open, the retry sees the fast CallNotPermitted failure and stops, instead of re-attempting against a dependency you’ve already judged down — retry-inside-breaker would keep generating calls the breaker must reject, defeating the point; retry-outside means retries respect the open circuit and back off.

36Production

You take a thread dump to find a hang

Why they ask When a service hangs or pegs a thread pool with no exception, the thread dump is the primary evidence — reading one cold is a senior skill.

Analogy A freeze-frame of every worker in the building at one instant: who’s mid-task, who’s standing idle waiting for a key someone else holds, and who’s in a standoff where two people each wait for what the other won’t release (a deadlock) — the photo tells you without interrogating anyone.

A thread dump (via jstack <pid>, jcmd <pid> Thread.print, or a SIGQUIT) is a snapshot of every thread’s stack and state: RUNNABLE (running, or in native/socket I/O), BLOCKED (waiting to enter a synchronized monitor another thread holds), WAITING/TIMED_WAITING (parked on a lock, condition, sleep, or get()). The pattern diagnoses the hang: dozens of request threads all BLOCKED on the same lock points to one slow critical section; all WAITING to borrow a connection points to pool exhaustion; the JVM even detects and prints deadlocks (‘Found 1 deadlock’) with the exact lock cycle.

Take two or three dumps a few seconds apart — threads stuck on the same frame across all of them are truly wedged, whereas threads that move are merely busy. The complement for a slow leak (not a hang) is a heap dump opened in Eclipse MAT, whose dominator tree names what’s retaining memory — but a live heap dump pauses the JVM and can be huge, so it’s a heavier, more deliberate tool than a thread dump.

The discipline I bring: for a hang or a saturated pool, thread dumps first — they’re cheap, safe to take in production, and usually name the culprit (a hot lock, a blocking downstream, a deadlock, a drained connection pool) in seconds. I automate capture (dump on liveness-probe failure, or at preStop) so the evidence survives a restart, and reach for continuous, low-overhead profiling (async-profiler, JFR) to catch what a single snapshot misses. The throughline to the rest of this volume: a thread dump is where ‘blocked, not busy,’ lock contention, and pool exhaustion stop being theory and become a line you can point at.
