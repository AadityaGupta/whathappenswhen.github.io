Track 01 — The classics

Networking, end to end

The request path is a chain of independent hops, and each one is a latency budget and a failure domain. These are the questions that check whether you actually know what happens between the keystroke and the byte.

01Networking

You type a URL and press Enter

Why they askThe single best test of whether you understand the whole stack, not just your layer of it.

Analogy Posting a letter: you look up the address (DNS), open a channel (TCP), seal it (TLS), then finally send the words (HTTP) — and each step is its own point of failure and delay.

First the browser decides where to go. It checks its HSTS list — so an http:// may be upgraded to https:// before anything leaves the machine — and looks for a cached DNS answer. If there's no cached IP, it resolves the hostname: the stub resolver on the host asks the configured recursive resolver, which walks root, TLD, and authoritative nameservers and hands back an A or AAAA record.

With an IP in hand the browser opens a TCP connection to port 443 — the three-way handshake, SYN, SYN-ACK, ACK. On top of that it runs the TLS handshake: negotiate the version and cipher, validate the server's certificate chain, agree on session keys. With TLS 1.3 that's usually a single round trip. Only now, over the encrypted channel, does it send the actual GET / with its headers, Host, and cookies.

That request almost never hits the origin directly — it lands on a CDN edge, then a load balancer, then an app server. The response may be a 200 with HTML or a 301/302 redirect that restarts part of this. The browser parses the HTML into a DOM, discovers CSS, JS, and images, and fetches them — multiplexed over HTTP/2 on the same connection — then renders.

On a repeat visit most of this is skipped — a warm DNS cache, a kept-alive connection, and a resumed TLS session can collapse it to almost nothing, which is why first-paint and repeat-visit latency differ so much. The modern path increasingly runs over HTTP/3 / QUIC, which rides UDP and folds the transport and TLS handshakes into one, shaving a round trip.

Every one of those hops is why we obsess over DNS TTLs, connection keep-alive and reuse, TLS session resumption, and CDN caching. Latency is additive across the chain, and any hop is a place the whole page can fail.

Check yourself On a page that is slow only on the first visit but fast afterwards, which hops are the likely culprits, and why does the second visit skip them? DNS resolution, the TCP handshake, and the full TLS handshake — the second visit reuses the cached DNS answer, a kept-alive (or resumed) connection, and a resumed TLS session, so only the actual request/response and render remain.

02Networking

A hostname gets resolved by DNS

Why they askDNS causes a huge share of real outages, and inside Kubernetes it's your service discovery.

Analogy Asking directions by hopping up a chain of authorities: a passer-by (recursive resolver) asks the town hall (root), which points to the street registry (TLD), which points to the building owner (authoritative) — and everyone writes the answer on a sticky note (cache) that fades on its TTL.

The application asks the OS to resolve a name; the stub resolver checks caches — in the browser, in the OS, and at the resolver — and every cache entry lives only as long as its TTL. On a cache miss the recursive resolver does the walking: it asks a root server, which points it at the TLD servers for .com, which point it at the authoritative nameserver for the domain, which returns the actual record — an A, AAAA, or a CNAME that sends it chasing another name.

Worth naming the distinctions: the recursive resolver does the legwork; the authoritative server owns the answer. Queries are usually UDP on port 53, falling back to TCP for large responses, with DoH and DoT as the encrypted variants. Root and TLD servers are reached over anycast, and even failures get cached — that's negative caching.

Inside Kubernetes the classic latency trap is the resolver config: a default ndots:5 plus the pod’s search domains means a lookup for an external name is first tried as name.namespace.svc.cluster.local, then several other suffixes, before the real query — up to five wasted round trips per resolve. The fixes are a trailing dot (FQDN), tuning ndots, or NodeLocal DNSCache.

TTL is the knob that bites: set it too high and a failover or IP change takes forever to propagate; too low and you hammer resolvers and add latency. Inside the cluster this same machinery is CoreDNS resolving service.namespace.svc.cluster.local — when DNS is slow or misconfigured there, it looks exactly like the app being down.

Check yourself A service in Kubernetes suddenly seems slow on every outbound call to an external API, and CoreDNS CPU is spiking — what DNS-specific cause should you suspect? The ndots/search-domain behaviour multiplying each external lookup into several failed cluster-local queries first; fix with an FQDN (trailing dot), a lower ndots, or NodeLocal DNSCache to cut the round trips.

03Networking

A TCP connection is established (and torn down)

Why they askConnection cost and TIME_WAIT exhaustion are real production problems at scale.

Analogy A phone call before a conversation: “can you hear me? — yes, can you hear me? — yes” (the three-way handshake) establishes the line, and hanging up politely (FIN) still leaves you holding the receiver a moment (TIME_WAIT) in case a last word arrives.

It's the three-way handshake. The client sends a SYN carrying its initial sequence number; the server replies with SYN-ACK — its own sequence number plus an acknowledgement of the client's; the client sends the final ACK. Now both sides have agreed sequence numbers and window sizes, the socket is ESTABLISHED, and data can flow.

From there TCP guarantees an ordered, reliable byte stream: every segment is sequenced and acknowledged, lost segments are retransmitted, flow control uses the receive window so a fast sender can't drown a slow receiver, and congestion control — slow start and friends — keeps the network itself from collapsing. Teardown is a FIN/ACK in each direction, and the side that closes first sits in TIME_WAIT for a while to catch stray packets.

Contrast it with UDP, which just fires datagrams with no handshake, ordering, or delivery guarantee — which is why QUIC built its own reliability on top of UDP to escape TCP’s head-of-line blocking. For the TIME_WAIT exhaustion incident, the levers are connection reuse (keep-alive/pooling), widening the ephemeral port range, and SO_REUSEADDR/tcp_tw_reuse — but reuse is the real fix, not kernel tweaks.

That setup cost — a full round trip before any data, plus TLS on top — is exactly why we pool connections and keep them alive rather than opening one per request. And at high connection churn, sockets piling up in TIME_WAIT can exhaust ephemeral ports, which is a classic "the service mysteriously stops connecting" incident.

Check yourself Why does the side that closes a TCP connection first sit in TIME_WAIT, and why can that become a production problem? To absorb any stray delayed segments from the old connection before the port pair is reused — safe per connection, but at high connection churn thousands of sockets stuck in TIME_WAIT can exhaust ephemeral ports, so the service mysteriously can’t open new connections.

04Networking

A TLS handshake happens

Why they askIt underpins every HTTPS call and all of service-to-service mTLS in a mesh.

Analogy Two strangers agreeing a shared secret in public, in the open, that an eavesdropper still can’t derive — then switching to a fast private cipher for the rest of the talk.

Once TCP is established, the client sends a ClientHello: the TLS versions and cipher suites it supports, the server name it wants via SNI, and — in TLS 1.3 — a key share up front. The server replies with a ServerHello choosing the cipher, and presents its certificate chain. The client validates that chain up to a trusted root CA, checks the hostname and validity dates, and checks revocation via OCSP or CRL.

Then they do an ephemeral key exchange — ECDHE — which gives forward secrecy, meaning a leaked long-term key can't decrypt past traffic. Both sides derive the same symmetric session keys, exchange Finished messages, and switch to fast symmetric encryption like AES-GCM. TLS 1.3 gets this down to one round trip, or zero on resumption. With mTLS, the server also demands a client certificate, so both ends authenticate.

Repeat connections skip most of this via session resumption (TLS 1.3 PSK / session tickets), enabling 0-RTT — fast, but 0-RTT early data is replayable, so it’s only safe for idempotent requests. And to avoid a revocation round trip during the handshake, servers use OCSP stapling, attaching a fresh signed ‘not revoked’ proof to the certificate themselves.

This is why certificate lifecycle is a first-class platform concern: automated issuance and rotation with cert-manager and ACME, short-lived certs, and a service mesh handing out and rotating mTLS certs so services authenticate each other without anyone managing keys by hand.

Check yourself TLS 1.3 offers 0-RTT resumption for speed — why must you never send a non-idempotent request (like a payment) as 0-RTT early data? 0-RTT early data can be replayed by an attacker (there’s no round trip to prove freshness), so a replayed non-idempotent request could execute twice; only idempotent, side-effect-free requests are safe as early data.

05Networking

A request hits a load balancer

Why they askHealth checks and draining are the machinery behind zero-downtime deploys.

Analogy A maître d’ at the door: checks who’s free and healthy, seats you at a good table, and — when a waiter goes off shift — lets them finish serving their current tables before sending them home (draining).

First, which layer. An L4 load balancer works at TCP/UDP and just forwards a connection to a backend; an L7 balancer understands HTTP, so it can route by host, path, or header, terminate TLS, and do sticky sessions. Either way it picks a backend from a pool — round robin, least-connections, or a hash — but only from targets currently passing their health checks. Unhealthy targets are pulled out automatically.

It then forwards to that backend, reusing a pooled connection where it can, and typically owns timeouts, retries, and sometimes circuit breaking. Because it's a proxy, the backend sees the balancer's IP unless the real client is preserved in X-Forwarded-For. In cloud and Kubernetes terms this is your ALB or NLB, or a Service of type LoadBalancer and an Ingress.

The health check has a sharp edge: a deep check that pings a shared dependency (the database) can make every backend fail its check at once during a blip, yanking the whole pool out — the same correlated-failure trap as a liveness probe on a shared dependency. And mismatched idle timeouts between the LB and the backend are a classic source of intermittent 502/504s.

The two features that make deploys safe live here: health checks so traffic only goes to ready targets, and connection draining so a backend being removed finishes its in-flight requests before it's cut off. Cross-zone balancing spreads load across AZs, and the balancer itself is both a latency hop and something you must make redundant.

Check yourself Why can a load-balancer health check that verifies a shared database turn a brief DB hiccup into a full outage? If every backend’s health check depends on the same database, a brief DB blip fails them all at once, so the LB marks every target unhealthy and has nowhere to send traffic — keep LB health checks shallow (“is this instance up?”), not dependency-deep.

06Networking

A TLS certificate expires

Why they askExpired certs are a recurring cause of very public, very avoidable outages.

Analogy A passport that stops working the instant it expires — no grace, no warning at the gate; everyone presenting it is turned away simultaneously.

There's nothing graceful about it — it's a hard cliff at the certificate's notAfter timestamp. The instant that passes, any client validating the chain rejects it: browsers throw a full-page security error, API clients raise TLS errors, and service-to-service calls fail — especially under mTLS, where both ends validate. Nothing degrades slowly; every consumer of that endpoint breaks at once.

The blast radius is exactly everything that depends on that certificate — one shared cert on a gateway can take down many services simultaneously. Recovery is to reissue the certificate, deploy it, and reload the server or mesh to pick it up.

It’s not only the leaf certificate: an expired intermediate in the chain breaks validation just as hard, and these have caused huge, confusing outages because the server cert looked fine. Clock skew bites the other end too — a cert that is valid but notBefore is in a client’s future (wrong clock) also fails, so NTP is quietly part of your TLS reliability.

This is a pure automation problem, and the answer is to never let a human be the renewal mechanism. cert-manager with ACME or Let's Encrypt for public certs, an internal PKI or the mesh for service certs, short lifetimes so rotation is routine and well-exercised, and monitoring that alerts on approaching expiry with plenty of lead time. If a cert expiring can surprise you, the process is the bug.

Check yourself Your leaf certificate is valid for months, yet clients suddenly get TLS errors — what two certificate-chain or environment causes should you check first? An expired (or newly-distrusted) intermediate CA in the chain, and clock skew on clients or servers making a valid cert appear expired or not-yet-valid; both break chain validation even when the leaf looks fine.

07Networking

A packet travels from one pod to another

Why they askMost people stop at “pods get an IP” — this tests whether you know how that IP actually routes across nodes.

Analogy Every pod gets a real street address on one giant flat network — the question is whether the mail is hand-carried directly (native routing) or sealed inside a second envelope to cross between buildings (an overlay tunnel).

Kubernetes’ model is a flat network: every pod gets its own routable IP and any pod can reach any pod without NAT. Making that real on top of ordinary node networking is the CNI plugin’s job. When a pod is created, the kubelet calls the CNI, which creates a veth pair — one end in the pod’s network namespace as its eth0, the other in the node’s root namespace — and programs routes so packets can leave the pod.

Getting a packet to a pod on another node is where plugins differ. An overlay (e.g. VXLAN, as in Flannel or Calico’s VXLAN mode) encapsulates the pod packet inside a node-to-node UDP packet — simple, works on any underlying network, but adds a little overhead and hides pod IPs from the fabric. Native routing (Calico BGP, or a cloud VPC CNI handing pods real VPC IPs) skips encapsulation: the network itself knows how to route pod IPs, so it’s faster and more transparent, but needs cooperation from the underlying network.

I’d frame the choice as overlay (portable, works anywhere, small overhead) versus native/VPC routing (faster, pod IPs visible to the fabric, needs network support), and note that eBPF dataplanes like Cilium increasingly replace both kube-proxy and parts of the overlay with in-kernel programs — better performance, identity-aware policy, and observability. It also sets up NetworkPolicy: the CNI is what enforces it, so your network-security model is only as good as the CNI you picked.

Check yourself What’s the core difference between an overlay (VXLAN) CNI and a native-routing (BGP/VPC) CNI, and one trade-off of each? Overlay encapsulates pod packets inside node-to-node packets — portable and works on any network, but adds overhead and hides pod IPs; native routing gives pods directly-routable IPs the fabric understands — faster and transparent, but requires the underlying network (BGP peering or a cloud VPC) to cooperate.

Track 02 — Control plane & kernel

Kubernetes & container internals

The heart of this role. Everything in Kubernetes is a level-triggered reconcile loop pulling actual state toward declared state — and a container is ultimately just a namespaced, cgroup-limited process on the host.

08Kubernetes

You run kubectl apply

Why they askIt's the whole control-plane write path and the reconciliation model in one question.

Analogy Filing a change request at a town planning office: it’s checked for your identity, your permissions, and the building code (admission), then recorded in the official ledger (etcd) — after which inspectors (controllers) keep working until reality matches the approved plan.

kubectl sends the manifest to the API server, authenticated via your kubeconfig. The API server runs it through a fixed gauntlet: authentication, then authorization — usually RBAC — then admission controllers, mutating ones first (defaulting, injecting sidecars) then validating ones (policy, quotas). Only after it validates the object's schema does it persist the desired state to etcd. The API server is the one and only component that talks to etcd — everything else goes through it.

Now the controllers react, because they're all watching. The Deployment controller sees the new spec and creates or updates a ReplicaSet; the ReplicaSet controller creates Pod objects — which are still unscheduled. The scheduler is watching for pods with no node, filters the nodes that can't fit and scores the rest, and writes the binding. The kubelet on the chosen node sees a pod assigned to it and actually brings it up.

With server-side apply, the API server tracks which controller or user ‘owns’ each field, so two actors editing the same object get a clear conflict instead of silently clobbering each other — replacing the old client-side last-applied annotation. Writes also use optimistic concurrency via resourceVersion, so a stale update is rejected and retried rather than overwriting a newer one.

The key insight to say out loud: this is level-triggered reconciliation, not a script. Each controller continuously drives actual state toward desired state via watches, which is what gives you self-healing. etcd is the source of truth — protect and back it up — and admission control is where governance and policy live.

Check yourself What makes Kubernetes reconciliation ‘level-triggered,’ and why does that give you self-healing that a one-shot deploy script wouldn’t? Controllers continuously compare desired state (in etcd) to actual state via watches and act on the difference, not on a one-time event — so if a pod dies or drifts later, the loop notices and re-converges, whereas a script runs once and is blind to anything that changes afterward.

09Kubernetes

A container actually starts on a node

Why they askIt separates people who know "pods" from people who know Linux containers.

Analogy A container isn’t a tiny virtual machine — it’s an ordinary host process wearing a blindfold (namespaces) and a weight limit (cgroups), sharing the same kitchen (kernel) as everyone else.

The kubelet takes the pod spec and calls the container runtime over the CRI — containerd or CRI-O. The runtime pulls the image if it isn't cached, verifying layer digests, and assembles the root filesystem by stacking the image's read-only layers under a writable layer with an overlay filesystem. It creates the pod sandbox — the pause container that holds the shared network namespace — and calls the CNI plugin to give the pod its IP and wire up routes.

Then it launches the container: a low-level runtime like runc uses Linux namespaces — PID, network, mount, UTS, IPC, user — to give the process its isolated view, and cgroups to cap its CPU and memory. That's the whole trick: a container is just a normal host process with a restricted view of the system and enforced resource limits. Finally the kubelet starts running the startup, readiness, and liveness probes.

Before the app container runs, any init containers run to completion in order (for setup/migrations), and all containers in the pod share the pause container’s network and IPC namespaces (same localhost and IP) but keep their own mount and PID views. That shared-kernel reality is also why a bad seccomp/AppArmor profile or a privileged container widens the blast radius of any kernel bug.

Say the boundary plainly: a container is not a VM — it shares the host kernel, so a kernel CVE can be a container-escape, which is why image provenance, signing, and running as non-root matter. cgroup limits are also why right-sizing requests and limits is a correctness issue, not just tuning.

Check yourself Two containers in the same pod can reach each other on localhost but can’t see each other’s files or processes — which namespaces do they share, and which do they not? They share the network and IPC namespaces (via the pause container — same localhost/IP and SysV IPC), but have separate mount and PID namespaces, so filesystems and process trees are isolated.

10Kubernetes

A rolling update rolls out

Why they askIt's the default deploy strategy — and how you avoid dropping requests during it.

Analogy Repainting a bridge lane by lane while traffic keeps flowing — you only close as many lanes as the surge/unavailable budget allows, and only open a freshly-painted lane once it’s dry (Ready).

You change the pod template — typically a new image. The Deployment controller creates a new ReplicaSet and scales it up while scaling the old one down, governed by maxSurge (how many extra pods you'll allow) and maxUnavailable (how many you can lose at once). Crucially, a new pod only starts receiving traffic once it passes its readiness probe and its IP is added to the Service endpoints.

Old pods are terminated gracefully: they get a SIGTERM, any preStop hook runs, and the app has until the termination grace period to drain in-flight work before a SIGKILL. Traffic shifts pod by pod. If the new pods never go ready, the rollout doesn't tear everything down — it stalls at the progress deadline, and you can roll back to the previous ReplicaSet, which Kubernetes kept.

Contrast it with the Recreate strategy, which kills all old pods before starting new ones — brief downtime, but the right choice when two versions genuinely can’t coexist (incompatible schema, a singleton holding an exclusive lock). And a rollout doesn’t hang forever: if new pods never go Ready, it fails at progressDeadlineSeconds, leaving the old ReplicaSet intact to roll back to.

Readiness gates plus a PodDisruptionBudget are what actually make this zero-downtime; graceful shutdown and connection draining are what stop dropped requests at the tail. And I'd contrast it with blue-green and canary: rolling is resource-cheap but mixes versions during the window, so it demands backward-compatible changes.

Check yourself When would you deliberately choose the Recreate strategy over a rolling update, accepting a moment of downtime? When the old and new versions can’t safely run at the same time — e.g. an incompatible, non-backward-compatible schema change, or a singleton that must hold an exclusive lock/volume — so mixing versions (which rolling does) would be incorrect.

11Kubernetes

A node dies

Why they askIt tests whether you understand self-healing — and how long it actually takes.

Analogy A sentry who stops answering roll call: you don’t declare them lost instantly (a radio glitch is likely), you wait a defined grace period before sending replacements — because overreacting to a blip causes its own chaos.

The kubelet stops renewing its node lease — its heartbeat. After a grace period the node controller marks the node NotReady. Pods are not evicted instantly: there's a toleration-based eviction timeout, around five minutes by default, so a brief blip or network partition doesn't trigger mass churn. Once eviction kicks in, the pods on that node are marked for deletion, and their owning controllers — ReplicaSet, StatefulSet — create replacements that the scheduler places on healthy nodes.

In parallel, the endpoint controller drops those pods from Service endpoints as they go NotReady, so traffic stops being sent to a node that's gone. Stateless workloads recover cleanly; StatefulSets with attached ReadWriteOnce volumes are trickier, because the volume must be safely detached and reattached, which sometimes needs fencing.

The actual lever behind that delay is a taint: a NotReady node gets node.kubernetes.io/unreachable, and each pod’s tolerationSeconds (~300s by default) decides how long it rides it out before eviction. A graceful node shutdown is different — the kubelet gets the signal and evicts pods cleanly — whereas a hard crash takes the full heartbeat-plus-toleration path.

The honest number is: recovery time is heartbeat timeout plus eviction delay plus reschedule plus pod startup — minutes, not seconds. What makes it graceful is spreading replicas with anti-affinity across nodes and zones, PodDisruptionBudgets, and keeping enough spare capacity that the survivors can absorb the load.

Check yourself Why doesn’t Kubernetes evict a dead node’s pods the instant the node goes NotReady, and roughly how long does full recovery take? To avoid mass churn from a transient blip or network partition, pods tolerate the unreachable taint for ~5 minutes before eviction; total recovery is heartbeat timeout + eviction delay + reschedule + pod startup — minutes, not seconds.

12Kubernetes

A liveness or readiness probe fails

Why they askConfusing the two is the source of a whole class of self-inflicted outages.

Analogy Readiness is “don’t seat customers at my table yet”; liveness is “this waiter has fainted, carry them out and send a fresh one.” Confusing the two gets a perfectly healthy waiter repeatedly carted off.

They mean different things. When a readiness probe fails, the pod is pulled out of the Service endpoints, so it stops receiving new traffic — but it is not restarted. It's a "don't route to me right now" signal: I'm warming up, or a dependency I need is down. When it passes again, it's added straight back. When a liveness probe fails past its failure threshold, the kubelet kills and restarts the container. That's a "this process is wedged, recycle it" signal. A startup probe exists to protect slow-booting apps so liveness doesn't kill them before they've finished starting.

Detection time is just arithmetic: periodSeconds × failureThreshold — too tight and a GC pause trips it, too loose and a wedged pod lingers. Probe type matters too: exec probes fork a process every check (expensive at scale), while HTTP/gRPC/TCP are cheap; and a slow-booting app needs a startupProbe so liveness doesn’t execute it before it has finished starting.

Here's the classic incident, and I'd tell it: someone points the liveness probe at an endpoint that checks a shared dependency — the database, say. The database has a brief hiccup, so every replica fails liveness at the same time, and the kubelet restarts all of them at once, turning a two-second blip into a full outage with a cold start. The rule I set as a standard: keep liveness cheap and local — just "is this process responsive" — and use readiness for anything that depends on something else.

Check yourself Your pods restart every few minutes under load with no crash in the logs — how could an over-aggressive liveness probe be the cause? Under load a GC pause or slow response can exceed the probe’s timeout × failureThreshold, so the kubelet judges the live process ‘wedged’ and restarts it — a self-inflicted restart loop; loosen the thresholds (or move the check to readiness) so transient slowness doesn’t kill a healthy process.

13Kubernetes

The Horizontal Pod Autoscaler scales

Why they askThe pod-vs-node scaling chain and its cold-start latency trip a lot of people up.

Analogy A thermostat for pods: it reads the ‘temperature’ (a metric), compares it to the target, and adds or removes pods — but the furnace (a new node) can take minutes to warm up, so a sudden cold snap isn’t met instantly.

The HPA periodically reads a metric — CPU or memory from metrics-server, or a custom or external metric — and compares it to a target. The math is simple: desired replicas is roughly current replicas times current metric over target metric, rounded up. It writes that number to the Deployment's replica count, and the ReplicaSet creates or removes pods. To stop it flapping, there's a stabilization window, especially on scale-down.

But new pods don't help instantly: they still have to be scheduled and pass readiness. And if there's no spare room on existing nodes, they sit Pending until the Cluster Autoscaler — or Karpenter — provisions a new node, which takes minutes. So there's a real cold-start chain: metric breaches, HPA reacts, pods schedule, maybe a node boots, pods go ready.

HPA v2 lets you scale on multiple metrics at once and shape reactivity with the behavior field (separate scale-up/down policies and stabilization windows). For spiky or queue-driven work the modern answer is KEDA: it scales on event sources (Kafka lag, queue depth, cron) and can scale to zero — which CPU-based HPA can’t.

Two things I'd flag as an architect. First, HPA scales pods and the Cluster Autoscaler scales nodes — for spiky traffic you pre-scale or hold headroom because that chain is too slow to catch a sharp spike. Second, scaling on CPU is often wrong; scale on the signal that reflects real saturation — queue depth, requests per second, or p95 latency.

Check yourself Why is scaling a queue-worker on CPU often wrong, and what signal should drive it instead? CPU may stay low while the backlog explodes (the worker is I/O-bound or waiting), so CPU doesn’t reflect real saturation; scale on the work itself — queue depth / consumer lag (e.g. via KEDA) — which directly measures how far behind you are.

14Kubernetes

A pod gets OOMKilled

Why they askIt ties cgroups, exit codes, and requests-vs-limits into one concrete failure.

Analogy A room with a strict occupancy sign: the fire marshal (kernel OOM killer) doesn’t ask the fattest person to slim down — there’s no ‘throttle’ for memory — it simply removes them, hard, exit 137.

Each container's memory limit is enforced by its cgroup. When the process tries to allocate past that limit, the kernel's OOM killer terminates it — you see exit code 137, which is 128 plus signal 9, a SIGKILL. The kubelet reports the container state as OOMKilled and restarts it per the restart policy; if it keeps happening, the backoff grows and you land in CrashLoopBackOff.

An important nuance: it's usually the cgroup limit that fires, not the host being out of memory — one container can be OOMKilled on a node with plenty of free RAM. Separately, node-level memory pressure can make the kubelet evict pods, which is a different mechanism.

That’s the key asymmetry: CPU over-use is throttled (slowed), but memory over-use can only be killed — you can’t slow down RAM. Your QoS class, set by how requests/limits compare, decides who dies first under node pressure: BestEffort (no requests) is evicted before Burstable, and Guaranteed (requests == limits) is protected longest.

The fixes are about right-sizing and awareness. Requests drive scheduling, limits drive the kill, so set both deliberately. Watch whether it's a genuine leak versus honest under-provisioning. And remember runtimes must be container-aware — a JVM or Node heap has to be capped below the container limit, or the runtime cheerfully grows into a SIGKILL. Because the kill is abrupt with no cleanup, design to tolerate it.

Check yourself Why can a container be OOMKilled even though the node has gigabytes of free RAM, and what distinguishes it from node-pressure eviction? Because its own cgroup memory limit fired, not the host’s — it exceeded its ceiling regardless of free node memory; node-pressure eviction is the separate case where the kubelet evicts whole pods because the node is low on memory.

A Service routes traffic to a pod

Why they askMost people say "it load-balances" without knowing there's no proxy in the path.

Analogy A Service is a permanent phone number that always rings whoever’s on shift — callers never learn the staff’s personal numbers (pod IPs), which change constantly underneath.

The detail worth knowing: in the default iptables mode, kube-proxy isn't a proxy in the request path at all — it writes kernel-level DNAT rules, and the kernel rewrites the destination. On top sit ClusterIP versus NodePort versus LoadBalancer, headless services, and Ingress or the Gateway API.

Two levers worth naming: externalTrafficPolicy: Local preserves the client’s source IP and skips an extra hop (at the cost of uneven balancing), versus Cluster which spreads load but SNATs the source IP; and a headless Service (clusterIP: None) returns the pod IPs directly in DNS, which is how StatefulSets get stable per-pod addressing.

The point to make is decoupling: clients target a stable Service and never care that pods are churning underneath, because readiness plus EndpointSlices keep the backend set honest. The reason people moved from iptables to IPVS and eBPF is that iptables rule evaluation scales poorly with thousands of services — a real platform-scale concern.

16Kubernetes

RBAC authorizes (or denies) a request

Why they askAuthorization is the step right after authentication in every API call — and least-privilege RBAC is table stakes for a platform owner.

Analogy Authentication proves who you are (your badge is real); RBAC decides what that badge opens — and Kubernetes RBAC is deny-by-default, so a badge opens nothing until a rule explicitly grants it.

After the API server authenticates a request (who are you — a user, group, or ServiceAccount), it authorizes it with RBAC. The model is four objects: a Role (namespaced) or ClusterRole (cluster-wide) lists allowed verbs (get, list, create, delete…) on resources (pods, secrets…); a RoleBinding or ClusterRoleBinding grants that Role to a subject. Permissions are purely additive and allow-only — there is no deny rule — and the default is deny, so anything not explicitly granted is refused.

The most important subject in practice is the ServiceAccount: every pod runs as one, and its token is what the workload presents to the API. Grant that SA only the verbs it truly needs — a pod that reads one ConfigMap should not be able to list all Secrets cluster-wide, because if the pod is compromised, its RBAC is the attacker’s permissions.

I treat RBAC as a least-privilege exercise, especially for ServiceAccounts and controllers: scope Roles to namespaces, avoid wildcard verbs/resources, and never bind cluster-admin to a workload. I’d use kubectl auth can-i to test grants, audit for over-broad bindings (a common real-world finding), and remember that access to Secrets or to create pods/exec is effectively privilege escalation. This pairs with admission policy (Kyverno) and NetworkPolicy as the three layers of in-cluster least privilege.

Check yourself Why is granting a workload’s ServiceAccount broad RBAC (say, list Secrets cluster-wide) a security risk even if the app ‘seems trusted’? Because if that pod is ever compromised, the attacker inherits exactly the SA’s permissions — broad RBAC turns a single breached pod into cluster-wide secret access or escalation; least-privilege RBAC bounds the blast radius of any compromise to only what that workload genuinely needs.

17CI/CD

You git push and a pipeline runs

Why they askThey want to hear where quality, security, and provenance gates actually sit.

Analogy An assembly line with inspection gates: nothing moves to the next station unless it passes the checks — and the finished part is stamped with a tamper-proof serial number (digest) and a signature saying who built it.

The push updates the remote branch, and a webhook — or polling — notifies the CI system. It matches trigger rules on branch, path, or tag and spins up a runner, usually ephemeral for isolation. The pipeline is itself a prime attack surface — ‘poisoned pipeline execution,’ secret exfiltration from a compromised build, or a malicious dependency — so modern practice hardens it: least-privilege ephemeral runners, pinned/verified actions and base images, and short-lived OIDC federation to the cloud instead of stored keys. I frame the pipeline as the enforcement point for everything non-negotiable: tests and scans as gates, image signing and an SBOM for provenance, and — for our agentic work — evals as a release gate the way unit tests are. Check yourself Why is ‘short-lived OIDC federation to the cloud’ preferred over storing a long-lived cloud access key in the CI system? Why they askPull-based delivery and drift detection are core to a modern platform team.

Why they askState, the plan/diff, and locking are where Terraform incidents come from.

21CI/CD

A blue-green cutover happens (and a rollback)

Why they askBecause instant rollback is the whole selling point — and the database is the catch.

Analogy Two identical stages, one lit (blue) and one dark (green): you rehearse the new show in the dark, then flip one switch so the audience is watching green — and flip it back instantly if it flops.

You stand up a full parallel environment — green — beside the live one — blue — running the new version, typically sharing the stateful backing services like the database, Kafka, and the search cluster. You validate green with smoke tests while blue still serves every request. The cutover itself is a routing switch: you flip the load balancer, Ingress, or Gateway route from blue to green, and all traffic moves at once.

Rollback is simply flipping that route back to blue — which is the entire point. Recovery is at the routing layer and effectively instant, with no rebuild or redeploy. The costs are real: double the resources during the window, and you have to handle in-flight requests and shared state carefully.

The routing is the easy part; shared state is the catch, which is why schema changes must be backward-compatible (expand-contract) or green breaks blue. A finer-grained alternative is a feature flag: ship the code dark to everyone, then turn the feature on for a cohort at runtime — decoupling deploy from release without standing up a parallel environment.

The hard part is never the routing — it's the data. Because both versions share backing services, schema changes must be backward-compatible, done as expand-then-contract migrations, or green breaks blue. In practice I've used a short maintenance window to absorb in-flight requests rather than claim true zero-downtime, and I flip Ingress or HTTPRoute rules while the underlying ALB stays put. Canary is the incremental sibling — shift 5%, watch the metrics, then 50, then 100.

Check yourself In a blue-green cutover the rollback is instant — so why is the database usually the hard part? Because both versions typically share the same database, so a schema change the new version needs must not break the old version still serving during the window (and after a rollback); changes must be backward-compatible (expand-then-contract), or an ‘instant’ rollback leaves the schema incompatible with the restored code.

Track 04 — Fundamentals & failure

Linux & reliability

Underneath every container is a Linux process, and underneath every incident is a resource that ran out or a dependency that slowed down. These are the fundamentals that let you reason about failure instead of guessing.

23Linux

A Linux process is created

Why they askIt's why containers need proper PID 1 handling for signals and zombie reaping.

Analogy A photocopier that only re-inks a page when someone actually writes on it (copy-on-write): forking is cheap until the child diverges from the parent.

The classic model is fork-then-exec. A process calls fork(), which creates a near-identical child — same memory image, but copy-on-write, so pages are only physically duplicated when one side writes to them. The child then calls exec() to replace its image with a new program. The parent gets the child's PID and can wait() on it; when the child exits it becomes a zombie — just an exit status — until the parent reaps it. Orphans get adopted by PID 1, which is expected to reap them.

Signals coordinate the lifecycle: SIGTERM to ask politely, SIGKILL to force it, SIGCHLD to tell a parent a child died.

Cheaper variants exist — vfork/posix_spawn avoid duplicating the address space when you’ll immediately exec — and a thread is really clone() sharing the address space rather than copying it, which is the fork-vs-thread trade. In a container, your app is usually PID 1 of its own PID namespace, which is precisely why signal-forwarding and zombie reaping become your problem.

This is exactly why PID 1 in a container is a real concern. If your app runs as PID 1 and doesn't reap children, you accumulate zombies; worse, many apps as PID 1 don't forward SIGTERM to their children, so graceful shutdown silently breaks and the pod gets SIGKILL'd instead. That's why we run a tiny init like tini as PID 1. It's also why fork is expensive at scale, and why prefork servers exist.

Check yourself Why do we often run a tiny init like tini as PID 1 in a container instead of the app itself? PID 1 has special duties — reaping orphaned zombie children and forwarding signals — that most apps don’t perform; if the app is PID 1 and ignores these, zombies pile up and SIGTERM may not reach children, so graceful shutdown silently fails and the pod gets SIGKILL’d.

24Linux

The system runs out of memory

Why they askOvercommit and the OOM killer explain a lot of "why did that process just vanish."

Analogy A hotel that overbooks (overcommit) betting not everyone shows up — when they all do, the manager (OOM killer) evicts the guest using the most rooms, instantly and without notice.

Linux hands out more virtual memory than it physically has — that's overcommit — betting that not everyone uses their allocation at once. When that bet fails and the kernel can't satisfy allocations even after reclaiming what it can — evicting page cache, swapping if swap is on — it invokes the OOM killer. It scores every process with an oom_score, roughly proportional to memory footprint and tunable via oom_score_adj, and sends SIGKILL to the worst offender to reclaim memory fast.

On a bare host that can kill something important and unexpected. Under cgroups — so, containers — hitting the cgroup's memory limit triggers a scoped OOM kill of just that container instead of a host-wide hunt.

Before the kernel OOM killer fires, the system often thrashes — swapping frantically, grinding to a crawl — which is slower and more insidious than a clean kill. Modern userspace tools (systemd-oomd, earlyoom) act earlier using PSI (pressure stall information), killing proactively based on memory-pressure stall rather than waiting for the kernel’s last-resort hunt.

The practical stance: set memory requests and limits so kills are scoped and predictable; Kubernetes historically wants swap off so you fail fast rather than thrash; hunt leaks proactively; and protect critical daemons with oom_score_adj. Because the kill is a SIGKILL with no cleanup, anything holding a lock or a partial write has to be designed to recover.

Check yourself Why does Kubernetes historically prefer swap off on nodes, trading some capacity for fail-fast behaviour? With swap on, a memory-pressured node thrashes — silently slowing every workload as it pages to disk — which is hard to detect and reason about; swap off makes the container hit its limit and get OOMKilled cleanly and predictably instead, so failures are fast and scoped rather than a slow mystery.

A disk fills up

Why they askThe held-open-file and inode-exhaustion gotchas separate the experienced from the rest.

Analogy A filing cabinet can fill up two different ways: no drawer space left (bytes), or no more labels to tag folders (inodes) — and a drawer you ‘emptied’ stays full if someone’s still holding the folder open.

Writes start failing with ENOSPC — no space left on device — and what breaks depends on who needs to write. The database can't commit and may go read-only or crash; the app can't write logs or temp files; and on a Kubernetes node the kubelet detects disk pressure and starts garbage-collecting images and evicting pods.

Two gotchas worth naming. First: deleting a big file doesn't free the space if a process still has it open — the inode survives until the last file descriptor closes, so you delete the log and df doesn't budge until you restart the writer. Second: you can be completely out of inodes while bytes are still free, if something created millions of tiny files — writes fail even though df shows space.

In Kubernetes the container angle matters: logs and temp files in the writable layer and emptyDir count against the node’s ephemeral storage, so a chatty log can trip node disk-pressure eviction — set ephemeral-storage requests/limits and emptyDir sizeLimit. And remember du (walks files) and df (asks the filesystem) disagree exactly when a deleted-but-held-open file is eating space.

The standards are boring and effective: alert on disk well before 100%, not at it; put logs and data on separate volumes so a runaway log can't take down the database; enforce log rotation and retention; and in Kubernetes know your ephemeral-versus-persistent storage — emptyDir counts against node disk, and node disk-pressure eviction is a real failure mode to design around.

Check yourself You deleted the giant log file but df still shows the disk full — what’s happening and what actually frees the space? A process still has the file open, so its inode (and blocks) survive until the last file descriptor closes — the directory entry is gone but the data isn’t; restart or signal the writer (or truncate via /proc/<pid>/fd) to release it.

26Reliability

A connection pool gets exhausted

Why they askIt's the anatomy of a cascading failure — the interview's favorite reliability story.

Analogy A revolving door with a fixed number of slots: when the room beyond slows down, people take longer to clear the door, slots fill, and everyone behind is stuck — and a crowd shoving harder (retries) only jams it worse.

A service holds a bounded pool of connections — to a database, or an HTTP client pool to a downstream service. When that dependency slows down, each request holds its connection longer, so the pool drains. New requests then block waiting for a free connection and eventually time out. Threads and requests pile up, latency climbs, and the service's own health checks may start failing.

Now it propagates: the callers upstream are waiting on this service, so their pools back up too. That's a cascading failure, and naive retries pour fuel on it — a retry storm multiplies load on an already-struggling dependency exactly when it can least take it.

The tell-tale signal to watch is pool wait time / saturation climbing before latency does — that’s the early warning. The fix has an order: bound the wait with aggressive timeouts first (so nothing blocks forever), then add circuit breakers and load shedding; and size the pool to the dependency’s real capacity, because a pool bigger than what the downstream can serve just moves the queue, it doesn’t remove it.

This scenario is the argument for a whole toolkit: aggressive timeouts everywhere so nothing waits forever; bounded pools and queues so overload is visible instead of unbounded; circuit breakers to stop hammering a dead dependency; load shedding to drop excess rather than collapse; retries with exponential backoff and jitter plus a retry budget; and bulkheads to isolate one slow dependency so it can't sink the whole service. And it only works if observability shows pool saturation, p99 latency, and queue depth so you see it building.

Check yourself Why do naive retries make a connection-pool/cascading failure worse, and what three patterns contain it? Retries multiply load on an already-struggling dependency exactly when it can least cope (a retry storm), accelerating the collapse; contain it with timeouts (bound every wait), circuit breakers (stop hammering a dead dependency), and backoff + jitter with a retry budget (spread and cap retries) — plus bulkheads to isolate the slow dependency.

28Linux

A container’s CPU gets throttled

Why they askIt’s the quiet, misdiagnosed sibling of OOMKilled — latency spikes with no crash and plenty of ‘spare’ CPU on the node.

Analogy Unlike memory, you can’t be ‘killed’ for using too much CPU — you’re put on a metered allowance: use your quota early in each 100ms window and you’re made to sit out the rest of it, stuttering, even while the node looks idle.

A CPU limit is enforced by the kernel’s CFS bandwidth controller as a quota per period — by default, so much CPU-time every 100ms. A limit of 500m means 50ms of CPU per 100ms period. If the container burns its quota before the period ends, it’s throttled: descheduled until the next period, even if the node has idle cores. Crucially, unlike memory, this is a slowdown, not a kill — so there’s no crash, just latency.

This produces a classic, baffling symptom: p99 latency spikes and the app feels stalled, yet node CPU utilisation looks low and nothing restarts. The tell is the container_cpu_cfs_throttled_periods metric climbing. It bites multi-threaded apps and bursty request handlers hardest — a JVM with many threads can exhaust a small quota in a few milliseconds and then stall for the rest of the window.

The standards I’d set: always set CPU requests (they drive scheduling and the fair share) but be deliberate about CPU limits — a too-low limit throttles a healthy app, and many teams deliberately omit CPU limits for latency-sensitive services so bursts can use idle cores, relying on requests for fairness. Watch the throttling metric, right-size based on real usage, and make runtimes CPU-aware (size thread pools / GOMAXPROCS to the limit). It’s the direct CPU parallel to the memory requests-vs-limits story — but throttle, not kill.

Check yourself An app has high p99 latency and feels stalled, but node CPU looks low and nothing is restarting — how could a CPU limit be the cause? Its CFS quota (the CPU limit) is too low, so it burns the allowance early in each 100ms period and is throttled — descheduled until the next period — even though the node has idle cores; it’s a slowdown not a kill, so there’s no crash; confirm via the CFS throttled-periods metric and raise or remove the limit.

Track 05 — Governance in the path

Secrets, policy & the edge

Where a platform enforces its rules at runtime: identity-based secrets from Vault, policy-as-code at admission with Kyverno, and the API gateway as the single governed front door. Each one sits in a critical path, so availability and blast radius are part of every answer.

29Vault

A pod fetches a secret from Vault

Why they askThey want to hear "no static, long-lived credentials" and how a workload proves its identity.

Analogy Instead of handing every worker a master key that never changes, each worker shows their staff badge (ServiceAccount JWT), and the key office (Vault) issues a single-use key that unlocks only their door and self-destructs on a timer (lease).

The pod needs a secret, but it should never ship with a long-lived token baked in. With the Kubernetes auth method, the workload presents its ServiceAccount JWT to Vault. Vault verifies that token back against the cluster's API with a TokenReview, maps the service account and namespace to a Vault role, and issues a short-lived Vault token whose policies are deny-by-default — it can read only the specific paths its role allows.

With that token the app reads its secret. Two flavors: a static secret from the KV engine, or — better — a dynamic secret, where Vault generates credentials on demand. The database engine, for example, creates a brand-new DB user with a lease and TTL, hands it over, renews it while it's in use, and automatically revokes it when the lease expires — so credentials are short-lived and unique per consumer. In practice you don't put Vault logic in the app at all: the Vault Agent Injector adds a sidecar, or the Secrets Store CSI driver mounts the secret as a file, authenticating and refreshing for you.

The subtle part is secret zero — how the workload proves identity without already holding a secret. It’s solved because the SA JWT is verifiable by Vault against the cluster’s API (TokenReview), so the cluster’s own trust bootstraps it. To survive a Vault blip, apps should cache their lease and renew, rather than calling Vault on every request — and dynamic secrets mean a leak self-heals when the lease expires.

The standard I set is: no static long-lived secrets in images or the pipeline. The workload gets an identity — its service account — and Vault issues short-lived, least-privilege, per-workload credentials, dynamic wherever the backend supports it, so a leak self-heals when the lease expires, with a full audit trail of who read what. On the GitOps side that pairs with external-secrets or sealed-secrets so nothing sensitive ever sits in Git.

Check yourself What is a ‘dynamic secret,’ and why is it more resilient to a leak than a static credential in the KV store? Vault generates it on demand with a lease/TTL — e.g. a brand-new database user, unique per consumer — and automatically revokes it when the lease expires; so a leaked dynamic credential is short-lived and traceable, and the exposure self-heals on expiry, unlike a static secret that stays valid until a human rotates it.

30Vault

Vault seals — and gets unsealed

Why they askIt probes whether you understand Vault's security model and HA, not just its API.

Analogy A bank vault that locks itself on every power cut: it still holds the gold (encrypted data) but needs several trusted managers to each turn their key (Shamir shares) — or a trusted automated custodian (cloud KMS) — before it will open.

Vault's storage is encrypted at rest behind a barrier. The data-encryption key is itself encrypted by a master key, and that master key is what's protected. When Vault starts — or after a manual seal or a crash — it comes up sealed: it has the ciphertext but not the key to decrypt it, so it can serve nothing until it's unsealed.

Unsealing reconstructs the master key. The classic mechanism is Shamir's Secret Sharing: the key is split into shares, and you need a threshold — say three of five — to reconstruct it, so no single operator can unseal alone. In production you almost always use auto-unseal, delegating that step to a cloud KMS or HSM so a node that restarts unseals itself without paging a human. For availability Vault runs as a cluster — one active node, standbys replicating via Raft integrated storage, with a standby promoted on failover.

A sharp operational gotcha: Vault treats audit as mandatory — if all configured audit devices fail to write, Vault blocks requests rather than operate unlogged, so a full audit-sink outage becomes a Vault outage. For multi-region, Enterprise performance/DR replication keeps standby clusters warm, and seal-wrap adds an extra encryption layer for sensitive values.

The design points I'd make: auto-unseal so a restart isn't an outage, but keep the Shamir keys as break-glass for when the KMS itself is unavailable; HA with Raft so there's no single point of failure; and — most important — Vault is a hard dependency for everything that fetches secrets, so consumers should cache their leases and degrade gracefully through a brief seal or failover window rather than hard-fail. And seal, unseal, and audit-device events are all monitored.

Check yourself Why do you use auto-unseal in production but still keep the Shamir key shares around? Auto-unseal (via cloud KMS/HSM) means a node that restarts unseals itself without paging a human, avoiding a restart becoming an outage; the Shamir shares are kept as break-glass for the case where the KMS itself is unavailable, so you can still unseal manually.

31Kyverno

Kyverno evaluates a resource at admission

Why they askPolicy-as-code is how a platform enforces standards at scale — and it plugs into the apply path.

Analogy A building inspector standing at the permit desk: before any resource is filed into the records (etcd), it must pass code — and the inspector can also auto-correct small things (inject a hard hat) or hand you companion permits (a default NetworkPolicy).

Remember the admission stage of kubectl apply: after authentication and authorization, the API server calls admission webhooks before it persists to etcd. Kyverno registers there as a dynamic admission webhook, both mutating and validating. So when a resource is applied, the API server hands it to Kyverno, which evaluates it against the ClusterPolicies you've written in plain YAML — no custom controller code, and no Rego to learn as you would with the Gatekeeper approach.

Kyverno does three kinds of thing. Validate — reject or warn if a pod runs as root, has no resource limits, or uses a :latest image. Mutate — inject defaults, like adding labels, a securityContext, or a sidecar. Generate — create companion resources automatically, such as a default NetworkPolicy or RoleBinding for every new namespace. A policy runs in enforce mode, which blocks the request, or audit mode, which allows it but records the violation in a PolicyReport. It also does background scanning of already-running resources, so you catch pre-existing violations and drift, not just new admissions.

The emerging in-tree alternative is ValidatingAdmissionPolicy (CEL expressions evaluated by the API server itself) — it removes the external-webhook-in-the-critical-path risk entirely for validation, though mutation and generation still need Kyverno/webhooks. Either way the rollout discipline is the same: ship in audit to measure blast radius, then flip to enforce.

I frame this as guardrails-as-code: the org's security and hygiene standards — Pod Security Standards, no privileged containers, required labels, signed-image verification — encoded as policy, version-controlled and GitOps-delivered like everything else. The rollout discipline matters: ship a new policy in audit first to measure blast radius, then flip to enforce. And name the trade-off — an admission webhook is in the critical path of every API write, so its failurePolicy, timeout, and HA must be set deliberately, or a broken policy engine can block all deployments cluster-wide.

Check yourself An admission webhook sits in the path of every API write — what’s the risk, and which setting governs what happens if the policy engine is down? If the webhook is slow or unavailable it can block all deployments cluster-wide; its failurePolicy decides the behaviour — Fail (closed: block writes, safe but risks an outage if the engine dies) vs Ignore (open: allow writes, available but lets policy be bypassed) — so it must be HA with a deliberately chosen failure mode.

32API Gateway

A request passes through an API gateway

Why they askThey want the line between a load balancer and a gateway, and where cross-cutting API concerns live.

Analogy The single staffed front door to a building full of offices: it checks your ID, your appointment, how often you’ve visited today (rate limit), then walks you to the right room — versus a turnstile (load balancer) that just lets anyone through to a free desk.

An API gateway is the single managed front door for your APIs — an L7 reverse proxy plus API-management concerns. A request arrives and runs through an ordered chain of filters or plugins: TLS termination; authentication — validate an API key, verify a JWT's signature, issuer, and expiry, or introspect an OAuth token; then authorization and scope checks; then rate limiting and quota enforcement per client; optionally request transformation — rewrite headers or paths, aggregate calls. Then it routes to the right upstream service, often with its own load balancing, retries, timeouts, and circuit breaking, and on the way back does response transformation, caching, and metrics and logging.

So the distinction from a plain load balancer is real: an LB just picks a healthy backend, while the gateway owns identity, throttling, and the API contract — it's policy enforcement plus routing. Concretely that's Kong, Apigee, or AWS API Gateway; and Kubernetes' Gateway API is the emerging standard for expressing this routing declaratively.

Patterns worth naming: a backend-for-frontend (a tailored gateway per client type), and the convergence onto the Kubernetes Gateway API (e.g. Envoy Gateway) as the declarative way to express this. The same shape is exactly an agent gateway for LLM/MCP traffic — one governed seam enforcing auth, routing, rate limits, and which models/tools an agent may reach.

I position the gateway as where cross-cutting API governance lives, so services don't each reinvent auth and rate limiting — centralized authN/z, quotas, versioning, observability, and a developer portal for consumers. Two caveats: it's a shared chokepoint, so it must be HA and its added latency budgeted; and I'd distinguish this north-south gateway from east-west service-mesh traffic. This is exactly the pattern for our agentic work too — an agent gateway fronting LLM and MCP tool calls to enforce auth, routing, rate limits, and policy on which models and tools an agent may reach.

Check yourself What does an API gateway own that a plain load balancer does not? Identity and the API contract: authentication (API keys, JWT verification, OAuth introspection), authorization and scopes, rate limiting and quotas per client, request/response transformation, and versioning/observability — a load balancer merely picks a healthy backend, while the gateway is the policy-enforcement front door.
