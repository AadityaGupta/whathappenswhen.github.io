DevOps · SRE · Infra — anti-patterns & the path out Interactive Field Guide

What Happens When…

Systems rarely fail from one bad decision — they rot from habits that felt reasonable at the time: a secret committed “just to unblock the demo,” a server SSH’d into and fixed by hand, a database quietly shared between two services, a prod repo that drifted from staging, an alert added for every log line. Each is an anti-pattern: a common, tempting practice whose cost shows up later and somewhere else. This guide names the ones that actually bite across git, IaC and Terraform, config management and Ansible, CI/CD, secrets, architecture, observability and SRE — and for each gives you the symptoms to recognise it, the causes (how teams accidentally create it), the impact and emergent problems it spawns, and — the point of the whole thing — a concrete, staged path out: where you are now, the intermediate steps, and the target state.

Track 01

Git & repository hygiene

The repo is the source of truth; when its hygiene slips — secrets in history, drift between environments, branches that never land — everything downstream inherits the mess.

01Secrets in git

Committing secrets straight into the repo

The anti-pattern An API key, password, private key or .env file gets committed into the repository, so the credential now lives in git history — readable by anyone who can clone, forever, across every fork and mirror.

Looks like Mailing a house key to everyone on your contact list, then changing your mind and asking them to ‘please forget they saw it’ — the envelopes are already out there.

Symptoms A secret scanner lights up, or GitHub blocks your push. You find password= or AKIA… with git log -p. Someone added a late .gitignore for .env — but the file is already tracked. A credential shows up in a public fork long after it was ‘removed.’
Why it happens Convenience under deadline — hardcoding is faster than wiring up a secrets manager. A .gitignore rule arrives after the file is already tracked, which does nothing. People assume a private repo is safe, forgetting forks, clones and leaked tokens.
Impact The credential is compromised the moment it is pushed and must be treated as such; deleting the latest copy is theatre while history, forks and mirrors retain it. Blast radius scales with the secret’s power — a cloud key can mean data exfiltration or crypto-mining on your bill.
The path out
  1. NowTreat any committed secret as breached: rotate it immediately at the source (revoke the old key, issue a new one). Scanning and purging come after rotation — the old value is already out.
  2. Step 1Install secret scanning: run gitleaks or trufflehog over full history to find everything, and enable GitHub push protection plus a pre-commit hook (gitleaks / git-secrets) so the next one is blocked before it lands.
  3. Step 2Move the secret out of code entirely: read it at runtime from a secrets manager (Vault, AWS/GCP Secrets Manager) or CI secret store, and then add it to .gitignore and git rm --cached the tracked file.
  4. Step 3Purge history with git filter-repo (or BFG), force-push, and have every collaborator re-clone — but only as cleanup, never as the fix, because rotation already neutralised the exposure.
  5. TargetSecrets never touch the repo: injected at runtime from a manager, scanned on every commit and push, with rotation-on-detection a reflex rather than a fire drill.

Check yourself A developer committed an AWS key, then ran git rm and committed the deletion. Are you safe now? No — the key is still in history and any clone or fork, so it is compromised. The only real fix is to rotate (revoke) the key at AWS; purging history with git filter-repo is cleanup, not a substitute for rotation.

02Git & repos

Separate, divergent repos for prod and non-prod

The anti-pattern Production and non-production live in different repositories (or permanent long-lived branches that are repos in disguise), so the same application is maintained twice and the two copies silently drift apart.

Looks like Keeping two copies of the same recipe in different kitchens: you tweak the salt in one, forget the other, and swear the dish ‘used to taste fine’ — nobody can say which copy is right.

Symptoms A bug is ‘fixed in staging’ but still live in prod because the fix never got copied across. Cherry-picking between repos is a routine chore. The two codebases have quietly diverged and nobody can tell you the real difference between them.
Why it happens It felt safer to ‘protect prod’ by isolating it, or the split is a historical accident nobody undid. Teams fear that one repo means a non-prod change can reach prod — so they duplicate instead of using environment config and promotion gates.
Impact The environments are no longer comparable, so passing in staging tells you little about prod. Every change is double work and a chance to forget one side; audits and rollbacks get murky because ‘the code’ has no single definition.
The path out
  1. NowPick the single source of truth — usually prod — and diff it against the other repo to make the drift explicit and reviewable before you touch anything.
  2. Step 1Reconcile the diff into the chosen repo so one codebase is provably correct for all environments, resolving each difference as either a real fix or genuinely environment-specific config.
  3. Step 2Externalise everything that legitimately differs into per-environment config (env vars, values-<env>.yaml, tfvars) — same code, different inputs — so no code difference is needed between environments.
  4. Step 3Introduce promotion: the exact artifact built once is promoted dev → staging → prod through a pipeline with gates, and freeze then archive the abandoned repo.
  5. TargetOne repo, one codebase; environments differ only by config and are reached by promoting the same immutable artifact, so ‘it worked in staging’ actually means something.

Check yourself A fix verified in the staging repo is still broken in prod a week later. What is the underlying anti-pattern, and the fix? Divergent prod/non-prod repos — the fix was never propagated. Converge to one repo with per-environment config and build-once/promote the same artifact across environments, so a staging pass is evidence about prod.

03Branching

Long-lived feature branches with no trunk

The anti-pattern Work happens on feature branches that live for weeks or months and merge back rarely, so main is not a continuously integrated trunk but a distant target everyone diverges from.

Looks like Six people writing different chapters of one novel in isolation for a month, then trying to staple them into a coherent book the night before the deadline — names change, plots contradict, nothing lines up.

Symptoms Merges are dreaded events measured in days, not minutes. Branches rot and need huge rebases against a main that moved on without them. ‘Integration’ is a scheduled, scary phase rather than a thing that happens continuously.
Why it happens A belief that isolation keeps things clean, or a review process so slow that branches pile up waiting. Big features feel like they need one big branch, and without feature flags there seems no way to merge unfinished work safely.
Impact You get merge hell and big-bang integration — conflicts, regressions and semantic clashes all surface at once, late. Code sits unintegrated and unvalidated for weeks, so bugs are found far from where they were introduced and velocity collapses near release.
The path out
  1. NowMeasure branch age and merge frequency to make the pain visible, and agree a ceiling — e.g. no branch older than a day or two — as the target to drive toward.
  2. Step 1Shrink the work: slice features into small, independently mergeable increments, and merge to main at least daily so integration happens continuously instead of in a lump.
  3. Step 2Adopt feature flags so incomplete work can merge to trunk dark — code integrates continuously but stays off in production until it is ready.
  4. Step 3Keep main releasable at all times with a fast CI gate on every push, so short-lived branches merge green and the trunk never rots.
  5. TargetTrunk-based development: everyone commits to a single trunk via short-lived branches merged daily, with flags decoupling ‘merged’ from ‘released.’

Check yourself A team wants to integrate continuously but has half-finished features that can’t ship. How do they merge to trunk daily without exposing unfinished work? Merge the incomplete code to main behind a feature flag that keeps it off in production. This is the core of trunk-based development: integrate continuously via short-lived branches; decouple merge from release with flags.

04Branch protection

No branch protection — force-push straight to main

The anti-pattern main accepts direct pushes (including --force) with no required review or passing CI, so unreviewed code reaches production and history can be silently rewritten.

Looks like A bank vault with the door propped open and no camera: most days nothing bad happens, but any single person can walk in, take what they like, and leave no trace of what the shelves held yesterday.

Symptoms Commits land on main with no pull request or approval. Someone’s git push --force erases others’ commits and nobody can reconstruct what was there. CI failures don’t block anything — red or green, it merges the same.
Why it happens Protection feels like friction on a small, trusting team, so nobody turned it on. ‘Move fast’ is read as ‘skip review,’ and force-push is the quick way out of a messy rebase — until it clobbers shared history.
Impact Unreviewed, untested code ships to prod, and a single mistaken force-push can destroy work with no audit trail. Compliance evidence (who approved what) simply doesn’t exist, and the integrity of history — the thing git is for — can no longer be trusted.
The path out
  1. NowTurn on a branch protection rule (or ruleset) on main today: block direct pushes and block force-pushes — that alone stops the history-rewrite risk immediately.
  2. Step 1Require pull requests with at least one approving review to merge, so no code reaches main unseen, and dismiss stale approvals on new commits.
  3. Step 2Make CI a required status check that must pass before merge, so a red build genuinely blocks and main stays shippable.
  4. Step 3Add CODEOWNERS so the right people must review their areas, and require branches to be up to date with main before merge to catch semantic conflicts.
  5. Targetmain is protected: no direct or force pushes, required reviews and green CI on every change, with an auditable record of who approved what.

Check yourself After a git push --force to main, a day of a teammate’s commits vanished and no PR records exist. Which one setting would have prevented both the data loss and the missing audit trail? A branch protection rule on main — blocking force-pushes prevents the history rewrite, and requiring pull requests gives the reviewed, auditable record. Add required CI so unreviewed, untested code can’t merge either.

05Repo bloat

Build artifacts and large binaries committed to git

The anti-pattern Compiled outputs, dependencies (node_modules), datasets, images and other large binaries get committed into git, where every version is stored forever in the object history of every clone.

Looks like Keeping every draft, offcut and empty paint tin in your backpack because you ‘might need them’ — soon you can barely lift the bag, and finding your keys takes ten minutes.

Symptoms A fresh git clone takes minutes and pulls gigabytes. The .git directory dwarfs the actual source. git status and diffs crawl, and CI spends real time just checking out the repo. Binary files show up as unreviewable blobs in PRs.
Why it happens It is the easiest thing to do — git add . sweeps everything in, and committing a build output or a dependency folder ‘just works’ today. There is no artifact registry set up, so the repo becomes the default dumping ground.
Impact Clones and fetches are slow for everyone, forever, because git keeps every version of every binary in history — and deleting the file later doesn’t shrink the repo. Diffs are meaningless on binaries, review is impossible, and storage/bandwidth costs grow without bound.
The path out
  1. NowFind the weight: run git-filter-repo --analyze (or git rev-list size tooling) to see which paths and blobs dominate the repo, so you fix the real offenders.
  2. Step 1Stop adding more: .gitignore build outputs and dependency folders, git rm --cached the tracked ones, and generate artifacts in CI instead of committing them.
  3. Step 2Give binaries a proper home — push build outputs to an artifact registry (Artifactory, GitHub/GitLab Packages, a container or OCI registry) and large assets to object storage, referenced by version, not vendored in git.
  4. Step 3For large files that genuinely belong with the code, adopt Git LFS so git stores a pointer and the bytes live in LFS storage, and purge the historical blobs with git filter-repo so clones actually shrink.
  5. TargetThe repo holds source and small text only; artifacts live in a registry, big assets in LFS or object storage, and clones are fast again.

Check yourself A team adds build/ to .gitignore and deletes it, but clones are still 3 GB. Why — and what actually fixes it? Those blobs are still in history, which every clone downloads; ignoring and deleting only affects the future. To shrink the repo you must rewrite history (git filter-repo) and host artifacts in a registry / Git LFS going forward.

06Repo strategy

Monorepo vs polyrepo chosen by accident

The anti-pattern The repository structure — one giant monorepo or many small polyrepos — emerged by habit rather than decision, with none of the boundaries, ownership or tooling that would make the chosen shape actually work.

Looks like A house that grew room by room with no plan: some families crammed into one hall with no doors, others scattered into sheds with no shared plumbing — both arrangements technically shelter people, badly.

Symptoms In an accidental monorepo, any change can touch anyone and the whole thing rebuilds and redeploys together. In accidental polyrepos, shared code is copy-pasted, versions drift, and a cross-cutting change means coordinating a dozen PRs. Either way, ‘who owns this?’ has no clear answer.
Why it happens The structure was never a decision — one repo ‘grew’ or teams spun up repos ad hoc. The real driver (team topology, release cadence, coupling) was never named, and the tooling that makes each model viable was never adopted.
Impact An unbounded monorepo becomes a giant blast radius where one change risks everything and CI is slow; scattered polyrepos become N repos drifting out of sync with duplicated code and brittle cross-repo changes. In both, missing ownership means slow reviews and orphaned code.
The path out
  1. NowName the real constraints — team boundaries, release cadence, how tightly code is coupled — and write down which repos you have and why, so the structure stops being invisible.
  2. Step 1Decide deliberately on mono- or poly- (or a pragmatic mix) against those constraints, and document the rule for where new code goes so the next service doesn’t land by accident.
  3. Step 2Add CODEOWNERS and clear ownership boundaries either way, so every path has an accountable team and reviews route correctly.
  4. Step 3Invest in the tooling the choice demands: for a monorepo, build-graph tools (Bazel, Nx, Turborepo) with affected-only builds and path-scoped CI; for polyrepo, shared libraries with real versioning plus automation for cross-repo changes.
  5. TargetA consciously chosen structure with enforced boundaries, clear ownership and tooling that contains blast radius (monorepo) or prevents drift (polyrepo) — the shape fits how the teams actually work.

Check yourself A monorepo where every commit triggers a full build and can break any team — is ‘split into many repos’ the fix? Not automatically — splitting trades blast radius for drift and cross-repo pain. The real fix is the deliberate decision plus the missing tooling: for a monorepo, affected-only builds (Bazel/Nx/Turborepo), path-scoped CI and CODEOWNERS to contain the blast radius.

Track 02

IaC & Terraform

Infrastructure as code is only as good as its discipline — these are the habits that turn Terraform from a source of truth back into a source of surprises.

07ClickOps

ClickOps — changing infrastructure by hand in the console

The anti-pattern Infrastructure is created and modified by clicking around the cloud console (or running ad-hoc CLI commands), so the running system diverges from — or was never described by — any code.

Looks like Rearranging a stage set live during the show by hand every night, then wondering why opening night can never be recreated: there is no script, only whatever the crew remembered to move.

Symptoms terraform plan shows changes nobody made in code — that’s drift. Resources exist that no Terraform manages. ‘How was this set up?’ is answered by a person’s memory, not a repo. Rebuilding the environment elsewhere is a research project.
Why it happens The console is immediate and the incident is now — clicking is faster than a PR under pressure. ‘Just this one quick change’ becomes the norm, and read/write console access is handed out broadly because it always was.
Impact The real infrastructure and the code describe different systems (drift), so Terraform may try to revert a critical manual fix — or destroy a resource it doesn’t know about. Nothing is reproducible, disaster recovery is a gamble, and every manual change is an unaudited, unreviewed edit to production.
The path out
  1. NowSwitch on drift detection — terraform plan on a schedule, or Terraform Cloud / driftctl — so you can at least see where reality and code disagree.
  2. Step 1Bring the unmanaged resources under code: terraform import (or generate config via import blocks / terraformer) so the console-born infrastructure now has a code definition.
  3. Step 2Close the back door: reduce console and broad CLI access to read-only for humans, so new changes must go through code, and route genuine emergencies through a logged break-glass path.
  4. Step 3Make code the only way in — all changes via PR and pipeline — and have drift detection open an alert (or auto-revert) whenever something is touched outside the pipeline.
  5. TargetThe console is read-only, every change is code reviewed and applied by the pipeline, and drift detection guarantees the running system matches the repo.

Check yourself Someone fixed an outage by editing a security group in the console. The next terraform apply wants to undo it. What are you looking at, and how do you prevent the recurrence? Drift from ClickOps — code and reality disagree, so Terraform reverts the manual fix. Capture the change in code (import / reconcile), make the console read-only with a break-glass path, and run drift detection so changes outside the pipeline are caught.

08Terraform state

Terraform state in git (or no remote backend)

The anti-pattern The terraform.tfstate file is committed to git or kept only on a laptop, with no shared remote backend — so there is no locking, no encryption and no single trustworthy copy of what Terraform believes exists.

Looks like Keeping the one master ledger of every account in a notebook people photocopy and scribble in independently — two edits the same afternoon and you no longer know what anyone actually owns.

Symptoms Merge conflicts in .tfstate (a file you should never hand-merge). Two people run apply at once and the state gets corrupted or resources duplicated. Secrets sit in plaintext inside the state file in the repo. ‘Whose copy of state is current?’ is a real question.
Why it happens Local state is the zero-config default, so a project starts that way and never graduates. Committing the file feels like ‘sharing’ it with the team, and nobody wanted to stand up a backend and locking before shipping the first resource.
Impact Concurrent applys with no locking corrupt state, which can orphan or double-provision real infrastructure. State routinely contains secrets in plaintext, so committing it is a credential leak. A lost or conflicted state file means Terraform no longer knows what it owns — a genuine recovery nightmare.
The path out
  1. NowGet state out of git immediately: git rm --cached terraform.tfstate*, add it to .gitignore, and treat any secret that was in it as leaked and rotate it.
  2. Step 1Stand up a remote backend with encryption at rest — S3 (SSE), Terraform Cloud / HCP, GCS, or an Azure Storage account — and migrate with terraform init -migrate-state.
  3. Step 2Turn on state locking so concurrent applies can’t collide: S3 with a DynamoDB lock table (or S3 native lockfile / Terraform 1.11+ with OpenTofu equivalents), which backends like Terraform Cloud provide automatically.
  4. Step 3Lock down and back up the backend: least-privilege access, bucket versioning for recovery, and audit logging on state reads/writes.
  5. TargetState lives in an encrypted, access-controlled remote backend with locking and versioned backups; it is never in git and never on one person’s machine.

Check yourself Two engineers ran terraform apply at the same time against state committed in the repo, and now resources are duplicated. Which two backend features would have prevented this? A remote backend with state locking (e.g. S3 + DynamoDB lock table, or Terraform Cloud) — locking serialises concurrent applies so they can’t corrupt state, and a remote backend gives one shared, encrypted copy instead of a committed file.

09State design

One monolithic Terraform state for everything

The anti-pattern The entire estate — network, databases, clusters, every app, all environments — lives in a single Terraform state and root module, so one plan/apply touches the whole world at once.

Looks like Wiring every light, appliance and the furnace in the house to one fuse: changing a bulb means flipping the main breaker, and one short takes everything dark.

Symptoms terraform plan takes many minutes and refreshes hundreds of resources to change one. A single lock blocks the whole org from applying. A small change’s plan is terrifying because it shows the entire estate. Everyone needs broad credentials because everything is in one place.
Why it happens It started as one small project and simply accreted — splitting later felt risky. One state is conceptually simpler and avoids wiring up cross-state references, so the monolith grew because nobody wanted to pay the refactor cost.
Impact Blast radius is the entire estate: a bad apply or a corrupted state can damage unrelated systems. Plans are slow, a single lock serialises every team, and because low-churn foundations (VPC) share state with high-churn apps, routine changes carry foundation-level risk.
The path out
  1. NowMap the resources into layers by lifecycle and blast radius — foundation/network, data, platform (clusters), apps — and by environment, so you can see the natural seams to split along.
  2. Step 1Carve out the first independent state at a clean seam using terraform state mv or moved blocks (or stand up the new config and import), starting with a low-risk layer to prove the pattern.
  3. Step 2Wire the states together read-only via remote state data sources or published outputs (e.g. SSM/outputs), so apps read network/platform values without being able to change them.
  4. Step 3Continue splitting by environment and blast radius, and adopt Terragrunt (or a stacks/workspaces convention) to keep many small states DRY and orchestrated.
  5. TargetMany small, independent states partitioned by lifecycle, blast radius and environment — fast plans, scoped locks, least-privilege credentials, and a change to apps that can’t endanger the network.

Check yourself A one-line change to an app’s tags produces a 12-minute plan that refreshes the VPC, the database and every other app, and blocks a teammate’s apply. What’s the fix — and the first move? Split the monolithic state by lifecycle and blast radius (foundation / data / platform / apps, per environment). First move: map the seams, carve out one independent state with state mv / moved, and connect them via read-only remote state data sources.

10DRY / modules

Copy-pasting Terraform per environment

The anti-pattern Each environment is a duplicated folder of nearly identical .tf files (dev/, staging/, prod/), copy-pasted and then hand-edited, instead of a reusable module driven by per-environment inputs.

Looks like Hand-copying the same form three times and tweaking each: inevitably one copy gets a correction the others miss, and three ‘identical’ forms slowly tell three different stories.

Symptoms A fix made in prod/ never reaches dev/ and staging/. The three folders have quietly diverged and no one can enumerate the differences. ‘Add a resource to every environment’ means the same edit pasted three times — and forgotten once.
Why it happens Copy-paste is the fastest way to spin up the next environment, and modules feel like premature abstraction on day one. ‘We’ll refactor later’ never arrives, so the duplication ossifies into three codebases.
Impact Changes are 3× the work and 3× the chance to forget one environment, so the environments drift and ‘passed in staging’ stops predicting prod. Bugs fixed in one place silently persist in the others, and the duplication multiplies review and maintenance burden without limit.
The path out
  1. NowDiff the environment folders to surface exactly where they’ve drifted, and separate real config differences from accidental ones — that diff is your module’s variable list.
  2. Step 1Extract the shared infrastructure into a reusable module (one definition), and reduce each environment to a thin root that calls the module — converging the drift as you go.
  3. Step 2Drive the per-environment differences through variables and *.tfvars (or workspaces), so the environments share one definition and differ only by inputs like size and count.
  4. Step 3Pin and version the module (registry or git tag) and promote versions across environments, so prod can lag dev deliberately rather than by accident; use Terragrunt if you want to keep the roots DRY too.
  5. TargetOne versioned module, per-environment tfvars/workspaces for the real differences, and changes made once — environments stay in lockstep by construction.

Check yourself A security-group fix in prod/main.tf left dev/ and staging/ vulnerable because they’re copy-pasted folders. What’s the structural fix? Extract a single reusable module and have every environment call it, passing differences via variables/tfvars (or workspaces). Then a fix is made once in the module and applies everywhere — eliminating the copy-paste drift.

11Secrets in .tf

Hardcoded values and secrets in .tf files

The anti-pattern Passwords, API keys and environment-specific literals (region, sizes, account IDs) are written directly into the .tf files, so the config is rigid and secrets end up committed to git and baked into Terraform state.

Looks like Writing the safe’s combination on a sticky note taped to the safe, in permanent marker: anyone who sees the safe sees the code, and you can never quietly change it.

Symptoms A password = "…" or access key sits in a committed .tf file, and a secret scanner flags it. Changing region or instance size means editing code, not a variable. The same literal is pasted across resources, and terraform.tfstate contains the secret in plaintext.
Why it happens Inlining a value is the quickest path to a working apply, and variables feel like extra ceremony early on. The secret is needed to provision a resource, so it gets typed in ‘temporarily’ and never extracted.
Impact The config can’t be reused across environments without editing code, so it invites the copy-paste trap. Worse, secrets land in two places at once — git history and Terraform state — both readable by more people than you think, and a committed credential must be treated as compromised.
The path out
  1. NowRotate any secret that was hardcoded (it’s in git history and state — treat it as leaked), and run a scanner over the repo to find every literal secret.
  2. Step 1Parameterise the non-secret literals into input variables with *.tfvars per environment, so region, size and counts are inputs, not code edits.
  3. Step 2Pull secrets from a secret manager at plan/apply time via data sources (Vault, aws_secretsmanager_secret_version, SSM SecureString) instead of literals, and mark variables sensitive so they don’t print in logs.
  4. Step 3Minimise secrets in state: prefer resources that reference a manager, let the app fetch secrets at runtime rather than Terraform provisioning them, and keep the state backend encrypted and locked down regardless.
  5. TargetNo literals in code — config comes from variables/tfvars and secrets from a manager via data sources — so modules are reusable and credentials never live in git or (where avoidable) in state.

Check yourself An engineer removes a hardcoded DB password from main.tf and replaces it with a variable. Is the secret now safe? No — it’s still in git history (so rotate it) and, if Terraform still sets the password, it’s in state in plaintext. Pull it from a secret manager via a data source, mark it sensitive, keep the backend encrypted, and rotate the exposed value.

12IaC CI

apply without plan review and no IaC CI

The anti-pattern Engineers run terraform apply locally — often with -auto-approve — with no pull request, no plan posted for review and no policy checks, so infrastructure changes reach prod unreviewed and ungoverned.

Looks like A surgeon operating with no pre-op checklist and no second pair of eyes, deciding what to cut mid-procedure: most days it’s fine, until the day they remove the wrong thing and no one caught it.

Symptoms Changes are applied straight from laptops; the first anyone hears of a change is after it’s live. A routine apply quietly destroys and recreates a database because nobody read the plan. There’s no record of who approved what, and no automated guardrails on what’s allowed.
Why it happens Running apply locally is the obvious workflow and setting up IaC CI is upfront effort. -auto-approve removes an ‘annoying’ prompt, and plans are long and dull so people skim or skip the diff.
Impact A plan shows destroys and replacements before they happen — skip it and you get surprise data loss or outages, applied by one person with no second check. With no CI or policy gates, nothing stops a mistaken or malicious change, and there’s no audit trail for compliance.
The path out
  1. NowStop blind applies: ban -auto-approve and make every change go through a pull request where a human reads the full terraform plan before anything is applied.
  2. Step 1Automate plan-on-PR in CI — GitHub Actions / GitLab CI or Atlantis / Terraform Cloud — so every PR posts its plan for review, and apply runs from the pipeline after merge, not from laptops.
  3. Step 2Add policy-as-code gates — OPA/Conftest, Sentinel, or tfsec/Checkov — so the pipeline fails PRs that violate rules (public buckets, no encryption, oversized instances) automatically.
  4. Step 3Require manual approval for production applies (and protect the branch), so prod changes need an explicit, recorded human gate on top of the automated checks.
  5. TargetEvery infra change is a reviewed PR with a plan in CI, policy-as-code guardrails, pipeline-run applies and an explicit prod approval — surprises and unaudited changes are structurally prevented.

Check yourself A terraform apply -auto-approve from a laptop destroyed and recreated a production database. Name the layered controls that would have stopped it. A PR with the plan reviewed would have shown the destroy/recreate; plan-in-CI (Atlantis / TF Cloud) removes laptop applies; policy-as-code (OPA/Sentinel) can block destructive changes; and a manual prod approval adds a final recorded gate. Drop -auto-approve.

13Immutable infra

Snowflake servers you can’t rebuild

The anti-pattern Each server has been hand-tuned over years — a package here, a kernel flag there, a config file edited live — so its real state lives only on the box and in someone’s memory, never in code.

Looks like A bonsai tree pruned daily for a decade by one gardener: beautiful, unique, and utterly unreproducible — when the gardener leaves or the pot cracks, no one else can grow it back.

15Ansible

Playbooks that break on the second run

The anti-pattern Playbooks are written as imperative scripts — piles of shell and command tasks that append lines, run installers, or mutate state — so running them twice does something different from running them once.

Looks like A recipe that says “add salt” with no target amount: follow it once and the dish is fine; re-run it to be safe and you’ve salted it twice — the instruction never asks what state the pot is already in.

Symptoms A re-run duplicates lines in a file, errors on “already exists,” or restarts services that didn’t change. Everything reports changed on every run, so you can’t tell a real change from noise. --check mode fails or lies because shell tasks can’t predict themselves.
Why it happens Teams translate their old bash runbooks into Ansible line-for-line instead of thinking in desired state. Reaching for command/shell is quick when you don’t know the right module, and “it worked once” hides the second-run bug.
Impact Playbooks become unsafe to re-run, so nobody dares converge regularly — which reintroduces drift. Dry-run (--check) and idempotence testing are impossible, convergence isn’t self-healing, and every run is a fresh risk rather than a no-op when nothing changed.
The path out
  1. NowFind the offenders: grep for shell and command tasks and the ones with no change detection — these are your non-idempotent hotspots.
  2. Step 1Replace them with purpose-built modules that declare desired state — ansible.builtin.package state=present, copy, lineinfile, service — instead of commands that mutate.
  3. Step 2For unavoidable command tasks, add guards: creates=/removes=, a when: condition, or changed_when: so they only run (and only report changed) when they truly change something.
  4. Step 3Prove it: run the playbook twice in CI and assert the second run reports zero changes; add --check dry-run to the pipeline so plans are reviewable.
  5. TargetEvery playbook is idempotent — safe to run repeatedly, converging to the same state and reporting changed only when reality actually differs — so continuous convergence becomes self-healing.

Check yourself A playbook runs clean the first time but fails the second with “file already contains this line.” What property is it missing, and which module pattern fixes it? It’s missing idempotence — it mutates rather than declaring desired state. Replace the shell/echo >> append with a state-declaring module like lineinfile (or blockinfile/copy), which adds the line only if absent, so the second run is a safe no-op and --check can predict it.

16Ansible

Looks like Keeping separate hand-copied address books for home and work: update a friend’s number in one and forget the other, and now you have two “sources of truth” that disagree and you can’t tell which is right.

Symptoms “It works in staging” but breaks in prod because the prod copy drifted. A fix has to be pasted into three files and someone always misses one. Diffing the environment playbooks shows accidental, undocumented differences nobody intended.
Why it happens Copy-paste is the fastest way to stand up a new environment, and hard-coding the one value that differs feels simpler than parameterising. Over time, per-environment hotfixes calcify into permanent, unexplained forks.
Impact Staging stops being a faithful test of prod, so it validates nothing. Changes are error-prone and slow, bugs reproduce in only one environment, and the “logic” and the “config” are so entangled you can’t reason about either.
The path out
  1. NowDiff the environment playbooks and separate genuine config differences (hostnames, sizes, replica counts) from accidental drift — the accidental differences are bugs to erase.
  2. Step 1Extract the shared logic into a single reusable role, so there’s exactly one copy of “how to configure this thing.”
  3. Step 2Push every per-environment value into group_vars/ and inventory (one group per environment), so the role is identical and only the variables change.
  4. Step 3Delete the per-environment playbooks; run the one role against a chosen inventory/group — ansible-playbook site.yml -i inventories/prod — so environment is a selection, not a fork.

18Drift

The anti-pattern Config management runs once at build time and then never again. Over weeks, live changes, manual tweaks, and ad-hoc fixes pile up, so running machines silently diverge further and further from the code that supposedly describes them.

Looks like A house that’s never maintained: one loose tile, then a damp patch, then a rotten beam — each small neglect invisible until the day the ceiling comes down and you can’t trace which drip started it.

Symptoms Two “identical” servers behave differently and no one knows the delta. Re-running the playbook months later makes a surprisingly large number of changes. Failures feel random and environment-specific, and “it was fine last month” is a common refrain.
Why it happens Convergence is treated as a one-time provisioning step, not a continuous process. Non-idempotent playbooks made re-running scary, so teams stopped — and every live fix (the SSH anti-pattern) adds another untracked delta that nobody reconciles.
Impact Reality drifts so far from code that the repo is no longer trustworthy, and rebuilding a box produces something subtly different. Failures become unreproducible and slow to debug, security baselines erode unnoticed, and small rot compounds into a surprise outage.
The path out
  1. NowMeasure the drift: run a scheduled --check (dry-run) converge across the fleet and report how many hosts and tasks would change — make the invisible rot a visible number.
  2. Step 1Make converging safe by ensuring playbooks are idempotent (see the non-idempotent anti-pattern), so re-running is a no-op when nothing has drifted.
  3. Step 2Converge continuously on a schedule (cron, AWX/Ansible Automation Platform, or a pull-based agent) so live state is pulled back to code automatically, not once a quarter.
  4. Step 3Alert on drift as a defect and treat recurring drift as a signal to move that workload to immutable rebuilds — replace the box from a fresh image rather than patching it back.
  5. TargetDrift is detected, bounded, and auto-corrected: machines continuously reconverge to code, persistent drift triggers an immutable rebuild, and the repo is once again a faithful description of production.

Those 40 changes are accumulated configuration drift — the gap between code and a box that’s been edited live and never reconverged. Continuous, scheduled convergence of idempotent playbooks (with drift detection, and immutable rebuilds for chronic offenders) keeps that delta near zero instead of letting it compound into a surprise.

CI is a feedback loop; these anti-patterns stretch that loop until it stops catching anything.

19Trunk-based dev

Hoarding changes in huge batches

The anti-pattern Developers work in isolation for days or weeks and integrate rarely, so each merge is an enormous batch of changes colliding with everyone else’s enormous batch all at once.

Looks like Six people editing the same shared document in private copies for a month, then trying to reconcile all six at midnight before launch — every paragraph conflicts, and no one remembers which version was right.

Symptoms Merges are dreaded multi-hour conflict-resolution marathons. A branch is “done” for days but not integrated, and integrating it uncovers problems nobody saw coming. Code review queues are stuffed with giant, unreviewable pull requests.
Why it happens Branches feel safe — isolation avoids stepping on others today — and large PRs feel efficient. Fear of breaking main, or a release process that only accepts “finished” features, pushes everyone to hoard work locally.
Impact Integration pain is deferred, not avoided — it concentrates into a painful big-bang merge and late discovery of design clashes. Feedback arrives days after the code was written (when context is cold), velocity is lumpy, and the true cost of a change is hidden until the end.
The path out
  1. NowShrink the unit of work: split the next feature into small, independently shippable increments, each a PR of a few hundred lines at most.
  2. Step 1Integrate to a shared main at least daily — merge small, finished slices continuously rather than parking a branch for a week.
  3. Step 2Adopt short-lived branches (hours to a day or two) and hide unfinished work behind feature flags so you can merge incomplete-but-safe code without exposing it.
  4. Step 3Make small-and-often the path of least resistance: require CI to pass on every PR and keep review turnaround fast so tiny changes flow without friction.
  5. TargetTrunk-based development: everyone integrates to main many times a day in small batches, conflicts are tiny and immediate, and “integration” stops being an event because it never stops happening.

Check yourself A team’s merges routinely take half a day of conflict resolution. What’s the root cause, and why does merging more often make merging easier, not harder? The path out

  2. Step 1Containerise the build — define the toolchain in a Dockerfile so it carries its own OS, tools, and libraries instead of borrowing the host’s.
  3. Step 2Run that same image everywhere: locally, in CI, and as the base for the runtime artifact — so dev, CI, and prod share one environment and parity gaps close.

  5. TargetHermetic, containerised builds from pinned inputs produce identical results on any machine; “works on my machine” is meaningless because every machine runs the same declared environment, and CI genuinely predicts prod.

Big-bang deploy — everything, everywhere, all at once

Impact Any defect is a full outage, not a 1% blip. Mean-time-to-detect is whatever your worst user’s patience is; rollback is also big-bang. The fear tax compounds into fewer, bigger, riskier releases.
The path out

  2. Step 1Adopt rolling updates with health checks and maxSurge/maxUnavailable limits so instances are replaced incrementally and a failing pod never takes the whole service down.
  3. Step 2Add a canary: route 1–5% of traffic to the new version, watch its error rate and latency against the stable version, and promote only if the signals hold.
  4. Step 3For stateful or risky changes use blue-green: stand the new version up beside the old, cut over atomically, keep the old environment warm as an instant fallback.
  5. TargetProgressive delivery as the default — Argo Rollouts or Flagger automate canary analysis and auto-rollback on bad metrics, so every change ships gradually and shrinks its own blast radius.

Staging reduces how often a bad change ships; it does nothing about blast radius when one does. The missing control is progressive delivery — canary/blue-green with automated analysis — so the inevitable escapee hits 1% of users for 90 seconds instead of everyone for an hour.

Manual, snowflake deploys — a runbook of clicks

The anti-pattern Shipping means a human following a document: SSH here, run these commands, click that button, edit this config — the real deploy process lives in someone’s head and fingers, not in code.

Looks like A landing checklist that only one senior pilot can actually fly, read aloud from a laminated card at 2am — every landing is a fresh performance, and a skipped line is found only after the wheels are already down.

Symptoms A wiki page titled “Release steps (IMPORTANT, read carefully).” Only one or two people “can” deploy. No two deploys are identical. Post-deploy surprises traced to a forgotten manual step. Releases wait for a specific person’s availability.
Why it happens The process grew organically and was never automated. Steps feel too fiddly or too dangerous to script. Tribal knowledge is job security. “We only deploy occasionally, so why invest?”
Impact Every deploy is error-prone and irreproducible; the runbook rots out of date; the deployer is a single point of failure (bus factor 1); there is no audit trail of what actually ran, and rollback is an equally manual, equally shaky ritual.
The path out
  1. NowWrite the runbook down completely and have a second person execute it verbatim — every gap, assumption and undocumented click surfaces as a step you can later automate.
  2. Step 1Script the steps into a single idempotent, re-runnable command (a deploy script in the repo) that takes a version as input — replace “edit the config” with code that renders it.
  3. Step 2Move that command into a CI/CD pipeline triggered from a versioned artifact, so the deploy runs on a server with logged output, not on someone’s laptop.
  4. Step 3Add gates in the pipeline — automated smoke tests, a manual approval for prod, environment promotion — so the pipeline, not a person, enforces the order and the checks.
  5. TargetOne-click (or fully automated) repeatable deploys: any authorised engineer ships the same way, every run is identical and audited, and the pipeline is the runbook — executable, version-controlled, and reviewed.

Check yourself “Our deploys are documented — we have a detailed runbook, so we’re fine.” Why is a thorough manual runbook still an anti-pattern, not the fix? A runbook is a human interpreter of a process that should be code. It drifts from reality, depends on the person executing it, has no real audit trail, and can’t be tested. The runbook is valuable only as the spec you automate from — the fix is turning it into a pipeline, not perfecting the prose.

27Rollback

No rollback — forward-only panic

The anti-pattern When a release goes bad there is no clean way back to the last good version, so the only option is to roll forward — write and ship an emergency fix while production is burning.

Looks like A submarine with hatches that only open one way: once you’ve gone through, the only escape from a flooding compartment is to keep swimming forward and hope the next door opens before you run out of air.

Symptoms Incidents say “we’re writing a hotfix” instead of “we’re rolling back.” Nobody is sure the previous artifact still exists or still runs. A migration already changed the schema, so going back would corrupt data. Outages last as long as it takes to code a fix under pressure.
Why it happens Artifacts are rebuilt rather than versioned and kept, so “the old one” isn’t sitting ready. Database migrations are destructive and not backward-compatible. No one practised a rollback, so it’s assumed to be impossible.
Impact Mean-time-to-recovery is gated on human coding speed during the worst possible moment; emergency fixes skip review and cause second incidents; data-destroying migrations make recovery genuinely irreversible; on-call dread goes up and deploy frequency goes down.
The path out
  1. NowGuarantee you can always name and fetch the last-known-good build: publish every release as an immutable, versioned artifact (an image tag or signed package) to a registry — never latest, never rebuilt in place.
  2. Step 1Make rollback a first-class, one-click pipeline action that redeploys a chosen previous version — and rehearse it in staging so it’s a known, boring procedure, not a theory.
  3. Step 2Split every schema change into expand → migrate → contract so old and new code both run against the intermediate schema; a rollback of code never meets a schema it can’t read.
  4. Step 3Decouple deploy from release with feature flags so most “rollbacks” become flag-offs — instant, data-safe, and not a redeploy at all.
  5. TargetFast, boring recovery: immutable versioned artifacts, one-click rollback, backward-compatible migrations, and flags — so the standard response to a bad release is “revert in seconds,” not “code a fix in panic.”

Check yourself A service can one-click roll back its code in seconds, but the on-call still refuses to roll back a particular release. What’s almost certainly blocking it, and how is it prevented next time? A non-backward-compatible database migration shipped with that release — the old code can no longer read the new schema, so reverting the binary would break or corrupt data. Prevent it with expand/contract migrations: add the new shape, backfill and dual-write, flip reads, and only drop the old columns much later, once rollback is no longer needed.

28Flags

The anti-pattern Deploying code and exposing the feature to users are the same event: the moment the binary lands in production, the new behaviour is live for everyone, whether it’s ready or not.

Looks like A theatre with no curtain: the only way to let the audience see the next scene is to rebuild the entire set on the live stage — and the only way to hide a scene that’s going badly is to tear the set down again in front of everyone.

Symptoms Half-finished work can’t be merged because it would go live. Big-bang “release days” where many features flip at once. Launches are timed to deploy windows, not to business readiness. The only way to turn a feature off is to deploy again.
Why it happens No flagging mechanism exists, so “merged” and “launched” are forced to mean the same thing. Long-lived branches hide unfinished work instead. A mental model where a deploy is a release.
Impact You can’t deploy continuously without exposing unfinished features, so integration gets batched and delayed; marketing/launch timing is hostage to engineering deploys; there’s no way to dark-launch, A/B test, or do a gradual user rollout; killing a bad feature means an emergency deploy.
The path out
  1. NowSeparate the two ideas in language and in process: deploy = code is in production; release = users can see it. Agree that merging to main and deploying should never require the feature to be user-visible.
  2. Step 1Introduce a feature-flag layer — a managed service (LaunchDarkly) or an open standard/toolkit (OpenFeature, Unleash) — and wrap new user-facing behaviour in an off-by-default flag.
  3. Step 2Ship unfinished work behind a flag that’s off in production, so you can merge and deploy daily; this unlocks trunk-based development and continuous delivery without exposing drafts.
  4. Step 3Use the flag for a progressive rollout — internal users, then 1%, then 10%, then everyone — and for instant kill-switches and A/B experiments, decoupled entirely from deploys.
  5. TargetDeploy continuously, release on a business decision: code flows to production all day behind flags, and launching, rolling back, or experimenting is a config change — not a redeploy.

Check yourself Enabling continuous deployment made a team nervous: “we can’t ship several times a day, half our work is unfinished and would go live.” What’s the missing capability, and what second practice does it unlock? Feature flags — they decouple deploy from release, so unfinished code ships to production dormant (off by default) and merging no longer means launching. Unlocked second: trunk-based development / continuous delivery, because short-lived branches can now integrate daily without exposing drafts, plus gradual rollouts, kill-switches and A/B tests as config.

29Parity

Environment parity gaps — prod isn’t staging

The anti-pattern Staging and production differ in ways that matter — different infra, versions, scale, or data — so passing in staging tells you little about how the change behaves in prod.

Looks like Rehearsing a play in an empty rehearsal room, then opening night on a raked stage with real lights, a full house, and a trapdoor the room never had — the lines were learned for a space that doesn’t exist.

Symptoms “It passed staging but broke in prod” is a recurring phrase. Staging runs one node where prod runs fifty. Staging has a tiny, clean, stale dataset. Config, OS, library or managed-service versions differ between the two. Staging is hand-built and drifts.
Why it happens Staging was set up manually and separately, not from the same IaC as prod. Prod-like scale or data is seen as too expensive or too sensitive. Environments are long-lived pets that each drift on their own.
Impact Staging gives false confidence — whole classes of bugs (scale, concurrency, data-shape, config, dependency-version) are invisible until prod; teams stop trusting staging and ship blind, or over-test and slow down; incidents recur because the test bed can’t reproduce them.
The path out
  1. NowMake the gaps explicit: diff staging against prod — infra, versions, config, scale, data shape — and write down exactly where they differ, so “parity” stops being a word and becomes a checklist.
  2. Step 1Build all environments from the same IaC modules (same Terraform/Helm, parameterised per env) so infra, versions and topology are identical by construction, not by luck.
  3. Step 2Give staging prod-like data — anonymised/subsetted production data or a realistic synthetic generator — and prod-like scale for the behaviours you most need to trust (load-test at prod ratios).
  4. Step 3Make environments disposable: spin up ephemeral, from-scratch environments per branch/PR so there are no long-lived pets to drift; pin every dependency so versions match dev→CI→prod.
  5. TargetHigh-fidelity parity — same IaC, same versions, prod-like data and scale, and ideally progressive delivery in prod (canary) as the final test — so “passed staging” is a real signal, not a hope.

Check yourself A change passes an identical, IaC-built staging environment and still falls over in prod. Code, config and infra all match — what two production properties most commonly cause this, and how do you close them? Scale and data. Staging usually runs far fewer nodes and a tiny, clean dataset, so concurrency limits, connection-pool exhaustion, N+1 queries on real data volumes, and hot-partition effects only appear at prod cardinality. Close them with prod-ratio load tests and anonymised/subsetted production-like data — and treat a canary in prod as the real final environment.

30Cadence

Infrequent deploys & Friday-deploy fear

The anti-pattern Releases are rare, large, and feared — batched up for weeks, shipped in a tense window, and never on a Friday — so each deploy carries weeks of accumulated, un-individually-tested change.

Looks like Only ever moving house once a decade: so much has piled up that each move is an exhausting, high-stakes ordeal you dread — which makes you do it even less often, so the next pile is even bigger.

Symptoms Deploys measured in weeks or months between them. “Never deploy on Friday” is a firm rule, not a joke. Releases are large batches of many changes. A failed release takes a long time to recover. Change failure rate is high and you can’t attribute a failure to one change.
Why it happens Each deploy is painful (manual, big-bang, no rollback), so the rational response is to do it less — a vicious cycle. Big batches feel “efficient.” Fear of the weekend is really fear of recovery, not of the day.
Impact Big batches mean more changes per release, so change failure rate rises and root cause is hard to isolate; lead time for a fix is long; low deploy frequency and high time-to-restore are exactly the four DORA keys of low performers; velocity and reliability both suffer, and burnout grows.
The path out
  1. NowStart measuring the four DORA metrics — deploy frequency, lead time for changes, change failure rate, time to restore — so cadence becomes a number you improve, not a vibe you argue about.
  2. Step 1Fix the things that make a deploy scary first (they’re the earlier cards): automated pipeline, one-click rollback, canary/progressive delivery, feature flags — cadence follows from safety, not willpower.
  3. Step 2Shrink batch size deliberately: deploy smaller changes more often so each release contains few changes and a failure is easy to attribute and revert — small batches are safer because they’re small.
  4. Step 3Deploy on-demand throughout the week, including Fridays: if recovery is fast and safe, the calendar stops mattering — the Friday ban is a symptom of slow recovery, so fixing recovery removes the ban.
  5. TargetElite cadence — frequent, small, low-drama deploys any day, with low change-failure rate and fast restore; the DORA metrics improve together because the same practices (small batches + progressive delivery + fast rollback) drive all four.

Check yourself “Deploying more often is obviously riskier — more deploys means more chances to break prod.” Using the DORA findings, why is this usually backwards? Because risk lives in batch size, not deploy count. Frequent deploys are small deploys: each contains few changes, so failures are rarer per deploy, easier to attribute, and faster to revert. Elite DORA performers deploy far more often and have lower change-failure rates and faster restore — the practices that raise frequency (automation, small batches, progressive delivery, fast rollback) are the same ones that lower risk.

Credentials are the keys to everything; these are the habits that leave copies of them lying around and the doors propped open.

31Secrets

Secrets in env vars, CI logs & baked into images

The anti-pattern Credentials are handed to apps as plaintext environment variables, printed into build logs, or copied into container-image layers — so the secret rides along wherever the config, the logs, or the image go.

Looks like Writing the house key’s cut on the key’s own fob, the spare’s fob, and a sticky note by the door — now “change the locks” means tracking down every copy you ever made before the old key is truly dead.

Symptoms printenv in a debug log dumps your database password. A secret appears in a CI job’s console output. docker history or an ENV/ARG layer reveals a token baked at build time. The same secret is pasted across CI variables, .env files and Dockerfiles.
Why it happens Env vars are the easy, 12-factor-looking default and nobody added a real injection path. Build steps echo commands that contain secrets. “Just bake the key in so the image works anywhere.” No distinction between config and secret.
Impact Secrets leak through any log aggregator, error tracker or crash dump; a child process or a dependency can read the whole environment; an image pushed to a registry carries the credential in a layer forever, even if a later layer “removes” it; revocation means hunting every copy.
The path out
  1. NowInventory where secrets live today — CI variables, .env files, Dockerfiles, env vars — and immediately turn on secret masking in CI and scrub/redact logs so you stop adding leaks while you fix the source.
  2. Step 1Stand up a secrets manager — HashiCorp Vault, AWS Secrets Manager, or GCP/Azure equivalents — as the single source of truth; stop storing secret values anywhere in the repo or CI config.
  3. Step 2Inject secrets at runtime, not build time: have the app or a sidecar fetch them from the manager on start; never put them in an image layer or an ARG. In Kubernetes, use the External Secrets Operator or a CSI driver to sync them in.
  4. Step 3Prefer short-lived, dynamically-generated secrets (e.g. Vault database creds) and mount them as files or fetched values — so even a leaked copy expires quickly and is tied to one workload.
  5. TargetSecrets never live in code, images, or logs: they’re injected at runtime from a manager, masked in CI, redacted in logs, and ideally short-lived — so “rotate” is one action in one place, not a scavenger hunt.

Check yourself A team moves its database password out of the Dockerfile and into a CI secret variable, then into a SECRET env var the container reads. Why is this still leaky, and what actually fixes it? Env vars are globally readable to the process and anything it spawns, trivially end up in crash dumps, error trackers and printenv debug logs, and encourage copies across CI configs. The fix is runtime injection from a secrets manager (fetched on start or mounted as a file via the External Secrets Operator/CSI), with log scrubbing and masking — ideally short-lived dynamic creds so a leak self-expires.

32Rotation

Shared static credentials, never rotated

The anti-pattern One long-lived username/password or API key is shared by a whole team or many services and effectively never changes — the same secret has authenticated every actor for years.

Looks like A single master key copied for the whole office, no log of who holds one — when someone leaves or a key goes missing, you can’t tell whose it was, so the only safe move is to re-key the entire building and hope you reach everyone.

Symptoms A credential whose created date is years ago and whose owner no one can name. “The service account password” pasted in a dozen configs. You can’t revoke access for one person or one service without breaking everyone. No audit trail of which actor did what.
Why it happens A shared account was simplest to set up and nobody ever untangled it. Rotation was never automated, so it “would break things” and got deferred forever. No per-identity model — humans and services all use the same login.
Impact A single leak compromises everything that credential touches, with a huge blast radius; you can’t revoke precisely, so a departure or breach forces a disruptive mass re-key; attribution is impossible, so audit and incident response are blind; compliance findings pile up.
The path out
  1. NowEnumerate every shared credential and what uses it, and flag the highest-blast-radius ones (prod DB, cloud root, CI master) for first action — you can’t rotate what you haven’t mapped.
  2. Step 1Give each human and each service its own identity and credential (per-service accounts, per-user logins, workload identities) so access can be granted, attributed and revoked individually.
  3. Step 2Move the secrets into a manager that supports automated rotation, and turn rotation on a schedule — short enough that a stale copy is worthless, automated so it never “breaks things” by surprise.
  4. Step 3Prove revocation works: disable one identity and confirm only it loses access; wire alerts on credential age and on use of a credential past its rotation window.
  5. TargetPer-identity, automatically-rotated, individually-revocable credentials — ideally short-lived/dynamic — so a leak is contained to one identity, revocation is a single targeted action, and every access is attributable.

Check yourself A single shared service-account password protects a critical system. Leaving aside “it’s old,” name the two capabilities you fundamentally cannot have while it stays shared and static — and the one change that restores both. You can’t do precise revocation (disabling one compromised actor without breaking everyone) and you can’t do attribution/audit (knowing which actor took an action). Both come from the same change: give every human and service its own per-identity credential — then rotation and least-privilege become possible on top.

33State

Secrets stored in Terraform state

The anti-pattern A password, key, or token is set as a resource attribute or variable in Terraform, so its plaintext value is written into the terraform.tfstate file — the state becomes a secrets file nobody treats like one.

Looks like A meticulous property inventory that, to be “complete,” also writes down the safe’s combination in the margins — now the inventory itself is as sensitive as the safe, but it’s photocopied and left where the inventory normally lives.

Symptoms terraform show or the state JSON reveals a cleartext password. A random_password or db_instance secret sits readable in state. State is in a backend (or worse, git) that more people can read than should see the secret. Plan output prints secret values.
Why it happens Terraform writes every managed attribute to state, including sensitive ones, by design. Generating secrets in Terraform (e.g. random_password) feels convenient. Teams forget state is a data store, not just a bookkeeping file.
Impact Anyone with read access to the state backend has the secret in plaintext — often a broader group than the secret warrants; state in git spreads it into history forever; sensitive = true hides it from console output but not from state; the state file becomes a high-value target.
The path out
  1. NowTreat the existing state as compromised-grade sensitive: ensure the backend is encrypted at rest, access is tightly scoped (few readers), and state is never in git; mark known-sensitive outputs sensitive = true to stop them printing in logs.
  2. Step 1Stop generating secrets in Terraform where you can: create and store them in a dedicated manager (Vault/AWS Secrets Manager) out-of-band, and have the app read them at runtime so Terraform never sees the value.
  3. Step 2Where Terraform must reference a secret, pull it via a data source from the secrets manager at apply time instead of hardcoding or generating it — and prefer resources that take a secret reference (an ARN/path) over the literal value.
  4. Step 3Rotate any secret that ever sat in state, since old state files and git history may still hold it; scan state and history for leaked values.
  5. TargetSecrets live in a purpose-built manager, not in state: Terraform holds references, not values; state is encrypted, access-scoped, and out of git — so reading state no longer means reading your secrets.

Check yourself A reviewer says “we’re fine — every sensitive variable is marked sensitive = true.” Why does that not actually keep the secret out of danger? sensitive = true only redacts the value from CLI/plan output — it still gets written to terraform.tfstate in plaintext. Anyone who can read the state backend (or git history, if state was ever committed) can read it. The real fixes are: encrypt and tightly scope the backend, keep state out of git, and above all don’t put secret values in Terraform — reference an external manager via data sources.

34Keys

Long-lived cloud access keys everywhere

The anti-pattern Static, never-expiring cloud access keys (an AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY pair, or equivalent) are minted and pasted into CI systems, laptops, scripts and servers to let them talk to the cloud.

Looks like Handing out permanent, un-dated backstage passes to every contractor, vendor and temp — years later the box office has no idea how many passes exist, who still has one, or which ones a thief could walk in with today.

Symptoms IAM users with ancient, active access keys. The same key pair in a dozen CI pipelines and a few laptops. “Key sprawl” — no one can enumerate every place a key lives. Leaked keys turning up in public repos and bots using them within minutes.
Why it happens Access keys are the quickest way to make a script or CI job authenticate, and they never expire so they never nag you. Workload identity / federation was more setup than anyone budgeted for. Keys get copied freely because copying is frictionless.
Impact A leaked long-lived key is valid until someone notices and manually revokes it — often after an attacker has mined crypto or exfiltrated data; sprawl makes revocation and rotation nearly impossible; there’s weak attribution; the attack surface is every machine and log that ever held the key.
The path out
  1. NowInventory all IAM users and access keys, disable unused ones, and set up alerting on key age and on leaked keys (e.g. GitHub push protection + provider leak detection) so a leak is caught in minutes, not months.
  2. Step 1Replace keys in CI with OIDC federation: let the CI provider (e.g. GitHub Actions’ OIDC) exchange a short-lived identity token for a temporary cloud role via STS — no static key stored in CI at all.
  3. Step 2Inside the cloud, give workloads workload identity instead of keys: IAM roles via IRSA for EKS pods, instance/task roles for EC2/ECS, GCP/Azure workload identity — the platform mints short-lived creds automatically.
  4. Step 3For humans, use federated SSO with temporary session credentials, not personal long-lived keys; set an org policy that blocks or flags creation of new static access keys.
  5. TargetNo static cloud keys anywhere: every machine, pipeline and person authenticates with short-lived, automatically-rotated credentials from OIDC/STS/workload identity — a leak expires on its own and key sprawl simply can’t accumulate.

Check yourself A CI pipeline needs to deploy to AWS. The quick answer is to store an access-key pair as a CI secret. What’s the modern keyless alternative, and what concrete risk does it remove? OIDC federation: the CI provider (e.g. GitHub Actions) presents a short-lived, signed identity token that AWS STS exchanges for temporary credentials scoped to a specific IAM role — no static key is ever stored in CI. It removes the standing risk of a long-lived key leaking from the CI config or logs and being usable indefinitely; the federated creds expire in minutes and are scoped to that workflow.

35IAM

Over-broad IAM & wildcard * permissions

The anti-pattern Roles and policies are granted sweeping access — Action: "*" on Resource: "*", or s3:* on every bucket — because scoping them precisely was fiddly, so everything can do almost anything.

Looks like Issuing every employee a master key that opens every door in the company “so nobody ever gets stuck,” including the vault and the server room — convenient right up until one lost key, or one bad hire, can walk into every room at once.

Symptoms Policies full of "Action": "*" and "Resource": "*". An app that only reads one bucket holds s3:* account-wide. AdministratorAccess attached to things that don’t need it. Nobody can say what a given role is actually allowed to do versus what it uses.
Why it happens Least-privilege is tedious to author up front, and a wildcard makes the error message go away immediately. Permissions are added when something breaks and never trimmed back. No tooling to show what’s actually used, so over-grants are invisible.
Impact A compromised workload or leaked credential inherits all that power — privilege escalation, lateral movement and data exfiltration across the whole account; blast radius is maximal; the gap between granted and used permissions is pure, unaudited risk; compliance and least-privilege requirements are violated by construction.
The path out
  1. NowFind the worst offenders: flag policies with Action: * / Resource: * and any AdministratorAccess that isn’t a human break-glass role — those are your highest-value fixes.
  2. Step 1Use access data to right-size: run IAM Access Analyzer (policy generation from CloudTrail usage) and last-accessed data to see which permissions are actually used, and draft least-privilege policies from that evidence.
  3. Step 2Scope every policy down to specific actions and specific resources (named ARNs, s3:GetObject on one bucket, not s3:*), adding conditions where it helps — and deploy via IaC so scoping is reviewed and versioned.
  4. Step 3Reserve powerful access for break-glass: no standing admin; elevation is temporary, approved, logged and alerted. Add preventive guardrails (SCPs / permission boundaries) so wildcards can’t creep back.
  5. TargetLeast privilege by default: every identity holds only the actions and resources it demonstrably uses, admin is break-glass only, and Access Analyzer continuously flags unused or over-broad grants — so a compromised credential inherits the smallest possible blast radius.

Check yourself A service only ever does GetObject and PutObject on one bucket, but its role has s3:* on * “to avoid permission errors.” Beyond style, what’s the real risk, and how would you right-size it with evidence rather than guesswork? If that role is compromised, the attacker inherits s3:* account-wide — delete every bucket, exfiltrate all data, change policies — so the blast radius is the whole S3 estate, not one bucket. Right-size with evidence: use IAM Access Analyzer policy generation + last-accessed data to see what the role actually uses, then write a policy scoped to s3:GetObject/s3:PutObject on that one bucket’s ARN, and add an SCP/permission boundary so wildcards can’t return.

36Scanning

No secret scanning or leak detection

The anti-pattern Nothing automatically checks whether credentials are being committed, pushed, or logged, so a leaked secret sits in the repo, history, or logs undetected until someone — often an attacker — happens to find it.

Looks like A bank with cameras but no one watching them and no alarm wired up: the break-in is recorded perfectly, and you only find out when the money’s already gone and someone thinks to rewind the tape weeks later.

Symptoms Secrets discovered by accident — a new hire greps the repo and finds an API key. A credential in git history that predates anyone’s memory. The first sign of a leak is a cloud bill spike or an abuse report. No pre-commit or CI step ever fails a build for containing a secret.
Why it happens Scanning was never set up because “we’re careful.” People assume .gitignore or code review will catch secrets (they don’t reliably). No ownership for detection; no process for what to do when a secret is found.
Impact Leaked secrets live for a long time before discovery, giving attackers a wide window; a secret in git history survives deleting the file, so “we removed it” is false comfort; without a rotate-on-detect reflex, even found leaks stay valid; you have no measure of how exposed you are.
The path out

A shared database between microservices

The anti-pattern Two or more services read and write the same tables directly, so the database — not an API — becomes the integration point between them.

Looks like Two chefs cooking from one unlabelled pantry: either can move the salt, and the other’s dish fails tonight — so eventually nobody dares reorganise the shelves at all.

Symptoms A schema change needs a cross-team meeting and a coordinated deploy. Several repos carry models for the same tables. You can’t say which service owns a column. One service’s slow query degrades another.

Impact Services can no longer deploy or evolve independently (a distributed monolith); the schema ossifies because any change may break an unknown consumer; lock contention and failures cross service boundaries; data ownership and on-call get muddy.
The path out

  4. Step 3Split the schema (separate schemas, then separate databases) behind the owner using the strangler fig pattern, migrating consumers one table at a time.

39Sync coupling

Why it happens Firefighting is visible and rewarded while prevention is invisible. Knowledge was never written down. Hiring and deadlines outpaced onboarding, so expertise concentrated in a few heads instead of spreading.
Impact A single person is a SPOF — the bus factor is one — so their illness or exit is an outage; they burn out from being always-on; others stay junior because they never get the reps; and the hero becomes a bottleneck on every change.
The path out
  1. NowName the risk out loud: list the systems with a bus factor of one and treat each as a reliability risk on par with a missing backup.
  2. Step 1Make the hero write while they work — turn the next few incidents they resolve into runbooks and architecture notes as part of the fix, not as a chore for later.
  3. Step 2Stand up a real on-call rotation with a primary and secondary, a documented escalation path, and a sane page load, so no single person owns the pager.
  4. Step 3Spread the knowledge deliberately: pair the hero with others on incidents, rotate who leads game days, and gate ‘done’ on a second person being able to operate the thing.
  5. TargetAny on-call engineer can handle a page from the runbook; heroics are rare and treated as a system failure to fix, not a badge; and prevention work is what earns recognition.

Check yourself Priya resolves 80% of your Sev-2s single-handedly, often after hours, and leadership keeps praising her saves. Why is this a reliability problem, not a success story? Because the system only works when Priya is available — she is a single point of failure with a bus factor of one, and she is on a path to burnout. The repeated saves are a symptom that no one else can operate the service and that prevention is being neglected; rewarding the heroics only deepens the trap. The fix is to spread her knowledge through runbooks, pairing and rotation, and to start recognising the quiet work that stops those Sev-2s happening at all.

51Postmortems

Blameful postmortems

The anti-pattern When something breaks, the review hunts for the person who ‘caused’ it — so incidents end in a name and a reprimand rather than in an understanding of how the system let a normal human action turn into an outage.

Looks like An airline that fired every pilot who reported a near-miss: within a year the reports stop — not because the near-misses stopped, but because nobody will admit to one anymore.

Symptoms Reviews circle around ‘who ran the command.’ People go quiet or defensive. Small incidents get hidden or relabelled to avoid a postmortem. Action items read ‘be more careful,’ aimed at individuals.
Why it happens An instinct that accountability means punishment. Pressure to show leadership that a cause was ‘dealt with.’ A belief that human error is a root cause rather than a symptom of a system that permitted it.
Impact Fear suppresses the honest reporting you depend on to learn; the same class of incident recurs because the systemic cause was never addressed; your best people leave; and MTTR climbs because engineers hesitate to act for fear of being blamed.
The path out
  1. NowAdopt the blameless rule explicitly: the postmortem assumes everyone acted reasonably with the information and tools they had, and asks how the system allowed it, never who is at fault.
  2. Step 1Use a template that bans names-as-causes: a factual timeline, contributing factors, what made detection or recovery slow, and what went well — kept separate from any performance conversation.
  3. Step 2Turn findings into concrete, tracked action items with an owner and a due date — guardrails, better signals, safer tooling — and review them until closed, not filed and forgotten.
  4. Step 3Make postmortems learning-first and widely shared, so the whole org learns from one team’s incident and reporting is rewarded rather than punished.
  5. TargetA culture where people volunteer incidents and near-misses, each one yields durable system improvements, and the real embarrassment is a recurrence of a known failure mode — not the original mistake.

Check yourself An engineer runs a migration that takes production down for twenty minutes, and the VP wants to know ‘who did this and what are we doing about them.’ What is the better framing? Reframe from the person to the system: how did one engineer’s routine action reach production unchecked and cause a 20-minute outage? That points at the real fixes — a missing review gate, no dry-run or canary, no fast rollback, a dangerous default. ‘Punish the engineer’ teaches the team to hide incidents and leaves the same trap for the next person. Blameless is not ‘no accountability’; the accountability is collective and aimed at hardening the system.

52Toil

Toil overload — most of your time on manual ops

The anti-pattern The team spends the bulk of its time on toil — manual, repetitive, automatable work that scales with the service and leaves nothing lasting behind — so there is never any capacity to engineer the toil away.

Looks like Bailing a leaking boat by hand so frantically that you never get a free moment to find and patch the hole — so you bail harder every week as the leak keeps growing.

Symptoms Days vanish into tickets, manual restarts, access requests and the same runbook steps. Engineers can’t point to anything they built this quarter. The ops queue grows with traffic. ‘We’re too busy to automate’ is said unironically.
Why it happens Toil is urgent and visible while automation is deferred as ‘nice to have.’ No one measures how much time toil eats, so it is never budgeted against. Growth adds load faster than manual process can absorb.
Impact A death spiral: more service means more toil means less time to automate means even more toil; engineers stagnate and burn out; reliability projects never ship; and the team scales headcount linearly with load instead of sub-linearly.
The path out
  1. NowMeasure it: for a few weeks have the team tag their work, then compute the fraction that is toil — you cannot cap what you don’t quantify.
  2. Step 1Set an explicit toil cap — the SRE norm is to keep toil under 50% of time — and ring-fence the remainder for engineering, protected like any other commitment.
  3. Step 2Rank toil by hours spent and automate the top of the list first: self-service the common requests, auto-remediate the repeated alerts, script the manual runbooks.
  4. Step 3Make toil a standing metric in reviews and feed it back into prioritisation and staffing — a team over its cap gets help or sheds scope, rather than being told to try harder.
  5. TargetToil sits below the cap and trends down as the service grows; the team spends most of its time on engineering that removes future toil, so capacity scales sub-linearly with load.

Check yourself Your SRE team is at 80% toil and says it has no time to automate. Adding two engineers didn’t help — six months later they’re at 80% again. Why, and what breaks the cycle? Throwing bodies at toil just raises the toil ceiling: more hands absorb more manual work, the service keeps growing, and the ratio snaps back — the classic death spiral. The cycle breaks only by protecting capacity for engineering: cap toil under 50%, ring-fence time for automation regardless of queue pressure, and spend it on the highest-volume toil first so the manual load actually shrinks. Measure it so the cap is enforced, not merely aspirational.

53Runbooks

No runbooks — response lives in people’s heads

The anti-pattern When an alert fires there is no written procedure for it; the on-call engineer improvises from memory, old Slack threads and whoever they can wake up, so every incident is solved from scratch.

Looks like A fire station with no drills and no map of the building: when the alarm sounds the crew stands on the pavement debating which door to try, while the fire the alarm found instantly keeps spreading.

Symptoms A 3am page means guessing, grepping old chat, and escalating to the one person who knows. The same incident takes a different — and longer — path each time. New on-call engineers dread the pager. ‘Ask Sanjay’ is the runbook.
Why it happens Writing runbooks is never the urgent thing during or after an incident. Knowledge sat safely in experienced heads, so the gap was invisible until those people were unavailable. Alerts were added without a matching response.
Impact MTTR is high and wildly variable because every response is reinvented; incidents hinge on specific people being reachable; on-call is stressful and error-prone; and the knowledge walks out the door when someone leaves.
The path out
  1. NowStart with the pages that actually fire: for each existing alert, write a one-page runbook — what it means, how to confirm it, the first diagnostic steps, how to mitigate, and when to escalate.
  2. Step 1Make the runbook link a required field on every alert, so a page arrives with its procedure attached and no alert exists without a documented response.
  3. Step 2Pressure-test the runbooks with game days — rehearsed failure drills — so gaps and stale steps are found in daylight, not at 3am, and the rotation gains real reps.
  4. Step 3Promote the well-worn, deterministic runbook steps into auto-remediation, so the system fixes the routine cases itself and only pages a human for the genuinely novel.
  5. TargetEvery alert carries a tested runbook; MTTR is low and consistent regardless of who is on call; the common failures self-heal; and knowledge lives in the repo, not in one person’s memory.

Check yourself Leadership asks why your MTTR is both high and unpredictable — the same database failover took eight minutes once and ninety another time. What’s the likely cause and the first fix? The response isn’t written down, so each engineer reinvents it and the time depends on who happens to be on call and how fast they reach the one expert. The first fix is a tested runbook for that failover, attached to its alert, then a game day to prove it works for anyone on the rotation — which collapses the variance. Once the steps are deterministic, automate the failover so it doesn’t need a human at all.

54Platform eng

The DevOps/SRE team as a new silo and bottleneck

The anti-pattern A central ‘DevOps’ or ‘SRE’ team is created to own deployment and operations — and promptly becomes the very wall between Dev and Ops that DevOps was meant to remove, now with a ticket queue in front of it.

Looks like Renaming the wall between two warring departments ‘the bridge’ and posting one overworked clerk on it: every crossing still needs a form, and the queue to see the clerk is longer than the old wall ever was.

Symptoms Developers raise tickets to ‘the DevOps team’ to get anything deployed, and wait. That team is a permanent bottleneck and escalation sink. Devs don’t know how their own service runs in production. ‘DevOps’ is a job title, not a way of working.
Why it happens An org re-labels its existing ops silo ‘DevOps’ without changing the handoffs. Leadership wants one team ‘accountable’ for delivery. Centralising control felt safer than giving every team production access.
Impact Handoffs and queues reappear exactly where DevOps aimed to delete them; lead time grows with every team that depends on the central one; developers feel no ownership of production, so quality and on-call suffer; and the bottleneck team burns out serving everyone.
The path out
  1. NowName the anti-pattern: the central team is a queue, not a bridge. Measure its ticket backlog and the lead time teams wait on it — that is your bottleneck, quantified.
  2. Step 1Shift ownership back to the teams that build: adopt you-build-you-run — stream-aligned teams own their service in production, on-call included — so the central team stops being the deploy gateway.
  3. Step 2Recast the central team as a platform team that builds a self-service platform — the thing teams use without a ticket — plus an enabling team that coaches rather than doing the work for them (Team Topologies).
  4. Step 3Pave golden paths: opinionated, well-supported routes to build, ship and operate a service, so the easy way is also the compliant, observable, reliable way.
  5. TargetTeams self-serve deployment and operate what they build; the platform team runs the platform as a product that lowers their cognitive load; and no human sits in the critical path of a routine deploy.

Check yourself A company renames its ops team ‘the DevOps team’ and routes all deploys through it via tickets. Lead time gets worse. Why did re-badging backfire, and what actually fixes it? DevOps is a way of working — shared ownership and fewer handoffs — not a team you can name into existence. Putting one team in charge of all deploys just rebuilds the Dev-to-Ops wall with a ticket queue in front of it, so lead time grows. The fix is structural: give delivery teams you-build-you-run ownership, and turn the central team into a platform team offering self-service golden paths (with enabling teams to coach), so it accelerates everyone instead of gating them.

55Culture

Buying tools instead of changing culture

The anti-pattern DevOps is treated as a shopping list — a CI server, a Kubernetes cluster, an observability suite — on the belief that installing the tools delivers the outcomes, while the handoffs, incentives and silos that actually slow delivery are left untouched.

Looks like Buying a professional kitchen full of gleaming equipment and expecting Michelin food to appear — while the cooks still don’t talk to the waiters and each guards their own station.

Symptoms A sprawling tool estate, but lead time and failure rates haven’t moved. Teams were handed tools with no change to how they work together. Pipelines mirror the org chart, each silo’s stage bolted to the next. ‘We adopted X’ is the goal, with no outcome attached.
Why it happens Tools are concrete and purchasable; culture change is slow and political. Vendors sell ‘DevOps in a box.’ Leadership can point to a tool as progress far more easily than to changed behaviour.
Impact Conway’s Law wins — the new pipeline just encodes the old silos and handoffs; responsibility stays fragmented (‘not my stage’); the four DORA metrics don’t improve; and the org concludes ‘DevOps doesn’t work’ when it was never actually tried.
The path out
  1. NowMeasure outcomes, not tool count: baseline the four DORA keys — deployment frequency, lead time for changes, change-failure rate, and time to restore — so ‘better’ means moving those.
  2. Step 1Map the real flow of work and find the handoffs and wait states between silos — the delays usually live in the gaps between teams, which no tool purchase touches.
  3. Step 2Invest in people and communication: shared goals and on-call across Dev and Ops, blameless learning, and team structures that remove handoffs — then buy tools to support that flow, not to define it.
  4. Step 3Since Conway’s Law says your architecture mirrors your communication, deliberately shape teams around the flow you want (an inverse Conway move) so the tools reinforce it.
  5. TargetTools serve a culture of shared ownership and fast feedback; the DORA metrics improve because handoffs were removed; and new tooling is adopted to solve a named problem, with the outcome tracked.

Check yourself A company spent two years and a fortune on best-in-class CI/CD, Kubernetes and observability, yet it deploys monthly and takes days to recover. What did they buy, and what did they miss? They bought tools and skipped the culture. DevOps outcomes come from removing handoffs and sharing ownership between Dev and Ops; tooling only amplifies whatever working relationships already exist. With the old silos intact, Conway’s Law means the shiny pipeline just automates the old handoffs, so the DORA metrics don’t move. The missing work is organisational — shared goals and on-call, fewer handoffs, teams aligned to flow — and only then do the tools pay off.

56Platform eng

Running the platform as a project, not a product

The anti-pattern The internal platform is built as a one-off project — funded, delivered, declared ‘done’ and the team disbanded — rather than as a living product with an owner, a roadmap, and users whose needs keep changing.

Looks like Building a block of flats, cutting the ribbon, then firing the building manager and doing no maintenance: within a few years the lifts are broken, nobody fixes anything, and the tenants move out.

Symptoms The platform launched with fanfare and was then starved of investment. No one owns its roadmap; feature requests go nowhere. It’s stuck on the tech and assumptions of its launch year. Teams quietly build their own tools around it.
Why it happens Project funding rewards ‘delivered and closed,’ not ‘operated and evolving.’ Platforms get seen as infrastructure you finish, like a data centre, rather than software that needs product management. The team was temporary by design.
Impact The platform rots and drifts out of date; its users’ real needs are never fed back in, so adoption erodes; shadow tooling proliferates and fragments the estate; and the original investment is wasted as teams route around a thing nobody maintains.
The path out
  1. NowReframe it as a product, not a project: give it a named product owner and a standing team with ongoing funding — a platform is never ‘done’ while it has users.
  2. Step 1Treat your developers as customers: talk to them, understand their jobs-to-be-done, and keep a visible, prioritised roadmap driven by their pain rather than by a fixed original scope.
  3. Step 2Measure it like a product — adoption, developer satisfaction, and the time it saves (the MONK-style signals: are teams happy, is it widely used, does it speed delivery) — and steer by those numbers.
  4. Step 3Run a continuous delivery loop on the platform itself: regular releases, a public changelog, deprecation and support policies, and a feedback channel that actually changes the roadmap.
  5. TargetA long-lived platform product that evolves with its users, is measured on adoption and the delivery it unlocks, and earns its usage because it stays genuinely useful — not because anyone is forced onto it.

Check yourself An internal developer platform launched strongly two years ago, but adoption is now falling and teams are building their own tooling around it. It was delivered as a funded project that then ended. What’s the root cause? It was run as a project, not a product. A platform’s users and their needs keep changing, so a platform that stops evolving starts dying the day the project closes — it drifts out of date, stops solving current pain, and teams route around it. The fix is product thinking: a standing team with an owner, ongoing funding, developers treated as customers, a roadmap driven by their needs, and adoption and satisfaction measured so the platform keeps earning its usage.

57Adoption

The field-of-dreams platform, built in isolation

The anti-pattern A platform team designs and builds the ‘ideal’ platform in isolation on the assumption that ‘if we build it, they will come’ — then has to mandate its use because developers, who were never consulted, don’t adopt it willingly.

Looks like Architects designing a beautiful town with no roads to where people actually work, then passing a by-law banning every other route — residents comply, grumble, and quietly pine for the old shortcuts.

Symptoms The platform solves problems developers don’t have while missing the ones they do. Adoption happens only because it’s compulsory. Teams file exceptions and build workarounds. The platform team is surprised by how it’s actually used — or not used.
Why it happens The team built for its own idea of ‘right’ rather than observed developer pain. Talking to users felt slower than building. A mandate was easier to secure from leadership than genuine adoption was to earn.
Impact Low voluntary adoption and widespread resentment; forced technology that doesn’t fit real workflows, so productivity drops; shadow platforms spring up; and the platform team loses credibility, making the next thing even harder to land.
The path out
  1. NowStop building and go talk to developers: shadow real workflows and find their actual top pains — the platform’s job is to solve their problems, not to express an ideal.
  2. Step 1Pick one high-pain, high-frequency journey and make the platform’s version of it demonstrably easier than the status quo — win a few lighthouse teams by being better, not by decree.
  3. Step 2Build golden paths that are paved, not mandated: make the supported route so clearly the path of least resistance — faster, safer, less to think about — that teams choose it.
  4. Step 3Treat adoption as the scoreboard: measure it, keep a tight feedback loop with users, and let a supported escape hatch build the trust that pulls teams in voluntarily.
  5. TargetDevelopers adopt the platform because it genuinely removes their pain and lowers their cognitive load; the golden path is the obvious default; and mandates are unnecessary because the paved road is the one people want.

Check yourself A platform team builds for a year without consulting developers, launches, sees near-zero uptake, and persuades leadership to mandate it. Why is the mandate a red flag, not a fix? Needing a mandate is the symptom that the platform doesn’t solve real developer pain — it was built field-of-dreams style, for the team’s idea of ‘right’ rather than observed needs. Forcing adoption buys compliance and resentment, spawns workarounds, and burns the platform team’s credibility, while delivering none of the promised productivity. The real fix is to talk to developers, solve their top pains, and make the golden path so obviously better that it’s paved, not mandated — chosen, not enforced.

58Shift-left

Not shifting left — security and testing bolted on at the end

The anti-pattern Testing, security and governance are treated as end-of-pipeline gates run by separate teams after development is ‘finished,’ so defects and vulnerabilities surface at the most expensive possible moment — just before, or after, release.

Looks like Inspecting a car only once it rolls off the production line: every fault found means stripping back work already done, so inspection becomes the thing everyone dreads and tries to rush past.

Symptoms A manual security or QA gate blocks releases at the end. Bugs and CVEs show up in staging or production, not in the editor. Developers get vulnerability reports weeks after writing the code. Security is ‘the team that says no.’
Why it happens Quality and security grew up as separate specialist functions with their own gates. Giving developers the tools and responsibility felt risky. It is organisationally easier to add a checkpoint at the end than to change how everyone works.
Impact Defects caught late cost far more to fix and arrive after the context is lost; the end gate becomes a release bottleneck and a source of Dev-vs-Security friction; teams route around it under deadline pressure; and genuine risk ships because the gate is a rubber stamp, not a habit.
The path out
  1. NowMap where defects and vulnerabilities are currently caught, and how late — the cost and the friction both come from how far right that point sits; the goal is to move it left, toward the developer.
  2. Step 1Shift into the developer’s loop: fast unit and integration tests plus pre-commit hooks — secret scanning, linting, SAST — so the fastest feedback is also the earliest.
  3. Step 2Automate the checks in the pull request: tests, dependency and container scanning, and policy-as-code run on every PR, giving quick, specific feedback while the author still has the context.
  4. Step 3Make the CI pipeline the enforcing backstop — the same automated quality and security gates run there — so standards are consistent and version-controlled, not a manual human gate at the end.
  5. TargetQuality, security and governance are continuous and automated across the dev loop (DevSecOps): issues are caught in seconds where they’re cheapest to fix, security is built in, and the end-of-line gate is gone.

Check yourself Your security team runs a manual penetration-test gate right before every release; it routinely finds issues that force late rework and slip the date. What’s the systemic fix, beyond ‘test faster’? Move the feedback left so issues are caught where they’re cheap, not at the last gate. Put secret and SAST scanning in pre-commit and the editor, dependency and container scanning plus policy-as-code on every pull request, and the same gates automated in CI as the backstop — this is shift-left / DevSecOps. The late pen-test then becomes a confirmation, not a discovery, because the common classes of issue were already prevented in the dev loop, and security shifts from ‘the team that says no’ to guardrails developers own.
